# Agent 调查与改造建议（2026-09-05）

本文为调查结果和待讨论方案，不代表改造已经实施。依据当前产品总方针、Agent 产品方针、Agent 技术基线及实际代码。调查未修改业务代码、配置或正式业务数据，真实模型回合在事务中执行并回滚。

## 1. 结论与验证范围

现有事实库、统一图和候选工具确实已接通；主要问题是自然语言合约无法表达信息不足、候选投影丢失适用条件、推荐结果缺乏解释和可交互的图、经验调查默认关闭且不可见。建议保留 AI Workflow 和统一图，重做 Agent 合约、候选评估和结果呈现。

本次实测：

- 当前配置：`deepseek-v4-flash`，模型密钥已配置，StatusMatcher 开关为 false；未输出密钥。
- 当前数据库：2 个持有会籍、376 个目录节点；查询天合联盟、不限费用和挑战时得到 12 条正式候选。
- 真实模型：“用我已有的会籍，推荐到天合联盟的路线，可以付费也可以挑战。”返回 RECOMMEND。不能把问题概括成所有模型请求均失败。
- 真实模型：“我有什么能匹配的？”返回 AgentProviderError，底层为 ValidationError，位置 `interpretation.target`，原因为 `interpreted target requires a program or alliance`。
- 确定性复现：正确的 ASK_CLARIFICATION 在 target 为空时也无法通过合约；混合价格 50/200 USD 被选为 50；两步中一步“无需挑战”、一步未知被判为 NO_CHALLENGE。
- 运行 agent contracts/controller/API/waiting、candidate routes、StatusMatcher 相关测试，31 项通过。说明这些测试不足以覆盖上述缺陷。
- StatusMatcher Air France 公司页 HEAD 返回 200，仅证明网络和该 URL 可达。本次未启用报告采集，也未把 HEAD 当成页面解析和推荐联调通过。
- 2026-09-04 受控验收记录记载过页面解析和真实推荐成功，不能代替当前产品开关、样本可比性和可用性验收。

## 2. 当前数据怎样流动

### AI Workflow 到 Agent

1. 每日入口处理当前启用来源：LoyaltyLobby 普通文章、StatusMatch/GetStatus 邮件发现的项目页面。
2. 采集保存文档版本，AI 提取事实并生成简报，程序校验并维护事实版本、冲突和生命周期。
3. 官方映射与普通文章中有证据的映射组成来源中立的统一会籍图。
4. Agent 首先读取 StatusHolding 和目录，把用户输入交给同一 AIProvider 做结构化理解。
5. 新持有会籍需要用户确认，再由持有会籍服务校验保存。
6. CandidateRouteService 从已持有会籍出发遍历统一图，按目标、费用和挑战条件形成 matching/nearby/unknown 三组候选。
7. Controller 把候选序列化给模型，模型返回首选和备选的 route_id，程序检查这些 ID 是否属于正式候选，最后返回结构化 API 响应。

二者并不互相聊天，也不是 Agent 每问一句就重新采集。它们通过同一个数据库和服务层协作。Agent 当前不会自动刷新过旧事实；正常推荐不读取每日采集健康度，也没有显示“数据截至何时”。

### Agent 写回范围

写入确认后的 StatusHolding、24 小时短期 AgentInteraction 和明确确认的等待目标。它不应改官方映射、费用和生命周期。StatusMatcher 经验不进入官方事实或统一图。

### 等待目标

每日流程更新事实后调用同一个确定性候选服务。无候选不调用模型；候选签名与上次相同不再通知；首次或不同签名恢复 Agent，保存应用内结果。当前实现仍保持 ACTIVE，并按整组候选签名去重，新增候选可能再次触发，与“找到方案后默认不继续寻找更好路线”的产品边界应再统一。状态接口消费待展示结果，尚无明确展示确认机制。

## 3. 问题清单

### P0：追问合约与错误恢复

- `agent/contracts.py` 的 InterpretationDecision 强制完整 StrategyInterpretation，其 target 又要求项目或联盟。即使动作是 ASK_CLARIFICATION，也必须先知道要追问的答案。
- `controller.py::_generate` 把 HTTP、超时、JSON 和字段校验等异常统一包装为“结构化结果”错误；没有结构化修复重试。
- 首次理解失败发生在交互记录创建之前，API 返回 502，没有可恢复状态和足够的运行诊断。
- 目录只给模型前 300 个节点，实际有 376 个；规范化阶段依赖精确规范名称，中文别名识别过度依赖模型。
- 成功推荐后 allowed_commands 为空，再输入“第二条更便宜吗”等跟进会启动新交互，无法利用上轮路线结果。

### P0/P1：候选事实的正确性与信息损失

- `_route_amount` 汇总整个机会的同币种最低价，没有绑定实际步骤的来源等级、目标等级、地区及申请方式。免费判定也可能借用机会中另一档位的零价格。
- `_challenge_state` 合并全路线文本，可能用一步的“无需挑战”掩盖其他步骤未知。
- CandidateRouteStep 将结构化申请路线价格压成 costs 文本，未显式保留完整 eligibility、地区提醒、会籍有效期、价格适用范围和精细证据引用。底座有字段，Agent 工具投影却没完整传递。
- HIGH 目标未按结构化等级排序或筛选，只给模型“按名称判断”的限制说明；不能宣称已经确认对应联盟高卡。
- 默认最多 6 步、100 条候选，无查询截断说明；与总方针完整可达关系的表达存在差距。达到资源上限不能被解释为完整搜索无结果。
- 无来源会籍映射的公开挑战没有进入当前按图路径构造的候选，也无法由无持有会籍用户查询到。
- 近似候选只考虑费用和挑战，产品举例中的相邻较低等级调整尚未实现。

### P1：结果界面和运行透明度

- 后端已有 primary_route/alternative_routes，并非只有文本；当前原生页面有简单卡片，但路径只是箭头字符串，长回答被整体放入 h2，没有策略子图。
- 没有每条路线的结构化“为什么推荐/相较首选牺牲什么”，推荐理由主要依赖一段自由文本。
- 降级时 API 返回候选，页面却只显示候选数量，用户仍无法继续查看可用路线。
- 没有统一显示查询条件、实际使用的持有会籍、数据更新时间、筛选理由、截断状态、经验调查是否执行。
- available 仅判断 Provider 对象存在，不能证明模型此刻可用。

## 4. StatusMatcher 现在究竟怎样联网

这里要区分 StatusMatch 官方活动链路和 StatusMatcher 社区申请报告，两者不是同一个数据源。

当前没有通用搜索引擎、浏览器搜索或全网检索。StatusMatcherExperienceClient 用固定项目别名表定位目标公司页，通过 httpx 读取 `https://statusmatcher.com/company/<slug>`，每步最多两页，用 HTML 选择器和字符串规则抽取报告。

触发条件是：服务端 enabled、用户意图 research_statusmatcher、程序已有正式候选。满足时模型先选最多三条，工具调查后再把观察交回模型进行最终推荐。模型不能指定任意 URL。当前 enabled=false，所以正常启动不会执行这条调查链。

现有问题：

- 关闭时通常直接跳到推荐，experience 为空，没有强制生成“未调查”的用户提示。
- 来源可比性只比来源项目名称，没有实际提取或筛选双方等级。
- 报告没有日期字段，无法执行产品要求的近 12 个月、扩展 24 个月窗口。
- 多步报告池化计数；只要页面读取完整且整体样本够多，就可能给出较强信号，没有按最弱一步限制。
- OTHER 被纳入总数，可能影响观察比例和信号，不符合“无法判断不进入观察比例”。
- 没有报告级稳定链接/日期去重键，按摘要等字段去重既可能误合并，也不足以稳定追溯。
- 两页窗口无匹配不代表站内没有案例；公司别名表未覆盖也不代表没有经验。
- 12 秒是客户端 HTTP 超时，不是整个回合统一截止时间。多路线、多步骤串行请求可能累积；重复公司页没有回合内共享抓取。
- 自动跟随重定向后才验证最终域名，应在每一跳发出请求前校验。
- observation 含最多 600 字的报告说明并进入 last_response，应按授权范围改为最小聚合结果，避免短期记录被误当作不保存正文。

当前产品文档要求正式自动使用前具备明确内容使用授权。用户表达“请联网”是调查意图，与内容使用授权是不同条件。现阶段应保持真实未启用状态，不伪造案例或联网完成提示。

## 5. 建议方案：保留底座，重做 Agent 的交互与候选接口

### 阶段一：修复可用性和会话连续性

- 将草稿理解与可执行查询拆开。追问可携带不完整 target；QUERY 才要求目录已解析、字段完整。
- 通过动作区分合约，表达 ASK/CONFIRM/QUERY 各自所需字段，避免所有动作共享一套必填参数。
- 区分 provider_http_error、timeout、invalid_json、schema_error、invalid_action；记录脱敏字段路径、调用阶段、耗时和 run_id。
- 对 JSON/Schema 错误最多修复一次，仍计入三次模型调用上限；额度不足时交付已查到的事实候选和重试入口。
- 用目录检索和中文别名消歧替代固定前 300 条。一个回合只问最关键问题，允许后续回合逐步补齐。
- 保留 TTL 内的最小已选路线、目标与条件，支持“比较第二条”“改成免费”等继续对话，不长期保存聊天全文。
- 模型故障时保留输入、可重试状态及事实候选卡；不能只显示数量。

### 阶段二：让数据传递准确且可解释

- 为每个实际申请步骤保留申请方式和适用范围，价格按来源/目标等级及已有条件绑定，无法判定时显式 UNKNOWN，禁止跨档位取最低价。
- 挑战、费用按步骤计算后合并；多步未知不能被其他步骤抵消。
- 每条路线补充事实版本、更新时间、证据引用、申请入口、资格、地区提示、会籍有效期和不确定项。地区按现有产品边界提示，不悄悄新增地区过滤引擎。
- 返回四种结果信息：正式候选、单条件近似、关键事实未知、被排除及原因；另返回覆盖范围和截断标志。
- 正式候选先做确定性去重和明显劣势路线消减，再给模型小型比较表；详情按候选 ID 展开，不把所有长文本反复塞入 Prompt。
- 模型负责在事实允许的路线中解释主观取舍；输出每条路线的理由、相对差异和引用，服务端检验引用和关键数值。
- “高卡”先确认具体等级；若要支持联盟高等级优化，另补有证据的等级对应小目录并更新基线，不能靠名称猜。
- 公开挑战如保留在 Agent 范围，应接入现有机会读模型并支持无图路径结果，不人为造边。

### 阶段三：以精选策略图为核心呈现

默认输出三层：一句结论、首选加最多两个备选的策略子图、路线比较和下一步。

图从实际使用的已有会籍出发，只保留选中路线的必要中间节点和申请步骤。共同起点可以合并，同一目标的不同推荐路线需要保留，不照搬既有匹配图“只保留一条最短到达边”的渲染规则。

首选高亮、备选弱化；连线标实际申请动作、适用费用和挑战状态；点选连线展开该步事实与证据。近似路线必须单独标“调整后才可能”，不能画成当前可行。

比较表按路线展示费用及未知范围、步骤、挑战、时间限制、经验信号、推荐理由和相对代价。图负责说明怎么走，表负责说明为什么选。

无解时显示唯一建议调整的前后差异和新增候选；用户可确认、改条件或拒绝。完全无近似路线时应设计明确的等待入口，避免现有流程直接结束的死角。

折叠区“本次依据”显示：使用哪些持有会籍、确认条件、事实更新时间、各类候选数量和原因、是否截断、StatusMatcher 未启用/未请求/成功/失败/不足及实际调查范围。展示可验证操作摘要，不展示模型思维过程。

先沿用现有 FastAPI/Pydantic/原生 JS 页面，复用通用图样式和布局能力；无需为此引入通用 Agent 框架或第二套事实库。若后续选择 React，需单独明确迁移范围，当前未跟踪 frontend 不视为已完成的新前端。

### 阶段四：经验调查真实生效且可审计

- 区分工具启用、调查意图和本次执行结果，并总是返回明确状态。
- 在授权可用时，按实际申请步骤匹配双方项目、等级与报告日期，分别统计 Match/Challenge/Deny；缺字段即降为部分可比或不足。
- 单独返回每一步信号，整条路线取最弱一步；OTHER 不进有效比例分母。
- 加回合总时间、请求总量和响应大小上限，同一公司页回合内复用；逐跳校验域名。
- 只保留授权允许的最小统计、报告引用、窗口和限制；不把社区经验写回官方事实。
- 先用许可范围内受控样本验收，再做真实网络端到端验证。未授权或调查失败仍交付官方路线推荐。

## 6. 完成标准

1. “你好”“我有什么能匹配的”“我有汉莎金卡”均能合理追问或展示范围，不报目标必填错误。
2. 已知会籍加明确目标直接查询；新会籍确认后保存；修改条件和指代备选能接续上轮。
3. 免费、金额上限和无挑战筛选覆盖多等级、多地区、多币种、多步骤未知；不得借用不适用档位。
4. 推荐展示精选策略图和有依据的差异；每条图边能打开对应机会事实。
5. 查询范围、更新时间、筛选原因和经验调查状态可查看；截断不能被呈现为无方案。
6. StatusMatcher 关闭、失败、无样本、部分可比、多步最弱信号均有清晰展示和测试。
7. 模型异常可定位和恢复，全部调用计入预算；已有事实结果不因文案失败丢失。
8. 等待目标触发、去重、命中后停止和展示确认行为与产品方针一致。
9. 使用固定真实中文用例和真实数据库做演示验收，不能只用 SequenceAIProvider 通过情况宣称可用。

建议按“一、二、三”作为可演示版本的核心范围，四在授权条件具备时完成真实接入验收。正式开工时同步更新产品方针、技术基线和验收用例，尤其是多回合确认、查询资源上限、公开挑战和等待生命周期。
