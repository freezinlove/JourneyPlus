## 1. Agent 定位

JourneyPlus 增加一个面向用户的会籍策略 Agent。它根据用户自然语言描述的已有会籍、目标和取舍，调用现有会籍数据库和确定性程序获得候选路线，在获得明确使用授权时针对候选路线调查 StatusMatcher 实际申请经验，给出个性化建议；没有合适方案时，主动提出一个最小条件调整，或者在用户明确同意后持续等待符合条件的新机会。

Agent 只解决一个核心问题：

> 结合用户已经持有的会籍、想获得的会籍以及可以接受的费用和挑战条件，现在最值得采取什么会籍匹配行动？

“现在没有值得采取的行动，建议按原条件等待”是合法且完整的结论。Agent 不得为了生成答案而强行推荐或持续降低用户要求。

JourneyPlus 不建设多 Agent 系统。自然语言理解、追问、候选经验调查、条件调整和等待目标恢复均由同一个 Agent 完成；采集、事实提取、图遍历、生命周期和每日调度仍是 AI Workflow 或确定性程序，不包装为其他 Agent。

## 2. 当前知识边界

Agent 只能在 JourneyPlus 当前结构化事实范围内推荐：

- 用户持有的会籍项目、等级和有效期；
- 目标会籍项目、等级或联盟；
- 当前有效的会籍映射和完整可达路径；
- 申请资格、挑战要求、路线价格、地区提示、截止时间、会籍有效期、注意事项、证据和入口；
- StatusMatcher 中与具体候选路线可比的实际申请报告。

当前产品没有完整、统一、可比较的会籍权益目录。第三方文章中的休息室、行李、值机等自由文本关注点不能替代权益数据库。因此 Agent 不根据休息室、行李、早餐、升房或其他具体权益做目标优化，也不承诺判断某个会籍是否最适合某种旅行体验。

## 3. 完整工作方式

```text
用户用自然语言说明已有会籍、想获得什么和可以接受的取舍
                              ↓
Agent 形成结构化理解，并判断是否存在会改变结果的关键歧义
                 ┌────────────┴────────────┐
               有歧义                    无歧义
                 ↓                         ↓
       主动提出一个确认问题          直接继续处理
                 └────────────┬────────────┘
                              ↓
       将确认后的已有会籍交给确定性程序校验并持久化
       将本次目标和取舍交给确定性程序查询候选路线
                              ↓
                 ┌────────────┴────────────┐
              有候选路线                无候选路线
                 ↓                         ↓
       选择少量最终候选路线       从程序返回的近似候选中
       授权可用时调查经验         提出一个最小条件调整
                 ↓                         ↓
       结合用户取舍和经验信号      用户确认、修改或拒绝
       给出首选、备选和风险                ↓
                                    确认后重新查询；
                              拒绝或仍无方案时可选择等待
```

这个过程不是固定问卷或固定调用链。Agent 必须根据用户表达和每一步结果，自主决定下一步是确认、查询、调查经验、提出调整、保存等待目标还是结束。

## 4. Agent 允许的动作

Agent 的行动空间严格限制为六种：

1. **确认理解**：向用户说明自己理解的已有会籍、目标和取舍。
2. **追问一个问题**：只有关键歧义会改变持久化或查询结果时才追问。
3. **查询路线**：把确认后的已有会籍交给程序校验和持久化，把目标和取舍交给程序查询。
4. **调查经验**：对可能进入最终推荐的少量候选路线调查 StatusMatcher。
5. **提出调整**：没有合适路线时，从程序给出的近似候选中选择一个最小条件调整。
6. **保存等待目标或结束**：仅在用户明确选择等待时保存目标，否则结束本次目标。

Agent 可以自主选择下一步动作，但不能自行增加新的动作类型、绕过确定性程序，或者扩大到申请执行和泛旅行服务。

## 5. 自然语言目标理解与推荐

用户只需用自然语言表达，不需要先理解 JourneyPlus 的目录、图谱或筛选条件。Agent 在同一项能力中完成：

- 理解用户明确声称持有的会籍；
- 理解目标会籍项目、等级或联盟；
- 理解免费、低成本和是否接受挑战等取舍；
- 发现会改变规范化、持久化或路线查询结果的关键歧义；
- 必要时主动提出一个确认问题；
- 将确认后的已有会籍交给现有规范化目录和持有会籍服务；
- 将目标与取舍交给确定性推荐程序；
- 根据程序返回的候选组织首选、备选和风险说明。

Agent 不得把无法唯一识别的会籍直接写入正式持有会籍，也不得自己判断路径、资格、价格、期限或活动状态。自然语言只负责形成候选理解，正式持久化和查询必须经过现有规范化目录与确定性服务。

推荐默认只展示：

- 一个首选；
- 最多两个具有明显不同取舍的备选；
- 每条路线最重要的限制和风险；
- 用户下一步应申请、确认条件还是等待。

完整会籍图和机会详情继续作为证据与展开入口，不把所有可达节点直接交给 Agent 自由排序。

## 6. 确定性推荐与 Agent 取舍

程序负责生成候选、检查硬条件并给出稳定的比较依据。Agent 负责理解用户的主观取舍和选择需要向用户呈现的路线。

推荐顺序遵循：

1. 路线必须达到用户明确的目标项目、等级或联盟；
2. 路线必须满足用户明确不愿放宽的费用和挑战条件；
3. 在可行路线中，按照用户表达的免费、低成本或少挑战偏好排序；
4. StatusMatcher 经验信号用于比较原本都可行的少量候选；
5. 条件接近时，优先更直接、更简单且不确定性更少的路线。

Agent 不生成不可解释的万能分数。每次推荐必须能用用户明确表达的取舍和可验证事实解释“为什么是这条路线”。

## 7. StatusMatcher 实际申请经验调查

### 7.1 唯一用途

联网调查只用于回答：

> 对于程序已经判定可行的具体候选路线，StatusMatcher 上的可比申请报告显示了怎样的经验成功信号，申请人可能遇到什么情况？

StatusMatcher 不用于发现新活动，不用于判断活动是否过期、价格、地区、资格、事实冲突或路径可达，也不用于更新统一会籍图。上述事实继续以 JourneyPlus 现有 AI Workflow 和确定性程序为准。这项按需调查不恢复已移除的 `statusmatcher_reports` 批量来源，不进入来源注册表或每日来源采集。

### 7.2 触发条件

只有以下情况触发调查：

- 程序已经返回至少一条符合用户当前条件的候选路线；并且
- 该路线可能成为首选或具有明显不同优势的备选；或者
- 用户明确询问这条候选路线的实际成功情况。

没有候选路线时不搜索 StatusMatcher。Agent 不得利用 StatusMatcher 绕过现有采集范围去发现数据库外的新路线。

### 7.3 调查范围

调查必须尽量对应相同的来源项目、来源等级、目标项目和目标等级。优先使用最近十二个月报告；可比报告不足时可以扩展到二十四个月，更早报告只能作为历史背景。

每条报告区分：

- `Match`：直接匹配成功；
- `Challenge`：获得挑战，不等于直接匹配成功；
- `Deny`：被拒绝；
- 无法判断：不进入观察比例。

多步路线分别调查每一个实际申请步骤。整条路线的经验信号不得高于其中证据最弱的一步。

### 7.4 输出规则

Agent 可以展示可比报告数量，以及其中直接成功、转为挑战和拒绝的观察数量。该比例只能称为“可比报告中的观察比例”，不得称为真实审批成功率。

经验结论只使用：

```text
较强
一般
较弱
证据不足
```

Agent 可以概括报告中提到的证明材料、已有预订、会籍取得方式、等待时间和拒绝原因。只有多份可比报告反复出现的情况才能称为“常见”；单份报告必须明确标为单个案例。

社区经验可以调整多个可行候选之间的推荐顺序，但不能覆盖 JourneyPlus 对官方事实和路径可行性的判断，也不能被表述为通过保证。

### 7.5 访问和使用前提

截至 2026-09-03，StatusMatcher 条款声明站内内容未经书面许可不得复用，并且不保证用户报告准确或及时：<https://statusmatcher.com/terms>。

因此，把 StatusMatcher 作为正式产品的自动调查来源前，必须获得书面许可、授权接口或其他明确使用授权。未经授权不得批量采集、保存、镜像或重新发布报告正文，也不得通过搜索结果摘要规避其使用条件。授权不可用时，Agent 必须跳过经验调查并明确显示“实际申请经验暂不可用”，不能阻止基于 JourneyPlus 官方事实完成路线推荐。

## 8. 无方案时的最小调整

程序没有返回符合全部条件的路线时，应同时提供只偏离一个用户条件的近似候选。Agent 只能从这些近似候选中提出一个代价最小、且最符合用户原始取舍的调整，例如：

- 从完全免费调整为接受一个明确的最高申请费；
- 从不接受挑战调整为接受一次明确挑战；
- 从指定目标等级调整为相邻较低等级。

Agent 必须同时说明：当前为什么没有方案、建议改变哪个条件、改变后会新增什么候选。用户只需确认、修改或拒绝。

Agent 每次只提出一个调整。用户确认后，程序使用新条件重新查询；如果仍无方案，Agent 不得继续层层降低要求，而应让用户自行修改目标或选择等待。

## 9. 等待目标管理

等待目标只在以下条件全部满足时建立：

1. 当前没有符合用户已确认条件的路线；
2. Agent 已经提出一次最小调整；
3. 用户拒绝调整，或者调整后仍然没有方案；
4. 用户明确确认按当前条件继续等待。

普通查询、临时假设和 Agent 未经确认的理解不得自动创建等待目标。

等待期间，现有每日 AI Workflow 和确定性程序继续更新机会并检查目标。没有新候选时不调用 Agent、不通知用户；第一次出现符合条件的新候选时才恢复 Agent，在授权可用时调查相应 StatusMatcher 经验，并生成一次说明“发生了什么、为什么符合原目标、经验信号如何、现在建议做什么”的通知。授权不可用时通知仍可基于 JourneyPlus 事实生成，但必须说明实际申请经验暂不可用。

同一候选不得重复通知。用户接受路线、取消目标或明确不再等待时，目标结束。找到方案后默认不继续寻找更好的路线，除非用户明确要求保留等待目标。

## 10. 数据与记忆边界

Agent 长期保存的用户信息只包括：

- 用户明确确认的已有会籍，复用 `StatusHolding`；
- 用户明确选择持续等待的一个当前目标。

本次查询目标、临时假设、未确认的会籍理解、被拒绝的条件调整、普通聊天内容和 StatusMatcher 报告正文默认不长期保存。不建设庞大用户画像，不保存完整会话历史，不把外部经验写回官方事实或统一会籍图。

## 11. 权限边界

Agent 可以自主完成：

- 判断是否需要一个确认问题；
- 查询持有会籍和候选路线；
- 选择需要调查经验的少量候选；
- 在已授权前提下调查 StatusMatcher；
- 根据用户取舍和经验信号组织推荐；
- 从程序近似候选中提出一个最小调整；
- 在用户明确同意后保存等待目标；
- 在新候选首次满足等待目标时恢复并生成通知。

Agent 不得：

- 发明或修改官方会籍映射、资格、价格、期限和活动状态；
- 把社区经验当作官方规则或通过保证；
- 自动提交申请、支付费用或联系会籍项目；
- 发送或长期保存用户证明材料；
- 处理客服邮件、退款、申诉或完整申请进度；
- 根据数据库不具备的完整权益信息推荐；
- 发现并写入数据库外的新活动；
- 创建其他 Agent 或多 Agent 编排。

## 12. 复杂度预算

每个用户请求遵循以下预算：

- 最多只追问当前最关键的一个问题；
- 只把一个首选和最多两个备选送入经验调查；
- 无方案时只主动提出一个最小调整；
- StatusMatcher 没有可比报告、访问失败或证据不足时立即降级为“经验不足/暂不可用”，不扩大为全网调查；
- 只有一个当前等待目标；
- 没有匹配到新候选时，日常监控不得调用 Agent；
- 用户未明确同意时不产生长期记忆或持续关注。

Agent 的自主性保留在“下一步选择”上，复杂度限制在“它能选择的动作和每次处理的候选数量”上。

## 13. 明确不做

```text
多 Agent
会籍权益目录和权益优化
泛旅行规划
数据库外新活动发现
StatusMatcher 批量采集或镜像
庞大用户画像
完整会话长期保存
异常处理中心
客服邮件分析
申请材料指导
退款与申诉处理
申请进度管理
自动申请、付费或对外联系
同时管理多个等待目标
```

## 14. 完成标准

Agent 能力完成后必须满足：

1. 用户可以用自然语言同时表达已有会籍、目标和取舍；
2. 表达明确时 Agent 不追问，存在关键歧义时只确认最重要的一项；
3. 只有用户确认且通过规范化目录校验的已有会籍可以持久化；
4. 路径、资格、价格、期限和活动状态仍由确定性程序提供；
5. Agent 默认只展示一个首选和最多两个备选，并能解释与用户取舍的关系；
6. 只有程序已经返回的最终候选才能触发 StatusMatcher 调查；
7. StatusMatcher 结果区分直接成功、挑战和拒绝，并明确为自报样本而非真实审批概率；
8. 没有可比报告或没有访问授权时，Agent 明确显示经验不足或暂不可用，不编造结论；
9. 没有符合条件的路线时，Agent 主动提出一个由近似候选支持的最小调整；
10. 用户拒绝调整后，Agent 不继续擅自降低要求；
11. 只有用户明确选择等待时才保存目标；
12. 等待期间没有新候选时不调用 Agent、不发送通知；
13. 新候选第一次满足目标时只通知一次；
14. 用户接受路线、取消目标或不再等待时，目标停止；
15. Agent 不进入权益优化、异常处理、申请执行或多 Agent 范围。

## 15. 真 Agent 判定

这项能力只有在以下行为真实存在时才称为 Agent：

- 同样一句自然语言，在不同已有会籍和取舍下会选择不同下一步；
- 信息充分时直接查询，信息不足时主动确认；
- 有候选时选择少量路线调查经验，无候选时不进行无关搜索；
- 调查结果可以改变可行候选的推荐顺序，但不会改变官方事实；
- 无方案时主动提出程序有依据的最小调整；
- 用户确认、修改或拒绝后，Agent 根据新状态重新选择动作；
- 未满足目标只有在用户明确选择后才进入等待，并在新候选出现时恢复处理。

如果实现只是“自然语言输入 → 固定查询 → 生成一段回答”，则仍是聊天式 AI Workflow，不符合本文定义的 JourneyPlus Agent。
