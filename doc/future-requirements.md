# JourneyPlus 后续需求备忘

本文保留早期确认的后续需求及其实施状态；活动时效要求已经进入正式 OpenSpec 并完成核心实现。

## 活动时效、过期状态与归档

- 记录日期：2026-08-21
- 状态：已由 `finish-status-opportunity-automation` 阶段四、五设计并实现，当前 LoyaltyLobby 与 StatusMatch/GetStatus Gmail 真实联调已完成，等待外部每日调度、至少三个北京时间自然日的连续观察和最终维护交接

### 用户意图

常旅客活动均具有时效性。系统后续不仅要识别和归并抓取到的活动，还要提取并使用活动截止时间进行筛选；当时间已过，应在数据库中明确记录活动已经过期，并进入可追溯的归档状态。

### 已确认边界

- 第一阶段人工金标只回答“正文是否描述会籍获取机会”，不考虑活动当前是否仍然有效。
- 已截止活动仍可在第一阶段金标中标为 `STATUS_OPPORTUNITY`。
- 时间判断应发生在活动识别和归并之后，不能反向改变文档主题标签。

### 后续最小能力

1. 从活动证据中提取申请开始时间和截止时间并保留原始文字与来源；查询时间统一规范化为北京时间，不增加独立时区或精度字段。
2. 为活动单独记录时间生命周期；它必须与现有的人工审核状态分离。
3. 查询和展示时支持按当前有效性过滤，并明确区分有效、已过期和时间未知的活动。
4. 截止时间到达后更新数据库状态并进行软归档，保留事件、正文、证据、事实版本和历史修订，不物理删除。
5. 来源在原截止时间前明确宣布延期时，可判断为原活动更新；活动过期或归档后出现的延期、重新开放或新一期材料一律创建新的现实活动。

### 已采用的实施决定

- 未公布或无法可靠规范化截止时间的活动使用 `UNKNOWN`。
- 所有时间统一按北京时间 `Asia/Shanghai`；仅日期的开始值取当日开始，截止值取当日结束。
- `EXPIRED` 与软归档同时发生；归档事件退出自动候选池且不得自动恢复，确需纠正错误归档时只能通过显式人工复核。
- 来源更新时立即重算当前事件生命周期；纯时间推进由后续每小时单轮自动化调用。

> `StatusEvent.status` 继续用于 `DRAFT`、`NEEDS_REVIEW`、`CONFIRMED`、`MERGED` 等审核流程；当前实现使用独立的 `lifecycle_status` 表示活动时效。
