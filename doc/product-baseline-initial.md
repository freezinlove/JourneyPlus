## 1. 产品概述

### 1.1 一句话定义

在用户给定旅行目标、预算和现有常旅客资产的前提下，自动寻找单位成本旅行体验最大化的方案，并持续监控未来可能使方案变得更好的机会。

### 1.2 产品解决的问题

传统 OTA 通常从一个即时交易问题出发：

> 我要从 A 到 B，请帮我搜索当前最便宜的机票或酒店。

本产品解决的是一个跨时间、跨权益、跨产品的长期规划问题：

> 我计划今年暑假去德国和奥地利，预算为某一金额，持有若干信用卡、积分、会籍和权益。请结合未来数月可能出现的匹配、促销、积分票、酒店权益和特殊价格，为我规划总体体验最好的旅行方案，并在情况变化时持续更新。

产品不只比较一次价格，而是同时考虑：

- 现金支出；
- 积分和里程的使用价值；
- 航班仓位与中转体验；
- 酒店等级、早餐、酒廊、延迟退房和升房概率；
- 信用卡、会籍、贵宾厅和交通权益；
- 当前机会对未来会籍与积分资产的战略价值；
- 方案的风险、执行难度和时间成本；
- 后续出现更优方案的可能性。

### 1.3 产品定位

本产品定位为：

> 面向常旅客的长期旅行体验优化与机会监控系统。

它不是 OTA，不代替用户完成交易，不以单次最低价搜索为主要竞争点。它提供信息、证据、分析、规划、行动建议、监控和相关链接。

## 2. 核心价值

产品希望为用户带来以下可衡量价值：

1. 更低的实际现金成本；
2. 更高的积分和里程兑换价值；
3. 更优的航班仓位和行程体验；
4. 更好的酒店待遇与升房机会；
5. 更多早餐、行政酒廊和延迟退房权益；
6. 更多机场、高铁和城市贵宾厅权益；
7. 更多合法、公开、可验证的促销与特殊低价机会；
8. 更早完成会籍、匹配、挑战和积分积累等长期铺垫；
9. 在机会失效、价格变化或用户资产变化时及时调整计划；
10. 降低用户自己搜集规则、判断资格和组合权益的认知成本。

产品追求的不是绝对最高规格，而是：

> 在预算、时间、风险偏好和执行意愿约束下，对用户而言最值得的体验组合。

## 3. 目标用户

### 3.1 核心用户

- 已经持有航空、酒店、信用卡或贵宾厅权益的常旅客；
- 对积分、里程、会籍和促销有一定兴趣，但缺少系统规划能力的用户；
- 每年有一到数次中长途或高价值旅行，希望提前数月布局的用户；
- 愿意在合理范围内调整出行日期、航线、酒店品牌或积分使用方式的用户；
- 更看重总体体验和单位成本价值，而非只看最低票面价格的用户。

### 3.2 非目标用户

- 只需要立即搜索最低价机票的用户；
- 要求产品代为付款、出票、订房、取消或索赔的用户；
- 希望绕过平台规则、伪造资格或使用非公开非法手段的用户；
- 不愿提供任何偏好和资产信息，却要求系统保证绝对最优结果的用户。

## 4. 产品原则

### 4.1 体验优化不等于消费升级

系统不能通过简单推荐更贵的产品来制造“体验更好”。任何体验提升都需要说明新增成本、可获得的权益、机会成本和风险。

### 4.2 证据优先于结论

涉及价格、资格、有效期、权益范围和活动规则的关键结论必须附带来源、观察时间和有效性状态。

### 4.3 计划是版本化的，不是假装永远正确

每次外部机会、价格、规则或用户状态发生变化后，系统应生成新的计划版本，并展示相对上一个版本发生了什么变化、为什么变化。

### 4.4 长期状态不依赖聊天记录

用户的旅行目标、权益资产、积分余额、机会、证据和行动状态应作为结构化数据管理。聊天只是一种交互方式，不是事实数据库。

### 4.5 自动规划不等于自动执行

系统可以自动收集、分析、比较、规划和提醒，但不自动执行任何预订、付款、取消、转点或申请操作。

### 4.6 风险与收益同时表达

特殊低价、积分票、会籍匹配和复杂权益组合都可能存在不确定性。系统必须同时展示收益、限制、失效可能性和备用方案。

## 5. 三个核心产品板块

三个板块是同一产品闭环的不同入口，不是三套相互独立的功能：

```text
个人旅行资产提供用户状态
机会情报提供外部信号
动态旅行规划完成决策与组合
规划结果再生成资产占用、行动和监控规则
```

### 5.1 个人旅行资产

个人旅行资产是系统的用户状态基础，不只是普通个人资料。它维护用户当前拥有什么、可以使用什么、什么即将过期，以及哪些资产已被旅行计划占用。

统一管理：

- 航空会员、酒店会员及会籍；
- 积分与里程余额及最后确认时间；
- 信用卡及其旅行权益；
- 贵宾厅资格；
- 升房券、房晚券、旅行报销额度；
- 权益有效期与剩余次数；
- 会籍匹配和挑战进度；
- 已报名或正在执行的活动；
- 已被具体旅行方案预留的积分和权益；
- 用户对积分、酒廊、早餐、升房等权益的个人估值；
- 用户确认、外部验证、模型推断和过期数据之间的来源差异。

资产需要区分：

```text
总余额
当前可用余额
已被计划预留的余额
即将过期的余额
尚待用户确认的余额
```

首版以用户手工录入和定期确认为主，可提供 CSV、截图或结构化表单辅助导入，但不连接私人会员账户，也不保存账户密码。

### 5.2 动态旅行规划

动态旅行规划是整个产品的核心决策引擎。用户输入未来旅行目标，系统结合个人旅行资产、外部机会情报和约束条件生成初始方案，并在出发前持续维护。

输入包括：

- 目的地或区域；
- 出发城市与可接受的替代机场；
- 日期范围和灵活度；
- 总预算及各部分预算；
- 同行人数与旅客类型；
- 舱位、酒店、餐饮、行李和中转偏好；
- 风险偏好和执行复杂度容忍度；
- 当前个人旅行资产；
- 已验证且与本次旅行相关的机会情报。

输出包括：

- 当前推荐方案；
- 保守、平衡和进取三个策略等级；
- 航班、酒店、地面交通和权益组合；
- 现金、积分、附加费用和机会成本；
- 使用及预留了哪些个人资产；
- 关键行动与截止日期；
- 需要继续等待或监控的机会；
- 关键证据、链接和有效期；
- 风险、失败条件和备选方案；
- 计划版本及变化说明。

动态规划不仅计算当前选择，还需要将长期机会组织成依赖路径。例如：

```text
注册匹配活动
→ 在规定时间内完成挑战
→ 获得高级会籍
→ 在目标旅行中获得早餐、酒廊和升房权益
→ 评估为此增加的入住成本是否值得
```

### 5.3 常旅客机会情报

机会情报是一个可独立浏览的信息更新聚合板块，同时也是动态旅行规划的外部信号源。

覆盖范围包括：

- 航空和酒店会籍匹配；
- 会籍挑战与保级活动；
- 积分和里程购买促销；
- 积分转点奖励；
- 公开积分票和酒店积分房；
- 公开特殊低价及疑似错误价格；
- 信用卡旅行权益变化；
- 航空、酒店和贵宾厅规则变化。

机会情报提供两个视图：

#### 公共机会流

用户无需建立完整资产档案，也可以浏览结构化机会、适用条件、有效期、风险、证据和相关链接。

#### 个性化机会流

系统结合个人旅行资产与旅行目标，进一步标记：

- 用户是否可能符合资格；
- 机会与哪些资产相关；
- 机会影响哪次旅行；
- 可能降低多少成本或增加什么体验；
- 是否值得立即行动、继续观察或忽略；
- 是否足以触发计划更新。

每个机会至少包含：

- 机会类型；
- 适用用户与资格条件；
- 预计现金成本；
- 预计积分或体验价值；
- 注册和执行期限；
- 风险等级；
- 来源、抓取时间和有效性；
- 对具体旅行计划的影响；
- 推荐动作：关注、关联旅行、立即处理、继续观察、忽略或人工确认。

系统从经过人工筛选的公开第三方来源持续收集信息，由模型完成语义筛选、字段抽取、跨来源聚类、冲突识别和初步有效性判断，再以少量确定性校验支持用户匹配和重要性计算。来源优先级为：

1. 专门维护会籍匹配、会籍挑战和会籍互通信息的第三方数据库或聚合站；
2. 更新稳定、会标注日期和原始链接的常旅客行业媒体与专业博客；
3. 活跃社区、论坛和地区性博客，用于发现区域限定或刚出现的机会；
4. 第三方文章所链接的活动落地页，用于用户行动前的按需复核和跳转，不作为首版主动发现与持续跟踪对象；
5. 搜索引擎发现结果，仅用于补充遗漏来源或冲突调查。

机会不因缺少官方来源复核而一律阻塞发布。系统应展示第三方来源、观察时间、交叉印证情况和置信状态；对费用较高、资格复杂、来源冲突或用户即将执行的机会，再触发人工确认或按需查看活动落地页。“实时”通常指按来源更新节奏进行小时级或日级发现，不承诺秒级监控。

#### 建议建设优先级

机会情报的长期范围包含上述类别，建议按以下顺序建设：

1. P0：高卡匹配、会籍挑战、会籍互通和公开会籍套利；
2. P1：买分、转点和积分促销；
3. P1：积分票与积分房监控试点；
4. 后续：公开特殊低价、信用卡权益和更广泛规则变化。

P0 中的“公开”不仅指没有资格门槛，而是指活动及其规则能被公众找到和查看。企业员工、特定地区居民、指定来源会籍或合作伙伴会员才可参加的活动，只要页面和规则公开，仍属于“群体公开”，可以收集和提醒；最终是否符合资格另行判断。

首版明确排除：

- 只能登录个人账户后看到的个体定向活动；
- 客服口头、人工试探或非预期行为形成的未公开 Bug；
- 需要绕过访问控制、验证码或网站条款才能获得的内容。

第一阶段以人工筛选的固定第三方站点、栏目、RSS/Feed 和公开页面为输入，只聚焦会籍匹配、会籍挑战、会籍互通及其关键资格变化。首版不建设官方域名扫描、官方邮箱接入、地区矩阵穷举或未挂目录页面发现；第三方来源中出现的新机会先由 AI 识别，必要时再进行人工复核。

## 6. 跨板块公共能力

### 6.1 行动中心

行动中心不是第四个核心板块，而是贯穿三个板块的统一交互层。它回答“用户现在应该做什么，系统接下来继续观察什么”。

统一展示：

- 今天、本周和临近截止的行动；
- 即将过期的积分、会籍和权益；
- 需要用户确认的信息；
- 正在执行的会籍匹配和挑战；
- 新出现且影响现有计划的机会；
- 最新计划变化；
- 系统正在监控的价格、库存、规则和活动。

### 6.2 旅行规划本

规划本是产品的核心交付物，不应只是一段聊天回答。

建议结构：

1. 旅行目标与硬约束；
2. 当前最佳方案摘要；
3. 航班与仓位方案；
4. 酒店与权益方案；
5. 现金、积分和价值测算；
6. 会籍与权益策略路径；
7. 行动清单与时间线；
8. 正在监控的机会；
9. 风险、限制与备选方案；
10. 证据及相关链接；
11. 版本历史和变化原因。

### 6.3 动态提醒

提醒应以“是否改变用户决策”为标准，而不是发现任何信息就推送。

典型提醒：

- 原计划成本明显下降；
- 出现更优仓位或积分可用性；
- 新机会使某项酒店或会籍策略变得可行；
- 用户即将错过活动注册或权益使用期限；
- 原有证据过期或规则变化；
- 当前计划因资格、时间或预算变化失效；
- 需要用户补充信息才能继续判断。

### 6.4 跨板块关联展示

三个板块应展示同一批关联对象的不同视角：

- 资产页面显示该资产被哪些计划使用、关联哪些机会；
- 机会页面显示用户是否符合、影响哪次旅行、是否已进入计划；
- 计划页面显示每项决策依赖哪些资产、机会和证据；
- 行动页面显示行动来自哪项资产、机会或计划决策。

## 7. 三板块联动与产品闭环

系统必须满足以下闭环规则：

1. 每个有效机会最终必须进入无关、继续监控、需要行动或触发重规划中的一种状态；
2. 每个正式计划使用的积分和权益必须产生明确的资产占用；
3. 每个依赖未来变化的计划决策必须产生监控规则；
4. 每个需要用户完成的步骤必须进入行动中心；
5. 每次资产变化必须检查受影响的有效计划；
6. 每次机会失效必须检查依赖它的计划；
7. 每次重规划必须生成新版本，不能覆盖旧版本；
8. 未受影响的计划决策应尽量保留。

典型闭环：

```text
机会情报发现酒店会籍匹配
→ 根据个人旅行资产判断用户可能符合
→ 识别与德国旅行相关
→ 计算完成挑战的成本和旅行权益价值
→ 增量更新酒店与会籍策略
→ 发布新计划版本和 Diff
→ 生成用户确认、注册和挑战进度行动
→ 完成后将新会籍写回个人旅行资产
→ 再次影响当前和未来旅行规划
```

## 8. Web 与移动端产品分工

### 8.1 Web：完整规划工作台

Web 端适合承载：

- 旅行目标的完整创建与编辑；
- 大量常旅客资产管理；
- 多方案对比；
- 现金、积分和体验价值分析；
- 计划版本 Diff；
- 证据与来源审阅；
- 监控规则管理；
- Agent 执行过程与评测结果的管理界面。

### 8.2 App：随身旅行助手

移动端适合承载：

- 查看当前推荐计划；
- 查看今天、本周和临近截止的行动；
- 接收重要机会与计划变化通知；
- 快速确认或更新积分、会籍和权益状态；
- 在旅途中查看贵宾厅、酒店权益和关键证据；
- 对新方案执行接受、忽略、稍后处理或继续观察。

两端共用同一套账户、数据、Agent 后端和计划版本，不复制业务逻辑。

## 9. 核心用户流程

### 9.1 首次使用

```text
注册或登录
→ 创建常旅客资产档案
→ 填写偏好与风险容忍度
→ 创建旅行目标
→ 补充系统识别出的关键信息缺口
→ 生成初始旅行规划本
→ 用户确认偏好和监控范围
→ 系统进入长期监控状态
```

### 9.2 出发前长期运营

```text
定时收集新信息
→ 去重与验证
→ 匹配用户资产和旅行目标
→ 判断是否产生实质影响
→ 必要时增量重规划
→ 生成新计划版本
→ 仅在达到阈值时通知用户
```

### 9.3 用户状态变化

```text
用户更新积分、会籍或信用卡
→ 系统识别受影响的策略和计划
→ 重新校验资格与预算
→ 保留未受影响的决策
→ 更新计划与监控规则
```

## 10. 决策与解释框架

系统需要综合多个维度，而不是只输出一个“总分”。

### 10.1 硬约束

- 总预算；
- 日期和停留时长；
- 签证、转机和出入境限制；
- 用户明确不可接受的航线、时间或产品；
- 积分和权益余额；
- 活动资格及截止时间；
- 权益使用次数；
- 同一资产不可重复分配。

违反硬约束的方案不得进入正式推荐。

### 10.2 软目标

- 航班仓位体验；
- 酒店等级和位置；
- 早餐、酒廊、升房和延迟退房；
- 行程便利性和中转风险；
- 积分兑换价值；
- 现金成本；
- 未来权益和会籍价值；
- 执行复杂度；
- 机会失效风险。

### 10.3 输出要求

系统不应只告诉用户“方案 A 最好”，还应说明：

- 相比基准方案多花或少花多少钱；
- 增加了哪些体验；
- 使用了多少积分以及放弃了什么其他用途；
- 依赖哪些尚未确定的条件；
- 如果条件失败，应切换到什么方案。

## 11. 产品边界

### 11.1 产品可以做

- 收集公开信息；
- 提供旅行规划和相关建议；
- 提供证据、规则摘要和相关链接；
- 比较现金、积分和权益方案；
- 判断公开规则下的表面资格；
- 生成行动清单、提醒和备用方案；
- 持续监控并更新计划。

### 11.2 产品不做

- 不代购、代订或出票；
- 不自动付款；
- 不自动取消或修改订单；
- 不自动转点、买分或申请信用卡；
- 不自动申请或执行会籍匹配；
- 不保存用户常旅客账户密码；
- 不抓取需要登录的私人账户页面；
- 不绕过验证码、访问控制或平台限制；
- 不保证特殊低价一定被承运方或酒店履行；
- 不保证搜索到全网所有价格和机会；
- 不构成法律、签证、税务或金融专业意见。

所有外部交易和账户操作均由用户自行前往对应官方或第三方页面完成。

## 12. MVP 范围

为了保证个人独立完成，MVP 先验证一个小而完整的产品闭环，不预设任何底层能力已经存在。

### 12.1 MVP 核心闭环

- 单用户、手工录入旅行目标与常旅客资产；
- 1 条主要旅行走廊，例如中国大陆至德国、奥地利；
- 少量航空、酒店和权益体系；
- 从少量人工审核的第三方来源形成可追溯的会籍匹配与挑战机会数据；
- 单 Agent 生成结构化旅行规划本；
- 使用确定性代码校验预算、日期、资格与权益占用；
- 输出保守、平衡、进取三种方案；
- 保存计划版本、证据、行动和需要继续监控的条件；
- 所有预订、支付、申请、转点和账户操作仍由用户自行完成。

### 12.2 MVP 不覆盖

- 全球所有航司、酒店和信用卡；
- 全网秒级价格监控；
- 复杂的小时级景点和餐厅行程；
- 自动预订与订单管理；
- 自动登录用户会员账户；
- 大规模社交或内容社区；
- 无确定性校验的高风险机会推荐；
- 代买、代订、自动申请、自动转点或任何外部写操作。

## 13. 验收标准

### 13.1 产品功能验收

- 用户能够创建并修改旅行目标；
- 用户能够录入至少两类积分/会籍和两类权益资产；
- 系统能够生成结构化旅行规划本，而非纯聊天文本；
- 规划本包含成本、积分、权益、证据、风险、行动和备选方案；
- 系统能够保存并展示多个计划版本；
- 资产页面能够显示资产被哪些计划占用以及关联哪些机会；
- 机会页面能够显示与用户、资产和旅行的匹配关系；
- 新机会或用户状态变化能够触发增量重规划；
- 计划发布能够生成资产占用、行动和监控规则；
- 机会过期能够使依赖它的计划进入重新校验或备用方案；
- 未受影响的计划决策在重规划后被保留；
- Web 与 App 能读取同一计划和行动状态；
- 用户能够查看每个关键建议的来源链接和观察时间；
- 系统不会执行任何预订、支付和账户操作。

### 13.2 产品质量验收

- 硬约束违反拦截率达到 100%；
- 权益重复使用拦截率达到 100%；
- 关键资格判断准确率不低于 90%；
- 关键结论来源覆盖率达到 100%；
- 来源对结论的支持率不低于 95%；
- 机会抽取准确率不低于 90%；
- 机会抽取召回率不低于 80%；
- 重复机会率不高于 5%；
- 应触发重规划的事件触发率不低于 95%；
- 未受影响决策保留率不低于 95%；
- 同一事件重复处理不会生成重复副作用，幂等率达到 100%。

### 13.3 用户验收

以至少 5 名目标用户完成可用性测试：

- 至少 4 人能够独立完成核心流程；
- 平均实用性评分不低于 4/5；
- 用户能够解释推荐方案的主要成本、收益和风险；
- 用户能明确区分“已确认方案”“待监控机会”和“高风险假设”。

## 14. 产品风险

### 14.1 信息时效风险

价格、库存和规则可能在抓取后立即变化。所有事实必须记录观察时间、有效期和重新验证要求。

### 14.2 来源与采集合规风险

不同网站对自动访问的规定不同。应建立第三方来源白名单、访问频率限制和停用机制，优先使用其公开 RSS、Feed、栏目页和允许访问的公开页面。

### 14.3 错误资格判断风险

会籍匹配、信用卡权益和促销规则经常包含地区、账户历史和定向限制。系统应区分确定符合、可能符合、不符合和需要人工确认。

### 14.4 价值计算主观性

积分、升房和酒廊价值因用户而异。系统应允许用户调整价值假设，展示原始构成，而不是输出唯一且不可解释的估值。

### 14.5 过度通知风险

监控信息量可能远高于真正有价值的机会。通知必须经过用户匹配、影响分析和阈值控制。

### 14.6 项目范围失控风险

常旅客领域覆盖极广。首版应通过少量计划、少量体系、少量来源证明完整闭环，再扩展覆盖面。

## 15. 路线图

### 阶段 0：单 Agent 产品基线

- 个人旅行资产与旅行目标；
- 单一旅行走廊和少量常旅客体系；
- 手工输入航班、酒店，以及从精选第三方来源经 AI 筛选和人工抽查的会籍机会；
- 单 Agent 结构化规划本；
- 确定性预算、资格和权益占用校验；
- 旅行规划离线评测集；
- 用真实样例验证产品闭环，再决定信息采集自动化和多 Agent 拆分。

### 阶段 1：多阶段编排

- Research、Verification、Strategy、Planner、Critic 编排；
- Context Builder 与分阶段工具权限；
- 与单 Agent 基线的消融比较；
- 失败恢复、人工中断和计划版本化；
- 只有在评测证明有收益时保留拆分节点。

### 阶段 2：第三方来源监控与增量重规划

- 接入精选第三方站点、栏目、RSS/Feed 和允许访问的公开页面；
- 监测新条目、内容更新、机会过期和来源停更；
- 使用 AI 完成相关性筛选、结构化抽取、语义聚类和跨来源冲突识别；
- 对高价值或高风险机会保留人工抽查与行动前复核；
- 领域事件、增量重规划、计划 Diff 和通知；
- 根据实际漏报情况再扩充地区性媒体、社区和 App/小程序公开入口。

### 阶段 3：优化、Web 与移动端

- 约束求解与多目标方案；
- 模型路由和成本控制；
- Next.js Web；
- React Native App；
- 推送通知；
- 离线查看旅行关键信息；
- 小规模真实用户测试。

### 阶段 4：范围扩展

- 新增航空、酒店和权益体系；
- 增加来源适配器；
- 完善线上评测和异常检测；
- 根据真实数据决定是否产品化运营。

## 16. 项目最终应证明什么

这个项目的价值不在于页面上出现多个“Agent”名字，而在于能够证明：

- 系统能把长期目标分解成可执行、可监控的策略路径；
- 系统能在外部事实变化后进行可控的增量重规划；
- Agent 的结论有证据、有边界、有不确定性表达；
- LLM 推理与确定性计算得到合理分工；
- 编排结构相对单 Agent 基线有可量化改进；
- Context 选择减少无关信息，同时不显著损害质量；
- 每一次计划变化都可追踪、可复现、可评测。

只要这些能力真实存在，本项目既能成为有实际价值的旅行产品，也能充分体现 Agent 编排、Agent 评测以及 Prompt/Context 工程能力。
