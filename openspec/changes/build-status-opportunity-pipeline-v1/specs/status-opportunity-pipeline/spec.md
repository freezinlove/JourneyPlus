## ADDED Requirements

### Requirement: 第一版仅处理会籍获取机会
系统 MUST 只把直接获得、升级或延长旅行忠诚度会籍的公开或群体公开路径作为第一版机会，包括会籍匹配、会籍挑战、快速通道、会籍互通、付费直升和直接授予会籍的合作活动。信用卡或购买行为可以是资格条件，但普通信用卡资讯、买分/转分促销、常规定级积累攻略、积分票和积分房晚 MUST 不作为第一版机会。

#### Scenario: 直接会籍获取路径被纳入
- **WHEN** 一份材料描述用户通过匹配、挑战或合作资格可直接取得、升级或延长某一会籍
- **THEN** 系统将该材料作为会籍获取相关候选继续处理

#### Scenario: 间接相关内容不扩张第一版范围
- **WHEN** 一份材料只描述买分、转分、信用卡奖励或常规定级积累，且没有直接的会籍取得、升级或延期结果
- **THEN** 系统将其判为不属于第一版机会，且不为其创建其他主题类别

### Requirement: 八组精选来源通过统一适配契约接入
系统 MUST 支持 Frequent Flyer Bonuses 博客、Frequent Flyer Bonuses 会籍汇总页、AwardWallet Elite Status、StatusMatch/GetStatus 邮件、StatusMatcher、LoyaltyLobby、Frequent Miler Elite Status 和很旅行八组来源。实施使用的稳定 `source_id`、完整 URL、正文策略、访问限制和默认状态 MUST 来自同一变更中的 `source-registry.md`，不得在业务模块另行猜测或散落配置。每个来源适配器 MUST 只负责发现和获取材料，并输出统一的来源条目与文档契约，不得直接创建业务事件。

#### Scenario: 注册表成为唯一来源配置输入
- **WHEN** 系统初始化第一版来源配置
- **THEN** 它按 `source-registry.md` 导入八个来源组对应的九条来源记录及其入口、策略和空采集频率，其中 StatusMatch 与 GetStatus 邮件具有独立 `source_id`，且不自动新增其他来源

#### Scenario: 目录或 Feed 条目继续获取正文
- **WHEN** Feed、栏目页或目录页只提供文章或报告入口
- **THEN** 对应适配器发现稳定条目标识和正文地址，并按该来源配置获取正文或 Feed 内全文

#### Scenario: 静态汇总记录成为独立材料
- **WHEN** Frequent Flyer Bonuses 会籍汇总页包含多个顶层活动记录
- **THEN** 适配器为每个顶层记录产生稳定指纹，使单条变化可以独立处理

#### Scenario: 邮件保持只读和幂等
- **WHEN** 邮件适配器读取 StatusMatch 或 GetStatus 的允许邮件
- **THEN** 系统以邮件消息 ID 建立来源条目，不修改、移动或删除用户邮件

#### Scenario: Feed 内有正文时不重复抓文章页
- **WHEN** LoyaltyLobby、Frequent Miler 或很旅行的 Feed 条目已提供允许使用的正文
- **THEN** 适配器直接使用 Feed 正文，并遵守注册表中禁止或无需继续请求文章页的策略

### Requirement: 采集频率保持待定
每个来源 MUST 具有可选的采集频率配置，且第一版规划中的频率 MUST 保持未设置。系统 MUST 不自行推断或启用任何采集周期。

#### Scenario: 未配置频率时不自动调度
- **WHEN** 一个来源已注册但采集频率为空
- **THEN** 调度器不自动执行该来源，但允许人工触发和测试调用

### Requirement: 发现与内容执行精确去重
系统 MUST 在获取正文前按来源内条目 ID、邮件消息 ID 或规范化 URL 去重，并在清洗后按原始内容哈希与规范化正文哈希去重。重复执行 MUST 不产生重复文档、分析结果或事件。

#### Scenario: 已处理条目不会重复获取
- **WHEN** 同一来源再次返回相同的稳定条目标识或等价规范化 URL
- **THEN** 系统识别已有条目并停止不必要的重复获取

#### Scenario: 同一地址内容变化被保留
- **WHEN** 已知 URL 的正文哈希发生变化
- **THEN** 系统保存新的文档版本并重新进入后续分析，不覆盖旧版本

#### Scenario: 规范化后内容相同
- **WHEN** 两份抓取载荷仅有模板或格式差异且规范化正文哈希相同
- **THEN** 系统复用已有内容分析，不创建重复业务事件

### Requirement: 正文执行可重放的轻量技术清洗
系统 MUST 将允许处理的 HTML、Feed 或邮件正文规范化为 Markdown 或文本，保留标题、段落、列表、表格和链接，移除脚本、样式、导航、页脚、广告及明显重复模板。清洗器 MUST 不依据会籍关键词删除内容或决定业务相关性。

#### Scenario: 页面模板噪声被移除而正文结构被保留
- **WHEN** 获取的文章同时包含导航、广告、正文列表和活动链接
- **THEN** 规范化结果移除模板噪声并保留正文列表与活动链接

#### Scenario: 清洗结果可追溯
- **WHEN** 系统保存一份规范化文档
- **THEN** 它同时记录允许保存的原始载荷或快照、原始/规范化哈希、解析器版本、来源和抓取时间

### Requirement: AI 只做会籍获取相关性判断
`StatusRelevanceAnalyzer` MUST 对每个新文档版本输出 `YES`、`NO` 或 `UNCERTAIN`，以及置信信息、简短理由和仅供候选召回使用的零个、一个或多个最小 `event_hints`。它 MUST 不直接创建或修改正式事件。

#### Scenario: 明确相关材料进入事件去重
- **WHEN** 分析结果为 `YES` 且结构化输出通过 Schema 校验
- **THEN** 系统将材料送入候选召回与事件关系判断

#### Scenario: 明确不相关材料停止处理
- **WHEN** 分析结果为 `NO`
- **THEN** 系统保存可追溯的分析结果，但不创建会籍事件

#### Scenario: 含义不清的材料等待人工复核
- **WHEN** 分析结果为 `UNCERTAIN` 或输出无法在有上限重试后通过 Schema 校验
- **THEN** 系统保留材料并建立人工复核项，不静默当作确定相关或不相关

#### Scenario: 一篇材料包含多个会籍机会
- **WHEN** 一篇材料并列描述多个彼此独立的会籍获取机会
- **THEN** 分析器在同一文档结果中输出多个最小 `event_hints`，并让每个提示分别进入事件关系判断

### Requirement: 跨材料语义去重形成现实事件
系统 MUST 将来源内容重复与现实事件重复作为两个不同问题处理。候选召回后，`EventRelationshipAnalyzer` MUST 返回 `SAME_EVENT`、`UPDATE_OF`、`DIFFERENT_EVENT` 或 `UNCERTAIN`，并由确定性聚合器更新事件关系。第一版候选召回 MUST 不依赖向量数据库。

#### Scenario: 多来源报道聚合到同一事件
- **WHEN** 两篇不同来源的材料描述同一会籍获取活动
- **THEN** 系统将两份材料关联到同一个 `StatusEvent`，并各自保留来源证据

#### Scenario: 后续信息创建事件修订
- **WHEN** 新材料被判断为已有活动的规则、日期或资格更新
- **THEN** 系统创建事件修订并保留旧版本，不覆盖历史事实

#### Scenario: 无法确定关系时不自动误合并
- **WHEN** 事件关系结果为 `UNCERTAIN`
- **THEN** 系统建立人工复核项，并在复核前保持材料和事件分离

### Requirement: 相关性与事件关系保持独立契约
相关性判断与事件关系判断 MUST 使用独立的输入、输出 Schema、提示词版本和运行记录。它们可以由同一后台任务顺序调用，但一个阶段的实现 MUST 可以在不修改另一个阶段契约的情况下替换。

#### Scenario: 单独重跑相关性模型
- **WHEN** 相关性提示词或模型配置升级
- **THEN** 系统能够从既有文档版本重跑相关性判断，而不强制修改事件关系分析器

### Requirement: 事实必须绑定来源证据
`FactConsolidator` MUST 只从已关联文档整理发生事项、适用对象、可获得会籍、成本、挑战要求、地域、截止时间、会籍有效期、行动链接和限制。每项关键事实 MUST 引用支持它的来源证据；缺失内容 MUST 保持未知，冲突内容 MUST 被标记而不是静默覆盖。

#### Scenario: 来源支持的事实被记录
- **WHEN** 一项截止日期在关联材料中有明确表述
- **THEN** `FactSet` 保存该日期及对应文档证据定位

#### Scenario: 来源之间存在冲突
- **WHEN** 两个来源给出不同的费用或截止日期且无法可靠裁决
- **THEN** `FactSet` 保留冲突状态并触发复核，简报不得把其中一个值伪装成确定事实

### Requirement: 系统生成原创中文简报
`BriefGenerator` MUST 只读取一个版本化 `FactSet`，输出中文标题、短摘要、关键要点、限制或不确定性和来源链接。简报 MUST 重新组织核心信息，不得复制长段来源正文，也不得生成 `FactSet` 中不存在的事实。

#### Scenario: 从事实集合生成简报
- **WHEN** 一个会籍事件具有通过 Schema 校验的 `FactSet`
- **THEN** 系统生成与该事实版本绑定的中文原创简报草稿

#### Scenario: 未知条件不会被补猜
- **WHEN** `FactSet` 未包含明确截止日期或费用
- **THEN** 简报省略该确定性陈述或明确标为未知，不由模型自行补全

### Requirement: AI 使用指定的北京地域配置
第一版 `AIProvider` MUST 使用阿里云百炼的 OpenAI-compatible 接口、北京地域 `cn-beijing` 和模型 `deepseek-v4-flash`。模型、Base URL、推理参数和凭证 MUST 由服务端配置提供，凭证不得进入源码、客户端或业务对象。

#### Scenario: 模型调用使用北京业务空间
- **WHEN** 系统发起第一版 AI 请求
- **THEN** 请求使用已配置的北京业务空间兼容地址、同地域 API Key 和 `deepseek-v4-flash` 模型 ID

#### Scenario: 业务代码不依赖供应商实现
- **WHEN** `AIProvider` 的底层实现或地址发生变化
- **THEN** 相关性、事件关系、事实和简报模块仍通过同一内部接口运行

### Requirement: 模型与处理运行可追溯和可重放
系统 MUST 为每次 AI 与解析运行记录输入文档版本、阶段、模型配置版本、提示词版本、Schema 版本、代码或解析器版本、结果和错误。系统 MUST 能从保存的文档版本重新运行后续阶段而无需重新抓取。

#### Scenario: 提示词升级后重跑
- **WHEN** 操作者选择既有文档并使用新提示词版本重新分析
- **THEN** 系统新增运行记录并保留旧输出，以便比较和回滚

### Requirement: 提供最小人工复核闭环
系统 MUST 提供内部复核入口，使操作者能够查看来源材料、规范化正文、相关性、事件关系、事实和简报，并执行确认、驳回、事件合并、事件拆分和简报重新生成。第一版 MUST 不要求公开产品界面。

#### Scenario: 人工纠正错误聚合
- **WHEN** 操作者发现两份材料被错误合并为同一事件
- **THEN** 操作者可以拆分事件，系统保存复核决定并据此重建事实与简报

### Requirement: 建立可共同维护的人工金标
系统 MUST 定义可版本化的金标格式和离线评测入口，至少支持相关性标签、事件分组或关系、预期关键事实及证据。首批具体文章由用户后续提供并共同标注；在建立基线前系统 MUST 报告评测结果而不得臆定固定上线阈值。

#### Scenario: 新金标案例参与回归
- **WHEN** 一篇材料及其人工标签被加入金标集
- **THEN** 离线评测能够比较当前与候选模型/提示词在相关性、事件关系和事实支持上的结果

### Requirement: 来源访问合规且故障隔离
系统 MUST 遵守每个来源注册的访问与内容保存策略，优先使用公开 Feed 和允许访问的页面，不得绕过验证码、登录控制或明确的自动访问限制。一个来源的失败 MUST 不阻塞其他来源或破坏已经保存的数据。

#### Scenario: 来源禁止正文抓取
- **WHEN** 来源策略只允许使用 Feed、必要摘要或元数据
- **THEN** 适配器仅保存允许内容、哈希和链接，不尝试绕过限制获取全文

#### Scenario: 单来源解析失败
- **WHEN** 一个来源因页面结构变化而解析失败
- **THEN** 对应采集运行记录失败并可单独停用，其他来源继续处理
