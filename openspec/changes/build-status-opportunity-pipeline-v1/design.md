## Context

现有产品与技术基线描述的是 JourneyPlus 的长期愿景，本变更只定义可开始实施的第一条纵向切片。第一版不建设完整 Agent、旅行规划或多主题机会平台，只验证以下闭环：

```text
精选来源发现
→ 精确去重
→ 获取正文并轻量清洗
→ AI 判断是否为会籍获取机会
→ 跨来源语义去重与事件聚合
→ 整理有证据的事实
→ 生成中文原创简报
→ 人工复核
```

第一版的“会籍获取机会”是指直接获得、升级或延长航空、酒店及其他旅行忠诚度会籍的公开或群体公开路径，包括会籍匹配、挑战、快速通道、会籍互通以及直接授予会籍的合作活动。信用卡或购买行为可以成为资格条件，但只有文章的直接结果是会籍获取、升级或延长时才纳入；普通信用卡资讯、买分/转分促销、常规定级积累攻略和积分票房晚不纳入。

本次是初步技术方向；除上述业务边界和最小流程外，其余实现细节可以在实践与金标评测后调整。

## Goals / Non-Goals

**Goals:**

- 接入已选的八组来源，并让每个来源故障可以单独处理和停用。
- 用少量确定性规则保证访问边界、幂等、格式和来源追溯，把语义判断交给 AI。
- 区分“同一内容重复处理”和“不同文章描述同一现实机会”。
- 从多来源事实生成短小、原创、可追溯的中文简报，而不是转载正文或只展示文章链接。
- 让来源、模型、提示词、候选召回和聚合算法可以独立替换或重跑。
- 为人工金标、回归评测和以后有限的主题扩展保留稳定边界。

**Non-Goals:**

- 不实现买分、转分、信用卡、积分票或积分房晚的独立采集与分类流程。
- 不实现个人会籍资产、资格匹配、路径规划、推荐、通知、自动报名或交易。
- 不实现官方站点持续监控；来源文章中的活动链接只作为证据与人工核验入口。
- 不实现通用规则引擎、知识图谱、跨主题关系图、微服务、Kafka、独立向量数据库或复杂 Agent 编排。
- 不在本变更中决定任何来源的采集频率。

## Decisions

### 1. 使用模块化单体，而不是提前拆服务

服务端保持一个应用和一个 PostgreSQL 数据库，后台任务与 API 可以使用独立进程，但共享领域模型。代码按职责分为：

```text
sources       来源注册、发现和正文获取适配器
content       原文保存、规范化和精确去重
status_topic  会籍获取相关性判断
clustering    候选召回、语义关系判断和事件聚合
facts         多来源事实整理与证据绑定
briefs        中文原创简报生成
review        人工复核
evaluation    金标与离线评测
ai            模型供应商适配
```

这些是代码边界，不是微服务边界。一次后台任务可以顺序调用多个模块，但模块之间只传版本化数据契约，不能互相读取私有实现。

**备选方案：** 一开始拆微服务或使用完整 LangGraph。当前流程是固定的短流水线，额外编排和部署成本没有明确收益；等出现需要暂停恢复的复杂分支并经评测证明有价值时再引入。

### 2. 来源适配与主题逻辑分离

所有适配器统一输出 `DiscoveredItem` 和 `RawDocument`，不直接创建会籍事件。完整 URL、稳定 ID、正文策略、访问限制和核验记录以同目录的[第一版来源注册表](./source-registry.md)为准。第一版使用四类适配器：

| 来源组 | 首选入口 | 适配方式 |
|---|---|---|
| Frequent Flyer Bonuses 博客 | `https://blog.frequentflyerbonuses.com/category/elite-status/feed` | Feed 发现条目，再获取文章正文 |
| Frequent Flyer Bonuses 会籍汇总页 | `https://www.frequentflyerbonuses.com/statusmatchoffers.html` | 静态目录解析；按顶层记录建立稳定指纹 |
| AwardWallet Elite Status | `https://awardwallet.com/blog/tag/elite-status/feed/` | Feed 发现条目，再获取文章正文 |
| StatusMatch 与 GetStatus | Gmail `statusmatch` 标签 + `kirikoomiku+statusmatch@gmail.com` | Gmail API 只读适配器；共用 `status_services_mail` 来源 ID |
| StatusMatcher | `https://statusmatcher.com/` 与 `/report/{report_id}` | 目录发现报告 ID，再获取服务端渲染正文 |
| LoyaltyLobby | `https://loyaltylobby.com/feed/` | 仅使用 Feed 正文，不请求文章页 |
| Frequent Miler Elite Status | `https://frequentmiler.com/category/travel/elite-status/feed/` | 使用 Feed 正文 |
| 很旅行 | `https://www.verylvke.com/feed/` | Feed 正文；允许一篇材料产生多个候选事件 |

来源注册表保存入口、适配器类型、启停状态、访问策略和可选的 `collection_cadence`。第一版所有 `collection_cadence` 保持未设置；未配置调度的来源只能被手工触发或测试调用，调度器不得自行推断频率。

**备选方案：** 为每站编写包含业务抽取规则的爬虫。它会把页面变化、主题边界和字段抽取耦合在一起，重现此前规则膨胀问题，因此只允许来源适配器保留发现与技术解析所需的最少差异。

### 3. 先做两级精确去重，再做语义去重

精确去重分两处执行：

1. 发现后以来源内条目 ID、邮件消息 ID或规范化 URL 判断是否已见，避免无意义重复获取；
2. 轻量清洗后以原始内容哈希和规范化正文哈希判断内容是否相同。若同一 URL 内容发生变化，则保留新版本并继续处理。

不同来源或不同文章描述同一机会时，普通 SQL 候选召回器先按时间、主体提示、会籍类型提示和文本检索缩小候选集，再由 AI 返回 `SAME_EVENT`、`UPDATE_OF`、`DIFFERENT_EVENT` 或 `UNCERTAIN`。`UPDATE_OF` 创建事件修订，不覆盖旧事实。

第一版不使用向量数据库。候选召回通过 `CandidateRetriever` 接口隔离；只有金标显示 SQL 召回造成不可接受的漏合并时，才评估 PostgreSQL `pgvector` 或其他语义召回实现。该选择与技术基线中“语义检索第二阶段按需启用”的方向一致。

### 4. 正文只做轻量技术清洗，不能用规则删业务语义

正文获取后转换为规范化 Markdown 或文本，保留标题、段落、列表、表格和链接；移除脚本、样式、导航、页脚、广告和明显重复模板。清洗器不得依据会籍关键词删除正文，也不得负责判断文章是否相关。

系统按来源许可保存不可变原始载荷或允许范围内的快照，并保存原始哈希、规范化哈希、解析器版本和抓取时间。若来源条款不允许保存全文，则只保存允许的必要内容、哈希、元数据和链接。

**备选方案：** 直接把未经处理的页面交给模型。大量模板噪声会增加成本并降低稳定性；反过来做重语义清洗又会提前误删证据，因此采用可重放的轻清洗。

### 5. 轻规则与 AI 各自只做擅长的事

确定性规则只负责：来源白名单与访问边界、URL/ID/哈希幂等、HTML 技术清理、Schema/枚举校验、必要来源引用、任务状态和数据约束。它不维护会籍关键词黑白名单，也不规则化猜测复杂资格。

AI 分为彼此独立的契约：

- `StatusRelevanceAnalyzer`：输出 `YES | NO | UNCERTAIN`、置信信息、简短理由和零个、一个或多个最小 `event_hints`；
- `EventRelationshipAnalyzer`：仅比较候选材料与已有事件的关系；
- `FactConsolidator`：从已关联材料整理事实，并把每项事实绑定到证据；
- `BriefGenerator`：只读取 `FactSet`，生成标题、摘要、要点、限制和来源链接。

相关性判断和语义去重可以在同一个后台任务中连续执行，但不能合并为一个不可分割的提示词或输出对象。这样既保持流程简短，又可以单独评测、重跑或替换其中一步。

### 6. AI 供应商通过 OpenAI-compatible 接口隔离

第一版运行配置为：

```yaml
provider: aliyun-model-studio
region: cn-beijing
model: deepseek-v4-flash
base_url: https://dashscope.aliyuncs.com/compatible-mode/v1
```

第一版实际使用用户选择的北京地域按量付费地址 `https://dashscope.aliyuncs.com/compatible-mode/v1`；上面的业务空间专属地址仍是未来生产环境可直接替换的同地域选项。模型名称、地域、兼容接口地址和推理参数属于版本化服务端配置；API Key 只存在于服务端环境变量或密钥服务。业务模块依赖内部 `AIProvider`，不依赖阿里云 SDK 类型。由于 `deepseek-v4-flash` 当前不支持原生 Structured Outputs，JSON Schema 作为提示词约束并由本地 Pydantic 严格校验，失败使用有上限的重试并保留运行记录，模型不得直接写正式事件或简报。

模型 ID 与北京按量付费/业务空间地址已按阿里云百炼当前官方文档核对；部署时须使用与地址匹配的北京地域 API Key。参考：[deepseek-v4-flash](https://help.aliyun.com/en/model-studio/deepseek-v4-flash)、[Base URL 总览](https://help.aliyun.com/zh/model-studio/base-url)。

### 7. 数据围绕“材料—事件—事实—简报”组织

第一版保留以下最小对象：

| 对象 | 责任 |
|---|---|
| `Source` | 来源配置、适配器、访问策略和未设置的采集频率 |
| `CollectionRun` | 一次来源执行及成功/失败信息 |
| `SourceItem` | 发现标识、URL/邮件 ID、时间和处理状态 |
| `DocumentVersion` | 允许保存的原始载荷、规范化正文、哈希和解析器版本 |
| `AnalysisRun` | 阶段、输入版本、模型/提示词/Schema 版本及结构化输出 |
| `StatusEvent` | 一个现实中的会籍获取机会及当前状态 |
| `EventEvidence` | 文档与事件的关系、证据定位和来源时间 |
| `FactSet` | 带证据引用的当前事实集合 |
| `Brief` | 基于特定 `FactSet` 生成的中文原创简报版本 |
| `ReviewDecision` | 人工确认、驳回、合并、拆分或修订记录 |
| `GoldCase` | 人工标注的相关性、事件关系和预期事实 |

原始材料与 AI 运行记录不可被后续结果覆盖。提示词、模型或规则更新时可以从 `DocumentVersion` 重跑，不需要重新抓取来源。

### 8. 原创简报以证据化事实为唯一输入

`FactSet` 只在来源支持时保存：发生了什么、适用对象、可获得会籍、成本、挑战要求、地域、截止时间、会籍有效期、行动链接和限制。缺失事实保持未知，不允许模型补猜。每项关键事实至少引用一条 `EventEvidence`；冲突事实必须保留冲突标记或进入人工复核。

`BriefGenerator` 不读取原文章正文，只读取审核前的结构化 `FactSet`，输出中文标题、短摘要、关键要点、限制/不确定性和来源链接。输出必须是重新组织后的信息摘要，不复制长段原文，也不能掩盖仍未知或冲突的事实。

### 9. 人工复核和金标先做最小闭环

第一版只提供内部复核入口，能够查看原始/规范化材料、相关性结果、事件关系、事实和简报，并执行确认/驳回、合并/拆分和重新生成。不建设公开产品页或复杂后台。

评测框架先定义金标格式和运行方式，具体文章由用户后续与系统共同标注。初始标签覆盖：相关性 `YES/NO/UNCERTAIN`、事件分组或关系、预期关键事实与证据。第一版先报告指标和错误样本，不在没有金标基线前写死上线阈值。

## Risks / Trade-offs

- **[第三方页面或 Feed 结构变化]** → 适配器独立、保存解析失败样本、单来源可停用，不让故障阻塞其他来源。
- **[AI 漏判或误判会籍机会]** → 保留 `UNCERTAIN`、抽样复核、版本化重跑，并使用金标持续比较提示词和模型。
- **[语义去重误合并或漏合并]** → 候选召回与关系判断分开，保留人工拆分/合并和事件历史；是否引入向量召回由评测决定。
- **[多来源事实冲突或过时]** → 每项事实绑定来源与观察时间，冲突不静默覆盖，简报显式显示限制或等待复核。
- **[转载与采集合规风险]** → 优先 Feed 和允许访问的页面，按来源策略控制保存范围，不绕过访问控制；对外只输出短篇原创简报和来源链接。
- **[固定单模型带来供应商风险]** → 首版按用户指定配置运行，但通过 `AIProvider` 和版本化 Schema 隔离，未来切换不改业务模块。
- **[为未来解耦造成过度设计]** → 只建立当前流程已有的接口，不预建未来主题表、关系图或通用规则 DSL。

## Migration Plan

当前没有运行中的系统或业务数据，无存量迁移。实施按可验证的纵向顺序进行：先建立数据与适配器契约，再跑通一个 Feed 来源，随后加入其余来源、AI 判断、事件聚合、事实/简报和人工复核。每新增一种适配器都复用同一后续管线。

部署时来源默认不启用自动调度；在用户配置采集频率前仅允许手工执行。回滚时可停用对应来源或 AI 阶段，并保留原始材料和运行历史，不删除已采数据。
