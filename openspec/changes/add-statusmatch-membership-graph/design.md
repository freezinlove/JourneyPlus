## Context

第一阶段为每个 ACTIVE StatusMatch watch 保存了一个当前 FactSet，其中 `status_mappings` 已包含来源项目、一个或多个来源等级、目标等级、可用性、条件、冲突和页面证据。它们目前仍是按活动分组的列表。用户真正查询的是“我现在有 X 项目的 Y 会籍，可以匹配到什么，并能否从新的会籍继续匹配”，因此需要跨当前项目连接同一忠诚度项目与等级。

底层事实天然是有向图，而且不同活动会共享来源或目标节点；直接把整张图交给 UI 会产生大量交叉线。用户要求的呈现形式则更接近以一个会籍为根、逐层展开的树。设计必须同时保留底层图事实与一个不会无限循环、不会重复展开共享子图的树视图。

## Goals / Non-Goals

**Goals:**

- 只消费 ACTIVE watch 的当前 FactSet，不调用 AI、不修改第一阶段数据。
- 把每个明确来源等级到目标等级的事实转换为方向固定的可追溯边。
- 规范化同一项目的不同写法，使真实的跨活动多跳路径能够连接。
- 表达确定、条件、通配和等级不明确的关系，不把不确定性伪装成确定事实。
- 从任一具体会籍生成有界、确定性排序、不会无限闭环的树状展开。
- 自动审计事实声明覆盖、边方向、自环、强连通环、冲突、歧义和截断原因。
- 用八个真实项目人工核对边与原始 FactSet，并检查树的可读性。

**Non-Goals:**

- 不推断用户是否实际满足地域、费用、证件或一次性申请等活动级条件；边上的 claim 只保留这些条件供展示。
- 不计算“最佳”匹配路径、成本最小路径或自动申请策略。
- 不将 `UNAVAILABLE` 当成可行边。
- 不接入普通文章或第三方文章关注点。
- 本阶段不制作最终前端画布；提供稳定树 JSON 和内部 API 供后续 UI 渲染。

## Decisions

### 1. 底层图与用户树分离

`MembershipGraphService` 每次从数据库当前事实确定性重建图快照。图节点表示“规范项目 + 规范等级”，图边表示“来源会籍可以申请目标会籍”。查询服务再以指定节点为根执行有界深度优先展开，返回嵌套树。

树展开维护当前祖先集合和全局已展开集合：目标在祖先中时返回 `CYCLE` 叶节点；目标已由其他分支展开时返回 `CROSS_REFERENCE` 叶节点；两者都不继续递归。这样保留关系存在这一事实，但不会复制整片子树或形成无限闭环。

替代方案是直接返回整张图供前端布局，但当前数百条映射会使线条大量交叉，也不能满足“从一个会籍逐条相连”的主要用法。

### 2. 节点规范化使用可解释的项目身份和等级规则

每个 StatusMatch 目标项目由 event program 形成一个规范项目身份。服务从该项目多个目标等级的公共前缀生成忠诚度项目别名，例如 `Air Astana Nomad Club` 同时拥有 `Nomad Club` 别名；来源项目只有在精确匹配或以足够明确的别名结尾时才合并。多个候选同分时不合并并记录 alias ambiguity。

目标等级先移除已确认项目别名前缀，再对大小写、空白、标点及尾部 `status` 做规范化；来源等级使用同一规则。节点仍保留首选展示名称和所有原始标签。该规则能够连接 `Air France Flying Blue Gold`、`KLM Flying Blue Gold` 与目标 `Flying Blue GOLD`，但不会仅凭包含常见词 `Club` 就合并项目。

替代方案是维护手工项目别名表。它以后可作为覆盖层加入，但当前八个项目可由目标身份和公共前缀确定性解释，先避免一套易过期的人工品牌词典。

### 3. 一个图边聚合多个事实 claim

同一来源节点和目标节点可能由多个活动或映射行支持。图中只保留一条边以控制分支数，边内保存一个或多个 claim。每个 claim 包含 watch、host、event、FactSet、原始项目/等级/目标、availability、conditions、conflict 和 evidence，并有稳定 claim ID。

`AVAILABLE` 与 `CONDITIONAL` 进入可遍历图；`UNAVAILABLE` 进入审计计数但不生成可达边。条件和冲突不在构图时裁决，树边以 claim 的最严格状态展示。

### 4. 通配关系作为规则保存，在查询时解析

类似 `All major airlines / All membership levels → Club Avolta Gold` 的映射保存为 wildcard rule，而不是预先复制成数百条永久边。当前 FAQ 表头被确定性解析为 AIRLINE、HOTEL、CRUISE、CARD 或 UNKNOWN 类别，用于给具体项目补充类别；规则查询时适用于同类别的已知具体会籍。

明确写着所有等级的规则标记为 `WILDCARD`；只说明项目或“精英会员”但没有具体等级的规则标记为 `UNCERTAIN`。查询具体会籍时两类规则都可以产生关系，返回结果必须保留 `derived_from_rule=true` 和相应 certainty，禁止显示成普通精确边。

这比把 `ANY_AIRLINE` 做成普通可见节点更符合用户从具体会籍出发的查询，也避免通配节点造成伪多跳。

### 5. 图规模在查询边界控制

树查询接受 `max_depth`、`max_nodes` 和 `max_branches`，使用保守默认值并设置硬上限。达到限制的节点返回 `DEPTH_LIMIT`、`NODE_LIMIT` 或 `BRANCH_LIMIT`，同时报告被省略数量。子边按目标项目、目标等级和 certainty 稳定排序，因此相同 FactSet 产生相同结果。

### 6. 事实忠实度和图逻辑分开审计

审计器首先把所有可用 mapping 的每个来源等级转成预期 claim ID，再与实际 edge/rule claim ID 比较，报告 missing、invented 和 duplicate；这回答关系是否符合提取事实。随后对具体边运行自环和强连通分量分析，对代表性根节点运行树展开并报告 cycle、cross-reference 和各类截断；这回答逻辑是否清晰。

审计不把存在环本身视为数据错误，因为现实中 A 会籍可能可匹配 B，而另一个活动又允许 B 匹配 A。产品约束是树查询必须识别并截断，而不是删除其中一条真实边。

### 7. 独立模块与只读访问面

新模块只依赖数据库模型、FactSet contract 和 StatusMatch 表格元数据解析器。CLI 提供根节点树查询和全图审计；内部 review API 暴露同样的 JSON。第一阶段处理链路、自动化和模型预算均不依赖图模块，避免图功能影响正常采集。

## Risks / Trade-offs

- [项目别名自动合并可能误合并或漏合并] → 只允许精确或明确后缀匹配、选择最长别名、同分歧义不合并，并在审计中列出。
- [旧 FactSet 没有来源类别字段] → 从同一当前 FAQ 的表头确定性补充类别，不调用 AI；无法确定时保留 UNKNOWN，通配规则不跨 UNKNOWN 猜测。
- [通配边使单个会籍分支很多] → 规则延迟展开、同目标聚合、默认分支上限和明确截断标志。
- [真实图存在 A→B→A] → 底层保留两条事实边，树层按祖先检测标记 CYCLE 并停止。
- [共享目标造成重复大子树] → 首次完整展开，后续分支返回 CROSS_REFERENCE。
- [FactSet 更新使图变化] → 图不持久化，每次查询读取 current FactSet；审计输出参与的 FactSet ID 便于复现。
- [活动级资格并不等于用户可实际申请] → claim 完整保留 conditions/conflict/evidence，图只表达页面公布的等级映射，不作资格决策。

## Migration Plan

1. 增加图 contracts、规范化器、构建器、树查询和审计器，无数据库迁移。
2. 增强现有 FAQ 表格解析器以提供不改变 FactSet 内容的来源类别元数据。
3. 增加 CLI 和内部只读 API。
4. 用 fixture 覆盖精确边、条件边、不可用边、通配边、未知等级、别名、环和交叉引用。
5. 在本地当前八个 ACTIVE watch 上构图并人工审核代表性多跳根节点。

回滚只需移除新模块和访问入口；第一阶段数据不需要回滚。
