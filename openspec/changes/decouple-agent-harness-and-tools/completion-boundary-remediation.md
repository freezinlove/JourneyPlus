# 第二轮正确性整改：交付、事实、参数边界

依据用户“开始执行修复”实施；保留现有未提交整改，不提交、不修改生产数据。本文补充 design D7：工具进度继续推送，配置业务交付校验时正文先缓冲，经过校验后交付，不能宣传为逐 token 的原生正文流式。模型仍选择正文、解释、对象和下一步，harness 不决定业务工具顺序。

## 已落地的机制与边界

- 通用 CompletionPort 返回通过、具体缺项、部分完成和可选已渲染正文。业务适配器由 composition 注入；通用运行核心不导入业务服务。拒绝后的模型草稿和反馈持久化，前端读取不展示草稿，后续回合默认不带入被拒草稿。修复上限保存在 checkpoint，耗尽后 PARTIAL，不伪报 COMPLETED。
- 业务最终回答可携带声明的展示、写入和完整读取交付项；对照当前轮真实 call/result 检查类型、比较列、对象数、操作回执、分页连续覆盖。曾声明的要求不能在修复时删减；旧轮回执不能替代本轮交付。
- 精确事实允许通过不可变 artifact JSON pointer 渲染，不接受模型提供覆盖值。模型保留解释文字和顺序，禁止把笔记/查询/展示标题当证据。该协议并不证明自由解释的事实正确，也不证明来源页面就是官方政策。
- 查询 patch 从无类型字典改为显式顶层字段，保留 null 清除与省略继承。既有行业、联盟、constraints 变更必须逐字段声明用户消息、引文、理由；错误不创建新查询/执行查询。消息引用与引文只验证来源，不宣称语义授权已经成立。
- 未解析会籍返回名称权威类别，原话作为主要回执文本；原话参与检索，路线源保留原始陈述。不同原话碰巧落到同一个未核实名称索引时不能静默 NOOP/合并，返回冲突供显式引用处理。

## 尚不能据此宣布解决的部分

1. 交付清单仍由模型解释自然语言后声明。首次就漏列要求，确定性程序无法仅凭该清单发现。当前没有另加分类模型，也不以关键词推断用户需求。需要继续设计显式任务约束承载及逐轮来源复核，不能把“清单校验通过”算语义验收通过。
2. 自由文本仍可能存在无依据事实或把经验外推成政策；字段引用保证引用值一致，不保证全部解释符合证据。必须继续做人工 ModelPort 第一视角检查及故障场景复验。
3. 全新 query 仍可能错误提取/放宽条件；逐字段变更声明阻止静默 patch，不能证明声明理由真实符合原话。未解析名称列仍是历史兼容的提取索引，尚未迁移成完全独立的陈述实体。

上述是明确剩余缺口，不是把原三类问题宣称修完。不得以新增机制和单元测试替代真实人工双视角验收；本轮在这些边界完成前不启动第三方模型回归。
