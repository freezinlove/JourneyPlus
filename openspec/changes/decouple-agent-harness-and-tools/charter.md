# 实施总纲：先完成系统，再验收第三方模型

本文件依据用户 2026-09-08 最新明确要求制定，是本 change 的实施、审查和阶段交付总纲。它补充并修正原方案的实施顺序；与旧附件中的阶段顺序、模型调用授权表述冲突时，以本总纲为准。功能规格继续有效，不能以调整顺序降低验收要求。

## 1. 目标形态

整体架构必须干净整洁、低耦合、逻辑清晰、分工明确。模型是可替换的决策核心，harness 是业务无关的运行核心；不能以固定工具顺序、意图分类、品牌特例或隐式状态把 Agent 重建成 AIWorkflow。

- 模型负责理解、决定下一步、选择工具、解释证据和组织回答。
- harness 负责协议、执行生命周期、资源控制、取消、恢复和结果回送，不判断业务意图。
- 工具提供独立、明确、可组合的能力，不互调 handler 形成隐藏工作流。
- 服务层负责确定性业务规则和显式数据操作，不读取整个聊天状态推断参数。
- 数据访问层负责作用域、事务、版本和持久化；正式知识、用户数据和临时工作区写入范围明确。
- 既有 AIWorkflow、简报、完整匹配图保持独立。Agent 通过稳定的只读知识接口及对应版本简报引用使用其成果，不触发采集、提取、发布或重建。

清理重复实现、废弃执行链、临时补丁和隐式状态；不能只移动文件宣称解耦，也不能为了形式上的分层增加无价值转发。纯业务算法可复用，但不能携带旧控制链依赖。

## 2. 正确性优先

效果和正确性是首要目标，满足后再优化上下文效率。不能为减少 token 丢失约束、证据、未知项、来源、必要历史或可恢复性。

逐项检查数据库结构、实际记录、工具 schema、输入输出及数据传输：字段含义一致，来源与版本可追溯，空结果与未覆盖明确区分，裁剪有覆盖说明及继续读取入口，实际写入与回执一致。避免重复累积、无用字段和含义不明的数据，但不能把未读当作不存在。

记忆和上下文应干净、合理、高效：用户原话、假设、模型笔记、工具观察、展示焦点各有来源；查询结果不得变成用户约束；历史可找回，笔记不覆盖原话，长期会籍不靠隐藏任务 flags 维护。

## 3. 人工坐在模型位置，双视角完整审查

实施者亲自接入真实 AgentModelPort/harness，以每一次实际模型输入为依据，阅读后决定下一次工具调用或正文。执行真实工具并使用隔离数据库；公开网页调查可以真实联网，但不调用第三方模型。

第一视角：只使用该次模型可见的提示词、工具定义、上下文、记忆和工具结果决定下一步。判断是否足以正确完成任务、是否存在歧义或冗余、工具是否可发现和组合、多轮是否能保留及改变用户条件。不得把第三视角查到但模型不可见的数据偷带入决策。

第三视角：另行检查实现、数据库结构及 before/after 记录，核对真实查询条件、数据来源、作用域、事务、状态变化、回执、恢复和前端显示。发现第一视角需要靠内幕补足的信息时，应修复数据契约并重新验收。

每条人工证据至少包含：需求/场景编号、用户输入、实际模型请求、基于可见信息的简短决策依据、实际调用参数、返回结果、数据库或状态核对、最终正文/展示、结论和待修项。只记录可审计的决策摘要，不要求隐藏思考链。

看代码、自动测试、预先编排完整调用序列只能作为辅助，不能冒充上述逐步人工调试。每个大板块完成后必须实际验收；修复后重新验证受影响链路，并保留首次失败。

## 4. 实施顺序与第三方模型禁用边界

1. 全面审查本 change、当前代码、依赖、数据库和已有证据，建立逐项人工验收矩阵。
2. 完成目标架构、数据契约、工具、上下文、记忆、运行恢复和 UI/API 改造；每个板块人工驱动、核对、修复、复验。
3. 在工作区完成旧控制链退役和本地人工预览收口，完成确定性及真实数据库/公开网络/浏览器验证，形成接入真实模型之前的审核包。
4. 交由用户审核，等待用户明确允许后，才可调用第三方模型 API 开始最终模型验收。

当前阶段禁止所有第三方模型调用，包括启动 echo 探针、冒烟测试、对照选型、自动 fallback、隐藏分类/润色及 Workflow 模型调用。之前的模型选型和费用授权不构成当前阶段调用许可。人工入口不得创建模型 HTTP client 或因启动/恢复隐式探测模型；协议兼容以本地传输 fixture 验证。

原 G5 的真实模型完成率、延迟、token 指标和 64 case-run 保留为审核后的独立门槛。人工审查不能冒充模型表现，也不能承诺所有模型能力相同。原 G6 的代码清理和本地人工预览前移；生产切换仍不属于本任务授权。

## 5. 本阶段完成标准

- 六项规格和 acceptance 各类别都有明确映射；系统侧要求有代码、人工输入输出及必要自动测试证据，无未解释的大缺口。
- 模型、harness、工具、业务服务及 Workflow 的依赖边界成立，旧决策链不再有活动入口，兼容仅保留历史读取与显式导入。
- 全部 12 个工具及主要操作、错误/空值/分页/作用域分支经过核对；写入生命周期、幂等、冲突、等待任务、取消恢复有实际数据库证据。
- 多轮条件变化、历史恢复、结果展开、上下文资源控制和展示引用经人工逐步使用；无已知会影响正确性的静默丢失、污染或错误表达。
- 相关回归、PostgreSQL 验证、OpenSpec strict 和依赖检查通过；失败和环境限制明确记录。
- 审核包区分“已实现”“自动测试通过”“人工验收通过”“待第三方模型验收”，列出改动、证据、已知限制和未提交文件；不得以任务勾选比例冒充质量完成度。

“最佳实践”以以上可验证职责、契约和运行行为为依据，不以模型试跑成功或绝对无缺陷承诺为依据。若仍有系统缺陷应继续修复，不提前把排查责任交给真实模型。

## 6. 操作边界

测试写入仅使用明确隔离数据；不修改用户真实会籍，不通过 Workflow 回填正式知识使样例通过。保留历史失败与证据，不泄露凭据。未经另行明确授权，不提交 Git、不重写历史、不发布生产、不自动归档，不删除新表或撤销已成功业务写入。

审核后模型验收优先使用百炼/千问平台性价比高的可用模型，避免 Max 等高价档；具体运行仍以用户审核后的明确许可为前提。
