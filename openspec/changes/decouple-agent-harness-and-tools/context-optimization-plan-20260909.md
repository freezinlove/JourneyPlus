# 上下文编排优化方案（2026-09-09）

依据 [本轮双视角验收](dual-perspective-review-20260909.md)，遵循 [实施总纲](charter.md)：效果、正确性、信息可恢复性优先；降低 token 是后续目标。本文件是待实施方案，所列离线实验没有改生产上下文。

## 1. 先回答开销来源

测量对象是 ReviewerModel 导出的真实 native wire messages/tools，统一按紧凑 UTF-8 JSON 字节统计，不使用磁盘缩进文件大小冒充传输量。下表不是千问 tokenizer 或计费账单；运行器无供应商 usage 时使用保守估算，二者不能直接混称。

| 本轮指标 | 实测 |
| --- | ---: |
| ModelPort 输入 | 60 次（含 1 次取消） |
| 累计 messages + tools | 2,096,348 bytes，约 2.10 MB |
| 单次输入范围 | 23,207–59,983 bytes |
| 每次完整 12 工具定义 | 19,246 bytes |
| 系统消息开销（概念例） | 3,887 bytes |
| 23 个完成回合的运行器输入估算合计 | 731,899 tokens |
| 完成回合估算范围（一次用户消息可能多次调用模型） | 17,469–52,383 tokens |
| 第三方模型实际消耗 | 0 |

证据：`context-measurements.json`、`summary.json`，位于 `.secrets/agent-harness/20260909/deep-review/`。

**既有调用次数因素，也有单次固定开销和重复历史因素。** 本轮仅二十余个用户回合，按现有预算估算就积累到约 73.2 万输入 token。换真实 tokenizer 后具体数字会不同，但原始字节已经说明有优化价值。

典型例子：路线调查后问“一句话解释会籍匹配”，本人零工具即可回答，但 `routes/request-016.json` 仍携带：

- 工具定义 19,246 bytes；
- 系统消息 3,887 bytes；
- 旧历史 26,861 bytes；
- 当前用户消息 279 bytes；
- 加 JSON 容器后合计 50,293 bytes，运行器本回合估算 17,503 输入 token。

另一个例子：读取剩余路线并比较，4 次模型输入后累计估算 52,383 token，最后一次因资源预留被要求只给最终回答。该回合成功完成要求，但若还需继续展开或展示，预算余量很小。只扩大预算会增加成本，不解决重复信息。

## 2. 已做的离线实验

### 2.1 完全相同或可确定推导的字段精简

对本轮实际 60 份请求复制件做以下表示层转换：

- `effective_input` 与同一 call 的实际 arguments **完全相等**时不重复携带；解析后的有效查询与输入不同的情况必须保留。
- `route_refs` 恰好等于当前 candidates 的 ref 序列时，从 candidates 得到该序列，保留顺序。
- 内外 `next_cursor` 相同只保留一个。
- history 消息中的 Part 联合类型仅去除不适用的 null 槽位，不删除业务字段 null。

累计从 2,096,348 降到 2,041,459 bytes，**节省 54,889 bytes，约 2.62%**。这证明有确定冗余，但仅靠删 JSON 字段不会带来数量级改善。正式落地仍需版本化工具视图、合同测试及人工回放；原始 ToolResult 不改变。

### 2.2 工具 schema 的收益有限

- 仅移除 default 注解：19,246 → 18,116 bytes，工具定义减 5.87%，单次省 1,130 bytes。
- 这些 default 有些会帮助模型理解默认行为，正式方案只删无决策价值的注解，关键默认值须用简短说明保留。不能把所有 default 一删就宣称效果不变。
- 公用子树 `$defs` 并不天然省钱：原 DTO schema 含 title 时为 22,235 bytes；去掉 title 后为 18,825 bytes，仅比当前内联版省约 2.19%。当前内联是为兼容供应商解析，不值得为了这点收益先冒兼容风险。
- 针对同一结果内部大块完全相同 JSON 子树的可逆引用池实验，44 个首次完整工具结果合计约 116 KB，只省约 4.5 KB（3.9%）。不建议为此引入通用内容寻址协议或跨工具压缩框架。

证据：`measure_context.py`、`measure_safe_candidates.py`、`safe-candidates.json`。上面的子树实验可恢复原 JSON；它不等于模型理解新引用表示已经验收。

## 3. 建议实施顺序

### P0：先关闭正确性缺口

先修验收报告中的 A（未解析数量）和 B（比较角色）。保持原数据和决策语义，补实际输入→返回→浏览器/SQL断言。不能在错误的汇总数字或不完整展示回执上做压缩。

### P1：精简结构重复，保留当前能力

涉及 model adapter 的 model-facing 视图与工具输出投影；完整日志、数据库、原始 ToolResult 均保留。

1. 落地 2.1 的确定冗余消除，要求逐项可恢复/可推导，不按文本长度盲删。
2. 统一 envelope 的覆盖口径：分页读取完成、知识检索范围、源资料完整度分开命名；保留 unknown、遗漏数量、源游标和补读路径。不能把 `PARTIAL` 一律改成 `OK` 来省说明。
3. 对工具结果重复的固定含义（例如“已知费用不是总价/个人资格”）可用一次合同说明加明确枚举，但影响费用理解的字段必须在结果上仍可辨识。
4. 保持全部 12 个工具立即可用。当前无需新增工具路由层、意图分类器或另一个模型。

验收：原话授权、null 清空、实际 query、候选顺序、未知费用、资格不确定、分页/引用和操作回执与基线完全一致；同一场景的必要调用数不增加。

### P2：按问题所需披露工具资料

这是比 schema 删注解更有价值的方向。

- `activity.read`：overview 继续轻量；detail 优先给请求 aspects 的事实及适用限制，避免同一 conditions/prices/validity 同时出现在 facts、options 和 evidence 中。证据 ref/版本保留；只有用户要原文或事实不足时再展开。不能为了只问价格而省去价格适用的身份/日期条件。
- `routes.evaluate inspect`：条件原文在 step.constraint_checks 已给出时，不在 candidate.material_caveats 再完整复写；保留汇总未知状态、哪些步骤未满足和来源引用。多个候选共享步骤仍只返回一次。
- 路线续页：保留 query_ref、当前有效来源/目标/条件的必要摘要，避免每页重复多层身份元数据及内部搜索统计。内部统计继续留在原始日志。
- 外站资料：作者/原方向/原等级、提交日期与申请日期、正文完整性和可比性保留；网页导航和无关选项不应混入经验事实。删重复内容不能让报告自述变成官方规则。

验收：拿本轮 SAS 多步路径、阿斯塔纳条件费、皇家约旦加拿大护照、Alaska 经验作正反例，由本人逐轮读取新返回完成同样任务。节省量按整回合统计，不能只展示某个小响应变短。

### P3：改进多轮历史工作集，保留可恢复的原话和证据

当前策略主要是“最多最近 12 条可见消息 + 老工具结果逐个约 3 KB”。它能控制无限增长，但不会识别整个已结束调查带来的重复成本。

建议在现有 context projector / WorkspacePort 内增量实现，不新增独立记忆系统：

1. **原始存储层**：完整消息、工具原始结果、query/material/route artifacts、展示和操作回执不变。
2. **当前工作集**：当前用户原话、当前轮 call/result、待完成操作、点击 focus、必须保留的用户约束和关键证据保持直接可见。当前轮证据超大时仍用有完整引用的明确部分投影。
3. **已结束旧回合**：保留用户原话、最终答复、操作结果及对象/查询/证据索引；旧的重复 call/result 可按完整组转成可展开的历史资料条目。明确谁说的、何时、所属 query/版本，不能把旧工具内容或笔记伪装成用户新约束。
4. **模型笔记**：继续是带源消息 ID 的辅助材料；补足引用能力即可，不让笔记成为授权或覆盖最新原话。不得用隐藏摘要模型处理。
5. 对“其他不变”“回到最初”“刚才点击”这类依赖历史的对话，必须保留能定位原查询的索引；有歧义时模型自己调用 workspace.read。harness 不靠品牌/意图正则决定查询或悄悄删除条件。
6. 必要时让模型显式维护要保留的工作资料 refs，由系统只校验引用、预算及存取。先复用现有工作区能力，只有证明现有字段不足才扩字段；不先造一个通用记忆编排平台。

概念问答例中，26.9 KB 旧历史说明优化空间较大，但**不能直接承诺全部删去或承诺省 50%**：需保留原话/引用，并核算以后找回产生的额外调用。以本轮 8+1 轮路线长对话重新完整运行，衡量累计开销、原查询恢复成功和信息缺失率。

### P4：再判断是否需要工具定义按需披露

只有 P1–P3 完成后，固定 schema 仍占主要成本时再考虑：

- 模型持续看见完整能力目录，并由模型主动请求所需工具的详细 schema；模型可随时获取任何能力，不按关键词给它限定一条流程。
- ModelPort/工具目录机制负责披露，harness 仍不选择业务工具。原有全 schema 模式保留作对照和回退。
- 这会增加一次发现/展开的模型往返，可能比携带 19 KB schema 更贵或降低首次调用成功率。必须用同样对话验证后决定，当前不作为默认改造。
- 不通过把参数全部放入任意 JSON 字符串、删除字段约束或合并成巨型万能工具来降低定义大小。
- 供应商缓存可作为 ModelPort adapter 的可选成本优化；兼容性、真实命中与计费效果留到用户批准真实模型验收后验证，不把缓存当作上下文正确性的前提。

## 4. 验收门槛

按 P0→P1→P2→P3 实施，每阶段都用真实 ModelPort 人工决策验收，再回查 SQL/产物/前端；P4 由测量决定是否值得做。

必须同时满足：

- 事实及适用条件无漏读误读，未知不变已知，假设不变已存来源，来源不变目标，中转不变终点。
- 条件连续修改、恢复原查询、超过 12 条消息后的原话找回、focus 与版本绑定无回退。
- 工具选择自由；不新增固定业务流程，不发生为了节省 token 而减少必要调查。
- 写入只凭真实用户来源、正确版本和成功回执确认，null/省略/NOOP/冲突语义保留。
- 页内裁剪和源分页一致，完整结果永远可找回，展开不能反复只返回同一份不可读索引。
- 对整回合/整段多轮对话统计：输入字节、估算 token、请求数、工具数、补读次数、预算提前结束次数和任务完成情况。费用/缓存收益后续用真实供应商 usage 单独核验。
- 先把效果保持住，再接受成本下降；不把预算用尽导致提前结束当作节省成本。

本方案不设未经实证的统一节省百分比。已测到的低风险结构精简收益约 2.6%；更大的潜力在历史工作集和工具资料去重，须经过完整对话重新验收。
