## Why

用户要求最终系统是两个职责独立的板块：AIWorkflow 生产并储存知识，提供简报和完整匹配图；Agent 消费同一数据库中的知识并引用简报。当前历史改造与过渡状态难以核对，本次以明确目标重新审计、重建和验收，不继续叠加旧方案或兼容旧数据。

## What Changes

- 以 [目标架构](target-architecture.md) 为核心，先建立全仓库“模块—输入输出—消费者—表—入口”映射，依据事实决定保留、整改和删除。
- 保留 AIWorkflow 的必要采集、处理、校验、存储和发布职责；使用一个正式知识契约，不将必要中间处理误判为废弃流程。
- 共用一个正常数据库，区分来源/处理记录、目录、正式知识、版本简报/图投影、用户数据和 Agent 会话。
- 完成可替换 ModelPort、通用 harness、独立工具及可追溯上下文，Agent 不触发知识采集/发布，简报和完整图独立可用。
- **BREAKING**：明确清空范围与恢复方式后停服清理旧数据，完成架构代码后从空库重建；不提供旧 schema 导入、兼容读写或旧查询回退，不复制旧验收事实作为重建数据。
- **BREAKING**：依赖核对后清除被替代的旧 Agent 控制器、表、入口、开关、无用脚本/文档和项目临时库；保留有用途的源码算法、测试及恢复记录。
- 重读邮件与 StatusMatch 官方资料，处理重建当天最新的 LoyaltyLobby 文章；LoyaltyLobby/GHA 的此前清理指令仅为一次性操作，不新增长期保留或禁采规则。
- 从最终正常网页完成只替换 ModelPort 的人工双视角验收，再使用经济型真实模型验收；先保证效果和正确性，再优化 token 与延迟。

## Capabilities

### New Capabilities

- `workflow-knowledge-production`: AIWorkflow 的来源、提取校验、统一发布及简报/完整图生产职责。
- `shared-knowledge-data-contract`: 单库逻辑分域、正式事实唯一性、版本证据、读写权限与清晰查询覆盖。
- `independent-agent-consumption`: 可替换模型、通用运行核心、独立工具、记忆与交付边界。
- `clean-rebuild-and-web-acceptance`: 有依据审计、停写清理、无旧数据兼容的空库重建、正常网页双视角及真实模型验收。

### Modified Capabilities

无现有已同步主规格作为修改基线。本 change 独立定义上述要求；旧 change 保持原样，不继承其任务完成度、问题编号或验收结论。

## Impact

涉及整个 JourneyPlus 仓库与本项目正常/临时数据库：AIWorkflow、知识模型和发布、Agent、产品页面/API、采集/调度、维护脚本、配置、测试与文档。物理表和文件变更须经本 change 的审计与映射确定，不按名称新旧盲删。

当前仅创建方案，不执行清理、真实采集、模型调用、Git 提交或外部部署。后续破坏性操作必须依据明确数据清单，用户真实会籍/会话/操作记录的处置不能从“旧知识清空”推断；源邮箱邮件不删除。恢复备份不是永久旧结构兼容方案。
