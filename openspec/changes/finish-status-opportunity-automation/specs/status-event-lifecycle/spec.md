## ADDED Requirements

### Requirement: 活动时效只使用最小窗口字段
系统 SHALL 为事件保存可空的申请开始时间、申请截止时间、生命周期状态和软归档时间，并在 FactSet 中增加有证据的申请开始字段且复用现有截止时间字段。事件查询时间 SHALL 统一规范化到北京时间 `Asia/Shanghai`，原始时间文字 SHALL 保留在 EventHint、FactSet 与分析记录中。系统 SHALL NOT 为本变更新增合作方、地区、入口指纹或活动系列 ID 等事件身份字段。

#### Scenario: 来源明确给出申请窗口
- **WHEN** 已关联材料明确给出申请开始和截止时间
- **THEN** FactSet 保存两个有证据的事实，事件保存可用于查询的规范化窗口

#### Scenario: 来源没有开始时间
- **WHEN** 材料只明确给出截止时间
- **THEN** 申请开始时间保持为空，系统不得补猜

### Requirement: 生命周期必须与审核状态分离
系统 MUST 使用 `UPCOMING`、`ACTIVE`、`EXPIRED` 或 `UNKNOWN` 表示活动生命周期，并继续使用现有 `StatusEvent.status` 表示人工审核状态。两个状态 MUST 能独立变化。

#### Scenario: 待复核但仍有效的活动
- **WHEN** 一个事件的关系需要复核且当前处于已知申请窗口内
- **THEN** 它可以同时具有审核状态 `NEEDS_REVIEW` 和生命周期 `ACTIVE`

### Requirement: 生命周期必须由当前时间和证据窗口确定
系统 MUST 将开始时间晚于当前时间的事件标为 `UPCOMING`，将截止时间已知且尚未超过的事件标为 `ACTIVE`，将截止时间已过的事件标为 `EXPIRED`，并将截止时间缺失、窗口矛盾或不能可靠规范化的事件标为 `UNKNOWN`。

#### Scenario: 已知截止时间尚未到达
- **WHEN** 事件没有未来开始时间且当前时间未超过有证据的截止时间
- **THEN** 生命周期为 `ACTIVE`

#### Scenario: 没有可靠截止时间
- **WHEN** 当前 FactSet 无法提供可靠截止时间
- **THEN** 生命周期为 `UNKNOWN`，系统不得凭文章发布时间把它判为过期

#### Scenario: 只有日期没有时刻
- **WHEN** 来源只提供截止日期
- **THEN** 系统统一按北京时间当日 `23:59:59.999999` 作为截止边界；仅日期的开始时间按北京时间当日 `00:00:00` 规范化

#### Scenario: 来源给出带时区的时刻
- **WHEN** 来源给出带明确 UTC 偏移的申请开始或截止时刻
- **THEN** 系统把该时刻转换为北京时间保存和比较；无时区的明确时刻按北京时间解释

### Requirement: 过期必须软归档且自动不可恢复
生命周期推进 MUST 在事件变为 `EXPIRED` 时设置软归档时间，但 MUST 保留事件、正文、证据、事实、简报和修订。自动候选召回 MUST 排除已归档、生命周期为 `EXPIRED`，以及可靠截止时间已经过去但生命周期状态尚未推进的事件。自动事实刷新和生命周期推进 MUST NOT 清空归档时间或恢复已归档事件；确需纠正历史归档时只能通过显式人工复核操作处理。

#### Scenario: 截止时间到达
- **WHEN** 当前时间超过事件的可靠截止时间
- **THEN** 事件变为 `EXPIRED` 并软归档，历史数据仍可查询

#### Scenario: 生命周期状态尚未推进但截止时间已过
- **WHEN** 事件仍保存为 `ACTIVE` 或 `UNKNOWN`，但可靠截止时间已经早于当前北京时间
- **THEN** 自动候选召回仍排除该事件，不等待下一轮生命周期推进

#### Scenario: 已归档活动随后出现延期
- **WHEN** 新材料在旧活动超过截止时间或归档后才写明延期、重开或新的截止时间
- **THEN** 系统创建新事件，旧事件保持 `EXPIRED` 和原归档时间，不自动恢复

#### Scenario: 人工纠正错误归档
- **WHEN** 操作员通过显式人工复核动作选择有证据的新截止时间并确认旧归档属于数据错误
- **THEN** 系统可以重新计算生命周期并清空归档时间，同时保留复核决定和旧事实历史

### Requirement: 新一期活动必须与旧活动分离
系统 MUST 将非重叠的新申请窗口创建为新事件。旧事件一旦超过截止时间或归档，后续明确延期、连续重开或新一期材料也 MUST 创建新事件，并保持旧事件的生命周期和归档历史。

#### Scenario: 下一年度重新开放
- **WHEN** 已过期活动之后出现新的年度或独立申请窗口，材料没有说明它是原活动延期
- **THEN** 系统创建新事件，不修改旧事件的截止时间或归档状态

#### Scenario: 截止前明确延期
- **WHEN** 原活动尚未超过截止时间且未归档，新材料明确延长同一活动截止时间并提供更晚日期
- **THEN** 系统可以将材料作为 `UPDATE_OF` 关联同一事件、更新截止时间并保留旧事实版本
