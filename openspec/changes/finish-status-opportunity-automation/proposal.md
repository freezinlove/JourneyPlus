## Why

会籍机会纵向流水线已经能够手工采集、分类、聚合、整理事实并生成简报，但第一期冻结金标尚未真正运行，事件也没有独立的活动时效状态，每日运行缺少可靠的幂等、隔离和观察边界。需要先用现有金标发现并修正分类与聚合问题，再在不扩大事件字段的前提下补齐活动窗口、生命周期和每日自动运行，才能完成会籍主题的稳定自动化交付。后续 `simplify-generic-article-pipeline` 已进一步收缩产品范围，因此本变更的最终自动运行边界以当前实现为准：LoyaltyLobby 是唯一通用公开来源，StatusMatch/GetStatus Gmail 只进入专用项目链路。

## What Changes

- 建立第一期冻结金标的真实模型运行、缓存续跑、分类与事件分组报告；本期金标不评测活动时效，且金标基线和必要调整完成前不得开始时效实现。
- 从旧来源集合中移除 StatusMatcher 和 Frequent Flyer Bonuses 会籍汇总列表的注册、CLI 入口、生产适配能力及专属规则；来源注册表保留 FFB 博客 Feed、AwardWallet、StatusMatch/GetStatus Gmail、LoyaltyLobby、Frequent Miler 和很旅行的适配器与历史兼容，但当前只启用 LoyaltyLobby 通用链路和 StatusMatch/GetStatus Gmail 专用链路，其他四个公开来源保持 `enabled=false`、`automatic_scheduling=false`。
- 移除没有独立业务价值的 `opportunity_type`；使用最小的 `program / target_status / summary`、来源权威项目名与完整材料判断活动关系，后续只新增可空的申请开始和截止窗口，不新增合作方、地区、入口指纹等事件身份字段。
- 为当时的 V1 事件链路明确同活动跨文章聚合、延期作为更新、同品牌不同活动与不同时期新活动拆分，以及不确定关系保守分开并进入复核的行为；这些结果保留用于历史审计和回滚，当前 LoyaltyLobby V2 不再执行跨文章关系判断。
- 在金标阶段完成后增加与审核状态独立的 `UPCOMING / ACTIVE / EXPIRED / UNKNOWN` 生命周期；过期事件软归档后退出自动候选池且不得自动恢复。
- 为当前两个启用来源配置一天采集周期，增加单轮调度、北京时间自然日幂等、数据库互斥、失败隔离、处理积压、生命周期推进和运行状态报告；已关闭来源不得被自动采集或送入当前通用处理。
- 为两个启用来源增加持久化增量发现边界：LoyaltyLobby 仅在首次升级运行中分页追赶北京时间 2026-08-24 全天之后的未扫文章，成功后改为读到上次 Feed GUID 即停止；Gmail 首次或 History 过期时进行 message ID 全量对账，正常运行只消费上次 Gmail History ID 之后新增或后加标签的邮件。游标只在安全完成本批后推进。
- 使用邮箱中运行时全部符合标签和专用别名条件的 StatusMatch 邮件完成只读真实联调和幂等验证；2026-08-23 首次技术验证时为四封，删除注册/验证干扰邮件后的正式重建集合为两封。邮件中的文字链接、按钮和仅图片可点击链接均须解析；跟踪链接在本地解包，不访问含私人跟踪参数的中转地址。系统只保留有业务价值且去重后的项目专属 `*.statusmatch.com` 域名，并分别读取活动首页和同域 `/faq`，将公开页面作为可独立增量更新的详细事实材料。真实邮件正文不得进入仓库测试夹具或金标，GetStatus 在收到真实邮件后补充联调但不阻塞首期上线。
- 在安装外部定时任务前，对当前 Gmail 发现的公开 StatusMatch 首页与 `/faq` 完成逐页审核，并用受控真实 LoyaltyLobby 批次验证当前通用 V2 的标题筛选、路由互斥、事实证据、简报、调用预算和幂等。旧的固定两日窗口入口只保留为 LoyaltyLobby 历史回放工具，不再要求对已关闭的四个公开来源执行全量初始化。
- 初始化审核发现同一证据的模型改写会被误判为冲突，且同一活动的多个资格、地区、价格和入口无法用单值事实表达；增加稳定事实复用和有证据的申请路径列表，缺失地域保持未知。Gmail 邮件始终只用于发现并去重项目链接，不创建业务事件、不进入事实与简报，也不成为引用对象；只有展开后的公开活动首页与 `/faq` 提供事实证据。FAQ 的原项目/原等级到目标等级长表逐单元确定性写入结构化 `status_mappings`，历史地区/费用表排除。简报不得引用未知事实，也不得用“以活动页为准”等通用兜底文字代替已经读取的具体页面信息。经用户确认后，先备份并仅清理可从原始文档重建的派生业务数据，再用当前规则重新生成，不删除来源、邮件或原始正文。
- 通过第一期金标、当前两个启用来源的真实端到端检查、外部每日调度安装及同日幂等与来源隔离验证后完成本变更；后续每日运行观察属于常规运维，不再作为本变更的完成门槛。

## Capabilities

### New Capabilities

- `gold-baseline-runtime`: 运行第一期冻结金标、缓存真实模型输出、报告文档分类和事件分组指标，并以结果作为后续时效开发的阶段门。
- `status-event-lifecycle`: 从有证据的活动开始/截止窗口计算独立生命周期、软归档过期活动，只允许截止前明确延期更新同一事件，并把过期后的延期或重开拆成新事件。
- `daily-source-automation`: 对 LoyaltyLobby 通用链路和 StatusMatch/GetStatus Gmail 专用链路执行一天采集、处理、生命周期推进、故障隔离、受控验证和运行状态报告，并排除已关闭来源。

### Modified Capabilities

- `status-opportunity-pipeline`: 从正式来源中移除 StatusMatcher 与 FFB 会籍汇总列表，并将 Gmail 项目链接的活动首页和 `/faq` 纳入完整材料；本变更保留的 V1 事件语义用于历史兼容，当前 LoyaltyLobby 通用文章行为由 `simplify-generic-article-pipeline` 的文章级 V2 规格约束。
- `event-scoped-status-processing`: 对明确判定为活动延期的 `UPDATE_OF` 允许截止时间形成新的当前事实版本，同时保留旧事实历史；普通来源分歧仍按冲突处理。

## Impact

- 影响金标评测 CLI、AI 运行缓存和评测报告。
- 影响来源注册表、来源工厂、CLI、StatusMatcher/FFB 汇总适配代码、Gmail 链接发现及其测试和说明文档。
- 影响历史 V1 的 `EventHint`、`StatusEvent`、`FactSet`、事件候选召回、关系判断、聚合、迁移和复核数据展示；当前 LoyaltyLobby V2 使用独立的文章分析与机会记录。
- 影响 FactSet 的 JSON Schema、事实协调和简报事实引用；不增加数据库列，旧派生 FactSet 在备份后通过受控重建退出当前业务状态。
- 新增每日单轮编排 CLI、运行互斥/幂等、来源运行状态、LoyaltyLobby 受控验证和生命周期推进。
- PostgreSQL 仍是自动运行目标；模型、现有正文、证据、事实和简报历史必须保留并可重放。
