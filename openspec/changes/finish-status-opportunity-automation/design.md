## Context

流水线已经完成第一期冻结金标、活动窗口、生命周期、每日单轮编排、StatusMatch Gmail 公开详情页展开和真实材料验证。本变更最初以六组注册来源为自动化候选；后续 `simplify-generic-article-pipeline` 明确把当前通用公开来源收缩为 `loyaltylobby_feed`，并让 `status_services_mail` 继续只服务 StatusMatch 专用项目链路。FFB Feed、AwardWallet、Frequent Miler 和很旅行保留适配器、注册记录、原文与历史结果，但当前保持关闭。

本变更的阶段顺序仍然有效：先移除已放弃来源并运行第一期金标，再实现活动时效和每日单轮。最终上线阶段以当前两条启用链路为准；外部定时任务只有在 Gmail 公开详情页审核、受控真实 LoyaltyLobby 批次验证和完整回归通过后才能安装。现有冻结金标不得为了覆盖时效而修改或重建。旧 V1 的跨文章事件数据继续保留审计，当前 LoyaltyLobby 新文档使用文章级 V2，不再自动进入 V1 关系与事实协调。

## Goals / Non-Goals

**Goals:**

- 用当前真实模型和生产提示词运行第一期冻结金标，得到可续跑、可比较的分类和事件分组基线。
- 在不增加多余活动身份字段的前提下完成并保留 V1 的同活动聚合和跨期拆分回归；当前 LoyaltyLobby V2 改为文章级独立记录，不执行跨文章自动聚合。
- 从有证据的申请开始和截止时间计算独立生命周期；过期活动软归档后退出自动候选池且不得自动恢复。
- 让 LoyaltyLobby 通用链路和 StatusMatch/GetStatus Gmail 专用链路以一天周期自动采集、处理并报告故障；其他四个注册公开来源保持关闭且不进入当前通用处理。
- 用当前邮箱中全部符合标签和专用别名条件的 StatusMatch 邮件完成真实只读联调，展开文字、按钮和图片活动入口，本地解包跟踪链接并读取去重项目的活动首页与 `/faq`，同时不把私人邮件正文或跟踪参数提交到仓库；2026-08-23 首次技术验证时共有四封，删除注册/验证干扰邮件后的正式重建集合为两封。
- 在安装外部调度前先审核 Gmail 展开的详细活动页，再用受控真实 LoyaltyLobby 批次验证当前文章级 V2；旧固定两日窗口只作为 LoyaltyLobby 历史回放入口保留，不再构成四个已关闭来源的初始化要求。
- 达到会籍主题可以低人工介入持续运行的状态。

**Non-Goals:**

- 不重抓或覆盖第一期既有冻结正文，不制作包含时效字段的新金标阶段；允许保留 v1、v2 的同时发布只修正已确认标签和活动归并的递增数据集修订。
- 不新增合作方、地区、申请入口指纹、活动系列 ID 等事件身份列。
- 不引入向量数据库、微服务、复杂常驻调度平台或跨主题通用事件模型。
- 不等待 GetStatus 发来真实邮件；收到后再补充联调。
- 不恢复 FFB Feed、AwardWallet、Frequent Miler 或很旅行的自动调度；重新开放任一来源必须另行完成来源和当前通用链路验收。
- 不在本变更中实现买分、转分或其他新主题。

## Decisions

### 1. 第一阶段只评测第一期金标，时效有硬性阶段门

金标运行器先校验冻结清单和 SHA-256，再按固定顺序读取65份规范正文，调用当前 `StatusRelevanceAnalyzer`、候选召回、关系判断和聚合逻辑。每份模型输出按数据集哈希、案例/文档键、模型配置、提示词和 Schema 版本缓存；中断后只补跑缺失项。真实基线使用隔离的评测数据库，不得写入正式业务数据。

报告包含文档标签混淆矩阵、Precision/Recall/F1、文档内活动数量、ID 无关的 pairwise 事件分组指标和逐项错误。数据库 UUID 只用于一次运行内部聚合，评测通过“两个活动提示是否落在同一预测事件”比较人工 `event_key`，不要求预测 UUID 等于人工键。

第一期金标明确不评测 `application_start_at`、`application_deadline_at` 或生命周期。只有基线已保存、错误已分类、必要提示词或聚合调整已回归验证后，时效任务才可开始。替代方案是先补时效再跑金标，但这会同时改变分类、关系和生命周期，难以定位错误。

### 2. 删除机会类型，活动身份只使用最小语义并在下一阶段增加时间窗口

本节描述本变更完成的 V1 事件模型和继续保留的历史行为。后续 LoyaltyLobby 文章级 V2 不调用这里的候选召回或关系模型；StatusMatch 专用项目链路仍可复用适用的最小字段、窗口与生命周期规则。

`opportunity_type` 的多个写法都只是会籍机会的机制描述，既不参与用户需要的文档分类，也不应决定活动身份。当前本地数据库只有少量早期事件，因此从 `EventHint`、`StatusEvent`、提示词、召回、复核和事实上下文中删除该字段，并用迁移删除数据库列。事件继续只以 `program`、`target_status`、`summary`、来源权威项目名和关联全文作为语义上下文；下一阶段只新增：

- `EventHint.application_start` 和 `EventHint.application_deadline` 可空提示；
- `FactSet.application_start` 证据字段，复用现有 `deadline`；
- `StatusEvent.application_start_at` 与 `application_deadline_at` 可空时间；
- `StatusEvent.lifecycle_status` 与 `archived_at`。

`EventHint` 保留来源中出现的原始时间文字，`FactSet` 的非空时间仍必须绑定正文证据；事件查询字段统一规范化到北京时间 `Asia/Shanghai`。仅日期的开始时间按北京时间当日 `00:00:00`，仅日期的截止时间按北京时间当日 `23:59:59.999999`。带时区的明确时刻转换为北京时间，无时区的明确时刻按北京时间解释；无法可靠解析时事件时间保持为空并进入 `UNKNOWN`，不猜测其他地区时区。

不增加合作方、地区、入口指纹等事件身份字段。申请窗口是强判别信息但不是唯一键：相同或重叠窗口仍可能存在不同企业专场、地区专场或普通匹配；缺少窗口也不能自动判为新活动。

候选召回允许项目全称、简称、名称包含和显著词重叠，例如 Kenya Airways 与 Kenya Airways Asante Rewards、Alaska Airlines 与 Alaska Airlines Atmos Rewards、Flying Blue 与 Air France KLM Flying Blue；召回只负责把可能候选交给关系模型，不能直接合并。FFB 会籍汇总列表不再作为来源，也不再提供权威项目名覆盖或专属候选过滤。

活动提示按现实活动而不是档位或措辞拆分：同一活动的多个目标等级、价格档和映射只输出一个提示，同一合作的双向路径仍是一项活动，主体活动中顺带给出的替代链接不另建活动。不同目标忠诚度项目且具有独立行动入口时必须拆成不同活动，即使其中一个会籍被当作另一个活动的资格来源。限时奖励可用于定级的精英房晚或定级积分属于会籍机会；旅行预订、旅行顾问或旅行会员平台如果通过具体活动直接授予或升级到明确命名的持续精英等级，也属于会籍机会。普通奖励积分、房券和折扣券不属于；名称中只有会员、会籍、Plus、Pass、Club 或 Card 的普通付费产品也不自动算会籍机会，如果购买结果只是会员资格、券、折扣或权益包而没有明确精英等级或定级进度，仍应排除。个人通过客服邮箱申请成功、但只有第三方数据点或个人结果，没有官方活动页或可确认群体条款的材料只证明个案，不作为公开会籍机会；对同时具有邮箱、个人申请表述、第三方数据源且没有其他外部官方入口的正判应用确定性公开性守卫，避免同一材料随模型采样波动。两项 IHG 双倍精英房晚活动因适用对象、上限和窗口不同保持独立；雅高混合文章只保留赠送等级房晚与 Kenya Airways 匹配两个会籍活动，不提取五折房券。用户确认 iPrefer 混合游记在本期视为低价值攻略并标为 `NONE`。Flying Blue 英国 BA Club 入口与通用入口指向同一现实活动时合并；正文顺带提到 Vietnam Airlines 的现有样本不另作本轮修正。

候选召回除项目名称与摘要外，可以在运行时从新材料和候选证据中提取行动链接域名及路径作为临时信号，用于 `马来西亚航空` 与 `Malaysia Airlines Enrich` 等跨语言材料。普通链接只用于召回，不得新增为事件字段或直接触发合并。完全相同的项目专属 `*.statusmatch.com` 子域是更强的关系信号：系统用子域项目名或该链接的非通用锚文本把链接归属到具体活动；当子域分别与新提示和唯一候选的项目身份相符、没有同页其他活动串线且没有已知的非重叠活动窗口时，关系层可以确定性返回 `SAME_EVENT`。这使 `[马来西亚航空](https://enrich.statusmatch.com/)` 即使模型只输出中文项目名也能与 `Malaysia Airlines Enrich` 关联；`/ba/`、根路径、查询参数和地区入口差异本身不构成拆分依据。不同项目子域必须保持分离；后续时间窗口阶段中，非重叠的新一期窗口优先于子域复用并创建新事件。

关系判断遵循：同一现实活动的多篇报道为 `SAME_EVENT`；候选事件尚未超过原截止时间且未归档时，同活动明确延期或资格/价格更新为 `UPDATE_OF`；非重叠的新一期且没有明确延期语义为 `DIFFERENT_EVENT`；同品牌同期不同机制仍为 `DIFFERENT_EVENT`；无法确认时保持独立并进入复核。过期或已归档事件不进入自动候选池，即使后来材料写有延期或重开，也创建新事件并保留旧事件归档。`RelationshipResult` 增加布尔字段 `deadline_extension`，只有正文明确说明截止时间延期、候选仍未过期且关系为 `UPDATE_OF` 时才允许为 `true`；普通规则、价格或资格更新即使属于 `UPDATE_OF` 也保持 `false`。新证据加入后刷新事件当前摘要和搜索文本，避免首篇材料信息不足永久降低后续召回。

同一命名项目和相同授予机制下，仅面向国家或群体不同、使用不同注册记录或联盟链接，不足以证明是不同活动。例如 Best Western Service Rewards 对美国和加拿大军人的同一 Gold 直授应聚合；只有材料明确表明机制独立或后续申请窗口属于不同期次时才拆分。

### 3. 明确延期可以推进当前截止时间，普通分歧仍是冲突

本节的跨材料事实协调属于 V1 事件与 StatusMatch 专用项目的兼容规则，不适用于当前 LoyaltyLobby 文章级 V2 的独立事实快照。

现有事实协调遇到不同已知值会产生冲突。时间字段增加一个窄例外：候选事件尚未超过原截止时间且未归档，新材料已被关系阶段判为 `UPDATE_OF`、正文明确说明延期并提供更晚截止时间时，创建新的 FactSet 版本并把更晚截止时间作为当前值，旧值仍保留在旧 FactSet 和事件修订中。若只是两个来源给出不同日期、没有明确延期语义，继续标记冲突并进入复核。活动过期归档后不再召回，因此过期后出现的延期或重开材料不会进入旧事件的事实协调。

这样可以自动处理常见延期，又不把任意日期差异静默覆盖。开始时间改变、截止时间提前或矛盾窗口默认不自动覆盖。

初始化原文审核补充以下事实稳定规则：

- 若候选已知值与当前值文字不同，但候选没有引用当前字段之外的新文档证据，则这只是同一证据的重新组织，保留当前事实，不创建新 FactSet 或冲突；需要纠正旧提取时必须使用新证据、显式复核或受控派生数据重建。
- 同一 StatusMatch 项目的首页概述与 `/faq` 细化条件能够同时成立时，FAQ 作为对首页的补充而不是冲突；只有相同作用域内互相排斥的具体值才保留冲突。真实冲突必须保存全部候选值和双方证据、把事件设为 `NEEDS_REVIEW`，但不得阻止中文简报产生；简报必须显示存在冲突及其候选信息，不得替用户静默裁决。
- 同一现实活动可以存在多条 `application_routes`，每条路径将简短作用域、资格、地区、价格和申请链接与证据绑定。不同国家、群体、资格来源、条件价格或合法入口属于不同路径，不互相构成冲突；只有同一路径内部的互斥事实才进入冲突复核。共同适用于全部路径的值仍可保留在原单值字段，路径间不同的单值字段保持未知而不是制造冲突。
- 来源没有明确地域限制时 `region` 和路径地域保持未知，禁止把“未提及地区”推断为“全球”或“无地域限制”。
- StatusMatch/GetStatus 邮件始终是发现材料：正文只用于本地发现、解包和去重项目链接，无论是否成功取得有用链接，都不创建活动提示或事件，不进入 EventEvidence、FactSet、简报或 `source_links`。同域活动首页和 `/faq` 自身携带项目主机强信号并作为公开业务材料处理；没有取得公开详情页的邮件只保留审计记录，不降级为弱事实材料。
- Gmail 初始化每次失败重试都使用新的采集身份重新查询当前邮箱，并以本次发现的邮件和公开页文档 ID 精确限定处理与积压；全局自动积压只选择每个来源条目的最新文档版本。邮件专用链接清洗不得作用于公开页，清洗解析版本变化通过 `(source_item_id, raw_hash, parser_version)` 新建可审计文档版本，完整工作流的幂等键包含分类、关系、事实和简报版本。
- StatusMatch FAQ 中的会籍对应表由确定性 HTML 表格解析器逐单元生成 `status_mappings`，保存原项目、原等级列表、目标等级、可用性、脚注条件和 FAQ 证据；`Recently ended offers` 下的历史地区/费用表排除，但其后的会籍对应表不排除。模型只整理正文事实与简报，不负责复制可能包含数百单元的长表。
- 事实层必须清空把通用“条款适用、请查看活动页”误作具体资格的候选，不得把该类文字转存为业务 `caveats`，且不得把项目名本身重复当作目标等级。简报层必须省略值为空的资格、费用、地域、截止时间等字段，也不得把“未明确”或“以活动页为准”作为替代陈述；通用兜底校验只匹配明确的页面/官网查看或为准措辞，以及作为完整独立分句出现的“条款和费用适用”等空话，不得把“费用不同”或“条件适用于具体人群”等事实陈述误伤；`source_links` 只能从公开事实证据来源白名单选择而不得使用 Gmail 邮件或申请入口，并在重试时接收前一次事实引用或来源链接校验的针对性纠错原因，而不是重复相同无效输出。
- 事实整理的模型生成、Schema、证据归属、地域守卫和协调失败必须按尝试记录安全诊断，只保存阶段、异常类型、简短错误、事件与允许的文档标识数量，不保存候选模型正文或私人来源正文；简报 grounding 校验 MAY 额外保存规则 ID、声明位置、事实键、正则起止词和不超过 160 字符的生成文案命中片段，用于区分模型违规与正则误伤，但不得保存完整候选或任何来源正文；确定性重试必须收到前一次失败原因和证据边界纠错提示。

`application_routes` 是 FactSet JSON Schema 的新增结构，不是事件身份字段，也不增加数据库列。初始化失败后的重建先保存 PostgreSQL 可恢复备份，只删除分析运行、事件、证据、修订、事实、简报、任务与初始化/自动运行状态等派生数据；`sources`、`source_items`、`document_versions`、`collection_runs` 和 Gmail OAuth/原文全部保留。重建从现有原始文档执行，避免重新抓取和修改私人邮件。

### 4. 生命周期与审核状态完全独立

`StatusEvent.status` 继续表示 `DRAFT / NEEDS_REVIEW / CONFIRMED / MERGED` 等审核状态。新 `lifecycle_status` 只表示：

- 开始时间在未来：`UPCOMING`；
- 截止时间已知且当前未超过截止时间：`ACTIVE`；
- 截止时间已过：`EXPIRED`；
- 截止时间缺失、窗口矛盾或不能可靠规范化：`UNKNOWN`。

所有活动时间统一按北京时间 `Asia/Shanghai` 计算。只有日期的截止值按北京时间当日末计算，只有日期的开始值按北京时间当日开始计算；带明确时区的时刻先转换为北京时间，无时区的时刻按北京时间解释。原始时间文字和证据保留在 FactSet 与分析记录中，不增加日期精度列。无法可靠规范化时保持 `UNKNOWN`。

生命周期单轮推进把 `EXPIRED` 事件同时设置 `archived_at`，但不删除事件、正文、证据、事实、简报或修订。候选召回必须同时排除 `archived_at` 非空、生命周期为 `EXPIRED`，以及可靠截止时间已过但生命周期尚未来得及推进的事件。明确延期只有在原截止时间到达前才更新同一事件；活动一旦归档，自动事实刷新和生命周期推进不得清空 `archived_at` 或恢复活动，过期后出现的延期、重开或新一期材料一律创建新事件。确需纠正历史归档时，只能通过显式人工复核操作处理。

### 5. StatusMatcher 与 FFB 汇总列表完全退出正式产品范围

从注册表、来源工厂和 CLI 可选来源中移除 StatusMatcher 与 `ffb_status_match_catalog`，清理适配器、测试、固定样本、FFB 权威项目提示词和专属初始化入口。若数据库已存在对应来源种子，迁移或启动清理必须使其不再启用或调度；已有关联历史原文时不得级联删除。

移除立即实施，不依赖金标或时效阶段。来源注册表继续保留 FFB Feed、AwardWallet、StatusMatch/GetStatus Gmail、LoyaltyLobby、Frequent Miler 和很旅行六组适配器与历史兼容；当前运行范围只启用 LoyaltyLobby 和 StatusMatch/GetStatus Gmail，其他四个公开来源保持 `enabled=false`、`automatic_scheduling=false`。

### 6. 当前两个来源统一一天周期，其他来源保持关闭

当前把 `loyaltylobby_feed` 和 `status_services_mail` 配置为一天周期并允许自动选择；前者进入通用文章 V2，后者只进入 StatusMatch 专用项目链路。FFB Feed、AwardWallet、Frequent Miler 和很旅行保留一天周期元数据以便未来重新验收，但保持禁用且不得被自动选择。实现一个可由外部 cron/系统定时任务调用的单轮命令，而不是引入常驻调度框架。每个周期按顺序：获取数据库互斥租约、选取到期且启用的来源、逐来源采集、处理新增文档直到本轮上限、推进生命周期、保存摘要并释放租约。

周期使用 `Asia/Shanghai` 自然日分桶的幂等键；同一北京时间日期重复触发时复用已经成功的来源运行，失败来源仍可安全重试，上一轮仍运行时新调用安全退出。两个启用来源的失败互相隔离；单轮具有来源条目数、待处理文档数和模型调用上限。代码中的来源自动标志与外部定时任务分离：当前两条链路可以被 `run-daily` 选择，但只有受控验证通过后才安装外部每日调用；关闭来源即使有历史积压也不得被处理或计入当前积压。

来源发现位置持久化在 `source_automation_states.discovery_cursor`，但两种来源使用各自的稳定边界。LoyaltyLobby 没有游标时，以 `Asia/Shanghai` 的 2026-08-24 整个自然日作为已完成基线，从最新页向旧页扫描，只返回其后的文章；成功后保存本次连续处理到的 Feed GUID。后续扫描从最新页开始，遇到保存的 GUID 即停止，因此文章总量增加不会导致每天回扫到 8 月 24 日。为兼容单轮条目上限，新增 Feed 项按从旧到新交给采集器，部分成功时只把游标推进到实际处理的最新条目；边界消失时才允许安全回退到日期基线和内容幂等。

Gmail 使用 `users.history.list` 的持久化 History ID 读取 `messageAdded` 与 `labelAdded` 变化。首次部署没有游标，或 Gmail 返回历史游标过期时，先记录当前 profile History ID，再对当前标签和专用别名做全量 message ID 对账；已有成功 message ID 不重新下载正文。正常增量批次只读取 History 返回的候选，再以当前标签和收件别名校验。History 游标只有整批发现与采集安全完成后才写入数据库；发现、正文或非托管材料失败时保留旧游标重试，单轮上限不足以容纳整批时明确失败而不静默跳过邮件。

### 7. Gmail 发现项目并展开公开详情页，仓库只保留合成测试

当前只读适配器已能发现并取得发送到专用别名且带 `statusmatch` 标签的 StatusMatch HTML 邮件；2026-08-23 首次验证时为四封，删除注册/验证干扰邮件后为两封。旧路径优先选择纯文本且 HTML 清洗会丢掉仅图片按钮的链接。新实现优先保存 HTML 原文，从所有锚点读取 `href`，用图片 `alt` 补足无文字标签；受支持的 `email.mail.statusmatch.com/c/...` 压缩跟踪载荷及其嵌套通用点击页均在本地递归解包，任何含用户或点击标识的中转 URL 都不得被请求。

有用链接严格限定为 HTTPS、单一项目专属 `*.statusmatch.com` 子域。系统排除 `www`、`email`、`mail` 等通用/跟踪主机以及社交、退订、条款和宣传链接，并按项目主机去重。每个项目产生两个稳定公开页面条目：规范化活动首页和同域 `/faq`。两页每天随 Gmail 来源重新检查，原始哈希未变化时复用旧版本，变化时保留历史并建立新版本。邮件原文仍以受限快照独立保存，只用于审计和以后重新发现链接，并被确定性标为非业务材料；公开页面按允许快照保存，作为资格映射、价格、窗口、有效期、申请入口与注意事项的唯一 Gmail 派生事实来源。活动首页与 FAQ 共享项目主机并聚合到同一活动，不因路径不同拆分。

实施阶段在本地 PostgreSQL 中验证当前全部符合条件邮件的首次入库、链接解包、页面读取、第二次采集幂等、分类、事件聚合、事实和简报；逐页人工回读真实公开原文。报告只记录消息数、项目数、阶段状态和匿名化结果，不保存邮件标题、正文、消息 ID 或跟踪参数到仓库。合成 Gmail 契约测试覆盖标签、别名、只读边界、无关链接过滤、重复链接、图片入口、跟踪解包和公开页面增量版本。

GetStatus 尚无真实邮件，不作为上线阻塞项。长期无人值守前必须确认 OAuth 刷新令牌不会因 Testing 状态周期失效，或把重新授权明确记录为运维限制。

### 8. Gmail 详情页与 LoyaltyLobby 受控验证

每日自动化代码和完整测试通过后、安装外部定时任务前，系统先对正式业务库执行受控验证。首先从当前合规 Gmail 原文重新发现项目域，对去重后的活动首页和 `/faq` 全量获取和处理，不使用邮件日期过滤，并逐页人工审核当前时效流水线形成的事件、事实、简报和生命周期。旧 FFB 汇总来源及当前关闭的四个公开来源只保留注册、适配器、原文与历史结果，不参与当前阶段门。

通用链路只使用真实 LoyaltyLobby 批次验证标题筛选、StatusMatch 精确链接路由互斥、正文标签、文档内机会、事实与逐字证据、简报、生命周期、调用预算和第二次运行幂等。当前验收基线采用 2026-08-24 的十篇真实文章批次；旧 `initialize-window` 的 2026-07-15 至 2026-08-22 固定两日窗口能力保留为 LoyaltyLobby 历史回放工具，但不再要求把全部窗口跑完，也不得扩展到已关闭来源。

受控批次处理完成后必须回读真实原文，逐项核对标题决策、文档标签、文档内机会数量、专用/通用路由、事实值与逐字证据、简报、生命周期和模型调用预算。发现模型或确定性逻辑错误、来源正文异常、无证据事实/简报、跨机会串线或尚未约定的产品边界时，当前批次报告问题并立即停止外部调度启用，直到用户作出规则和边界决定、相应修复与回归验证完成。

### 9. 本变更完成门槛

本变更完成前必须满足：第一期金标基线已运行并完成必要调整；LoyaltyLobby 和 StatusMatch/GetStatus Gmail 两条当前链路各自真实采集成功；当前全部合规 Gmail 邮件、去重活动首页与 `/faq` 完成幂等联调和逐页审核；受控真实 LoyaltyLobby V2 批次的标题筛选、路由、事实证据、简报、生命周期与零调用重跑通过；旧 V1 的关系和生命周期回归继续通过；完整测试与严格 OpenSpec 校验通过；外部每日调度已经安装，并完成默认来源集合、关闭来源隔离和同日重复触发幂等验证。

外部调度启用后的每日结果继续通过独立任务和 `automation-status` 进行常规运维观察，不再构成本变更的额外完成门槛。

不在基线运行前臆定新的固定模型质量阈值。基线报告和具体错误样本由用户确认是否存在阻塞性系统错误。

## Risks / Trade-offs

- [只有时间窗口不能区分同期不同活动] → 窗口不作唯一键，继续把现有语义和完整材料交给关系判断。
- [缺少开始或截止时间] → 使用 `UNKNOWN`，不猜测过期，也不阻止文档分类和事件聚合。
- [模型把新一期误判为延期] → 非重叠窗口默认偏向拆分；不确定关系保持独立并复核。
- [每日重新访问 StatusMatch 页面和 LoyaltyLobby 可能产生积压] → 页面与文章内容哈希精确去重、顺序执行并设置单轮上限；关闭来源的历史积压不进入当前统计或处理。
- [Gmail OAuth 令牌失效] → 运行状态暴露授权错误并隔离邮件来源，LoyaltyLobby 通用链路继续运行。
- [移除 StatusMatcher 与 FFB 汇总后历史来源记录残留] → 禁用来源记录，不级联删除已有原始历史；派生业务结果按已批准的重建边界退出当前状态。
- [第一期金标未覆盖时间] → 将其限制为分类和事件分组阶段门，时效使用独立的确定性测试与真实案例验证。

## Migration Plan

1. 立即移除 StatusMatcher 与 FFB 会籍汇总正式来源及相关代码、测试和文档，保留其他来源适配器和历史数据。
2. 实现金标运行器，校验并运行第一期 v1 基线；保留首轮报告，发布只含人工确认纠错的 v2 冻结修订，修正阻塞性分类或聚合错误并全量重跑比较。
3. 在阶段门通过后增加活动窗口、事实字段、事件关系语义和数据库迁移。
4. 增加生命周期计算、截止前延期、归档自动不可恢复、过期后新事件、跨期拆分和软归档，完成确定性测试。
5. 使用 LoyaltyLobby 和当前全部合规 Gmail 邮件完成 PostgreSQL 真实联调；本地解包有用链接并逐页审核项目首页与 `/faq`，其他四个公开来源保持关闭。
6. 增加单轮每日编排、互斥、幂等、上限、状态报告和受控验证入口；只允许 LoyaltyLobby 与 StatusMatch/GetStatus Gmail 被当前自动单轮选择。
7. 全量验证 Gmail 发现的去重项目首页与 `/faq`，再用受控真实 LoyaltyLobby V2 批次完成人工审核；任何问题或新边界立即暂停并等待用户决策。
8. 受控验证全部通过后安装外部每日调度，核对默认来源集合、关闭来源隔离和同日幂等，完成本变更；后续运行纳入常规运维观察。

回滚时先关闭 LoyaltyLobby 与 StatusMatch/GetStatus Gmail 的外部调度，再回退单轮命令；其他四个公开来源保持关闭。活动窗口列和历史数据保留。生命周期逻辑回滚不得恢复物理删除，软归档事件仍可人工查询。StatusMatcher 的移除不自动回滚，除非以后另立变更重新评估访问范围。
