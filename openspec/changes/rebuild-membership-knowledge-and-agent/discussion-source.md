**1．“未结构化”错误，已经复现并定位**

我用真实模型测试了两句话：

| 输入 | 实际结果 |
|---|---|
| “用我已有的会籍，推荐到天合联盟的路线，可以付费也可以挑战。” | 成功返回推荐 |
| “我有什么能匹配的？” | 返回结构化校验错误，无法继续 |

第二句失败的原因很明确：**系统要求模型必须先填写“目标项目或联盟”，即使模型下一步只是想追问你要什么目标。**

也就是说，产品要求“信息不足先问”，代码却要求“信息必须完整才能问”。日常自然表达很容易撞上这个问题。

此外还有几个放大故障的因素：

- 网络、超时、JSON 和字段校验错误都包装成类似的“结构化结果失败”，提示无法帮助定位。
- 没有一次受限的格式修复。
- 首轮失败没有可恢复的交互状态。
- 目录实际有 **376 个节点**，给模型的却只有前 **300 个**。
- 推荐结束后，再问“第二条呢”“能不能更便宜”，当前页面会开启新请求，上轮推荐上下文没有正常接续。

所以，问题不只是 Prompt 写得不好，更不是换个模型就能解决。

**2．Agent 与 AI Workflow 现在怎样交互**

目前的实际链路是：

```text
LoyaltyLobby 文章 / StatusMatch 项目页面
                  ↓
AI Workflow：提取事实、生成简报
                  ↓
数据库：映射、费用、条件、证据、版本、活动状态
                  ↓
统一会籍图 + 确定性候选查询
                  ↓
Agent：理解你的条件、选择路线、组织建议
                  ↓
页面展示
```

可以理解成：

- **Workflow 负责准备和更新资料。**
- **程序负责沿关系图找路、判断已实现的硬条件。**
- **Agent 负责结合你的取舍选择、解释和追问。**

它们通过同一个数据库和服务层协作，不是两个 AI 互相聊天。你提问时，Agent 也不会重新执行一遍采集。

Agent 会读取已保存的会籍；新会籍经你确认后保存。普通查询不会修改官方事实。你明确选择等待后，每日 Workflow 更新数据，再由程序检查有没有新候选，有命中才恢复 Agent。

**你觉得“数据串通很差”，有具体原因：底座里的细节到了 Agent 接口，被丢掉或压扁了。**

例如：

- 结构化价格被转成费用文本，价格适用于哪个等级、地区、申请方式，没有完整保留。
- 资格、地区提示、会籍有效期和细粒度证据，没有完整进入候选工具结果。
- 页面没有显示用了哪些持有会籍、哪些条件、数据更新时间，以及路线为什么被排除。

更严重的是，我复现了两个确定性错误：

1. **混合档位的 50／200 美元价格，函数直接取 50。**没有先确认哪档适用于当前路线，可能错误判断满足预算。
2. **两步路线，一步明确无挑战、另一步未知，整体被判为无挑战。**

另外，“高卡”目前没有可靠的等级对应数据支撑，仍让模型根据等级名称比较；候选查询还有默认 6 步、100 条的限制，却没有说明是否截断。不能把这些结果当成完整、严格验证后的全量可行方案。

**3．StatusMatcher 联网究竟有没有起作用**

这里要区分两个名字：

- **StatusMatch**：官方活动链路，进入 Workflow 和正式事实。
- **StatusMatcher**：社区申请报告，供 Agent 参考实际经验。

目前 StatusMatcher 并不是通用联网搜索。它的方式是：

1. 程序已经查出正式候选；
2. 服务端开关开启，而且用户表达了调查经验的意图；
3. 模型选择最多三条路线；
4. 程序通过固定别名表定位公司页面，每一步最多读取两页；
5. HTML 解析器提取报告，再把统计交给模型。

**我检查到当前配置是关闭的，所以按当前配置启动的正常推荐不会执行调查。**代码还没有强制显示“本次未调查”，这是盲盒感的重要来源。

本次对公司页做了 HEAD 连通性检查，返回 200；这只证明网址可达，不能证明完整调查链路正确。昨天的验收记录记载过受控成功，但不代表今天正式功能已经启用。

即使开启，目前也存在影响结论可信度的问题：

- 主要按来源项目名称匹配，没有真正核对双方等级。
- 不提取报告日期，无法落实近 12／24 个月筛选。
- 多步报告混在一起统计，没有按证据最弱的一步限制整条路线信号。
- 无法判断的报告也可能进入统计分母。
- 两页没找到案例，无法代表站内没有案例。

因此，不能只把开关打开就宣称“真实经验调查已经做好”。

**4．我建议怎样改，才能有值得展示的 Agent 价值**

我建议做四块，按顺序推进。

**第一块：先修到自然语言真正可用。**

把“不完整的理解草稿”和“可执行查询”分开。没有目标可以追问，只有正式查询时才要求字段完整。

同时补上目录检索、中文别名、一次格式修复、分类错误和短期上下文，让“第二条”“改成免费”“不接受挑战”能接着聊。模型失败时保留已有候选，用户能继续看、继续改。

**第二块：重新做好候选数据接口。**

每个申请步骤必须保留适用价格、资格、挑战、期限、有效期、证据和不确定项。费用和挑战逐步判断，再合并整条路线；适用性不明确就标未知。

工具返回的不只是路线，还要包含：

- 为什么符合；
- 为什么被排除；
- 只差哪个条件；
- 哪个事实未知；
- 数据截至何时；
- 是否查询到资源上限。

模型再从经过筛选、去重的候选中做主观取舍，并给每条推荐附上具体理由和事实引用。

**第三块：结果以“精选策略图＋对比”为核心。**

你要的不是整棵会籍树搬过来，这一点我赞同。默认应该展示：

- 一句明确结论；
- 一个首选、最多两个有明显不同取舍的备选；
- 只包含这些路线必要节点和步骤的关系图；
- 一张费用、挑战、步骤、期限、经验与取舍对比表；
- 下一步操作。

图从实际使用的已有会籍出发，首选高亮，共同节点合并。**如果两条推荐通过不同路径到同一目标，应保留两条路径**，不能复用现有匹配图“同一目标只画一条最短路径”的规则。

点击连线就能查看这一步的费用、条件和证据。调整后才可行的路线必须明确区别于当前可行路线。

这样图回答“怎么走”，对比表回答“为什么值得走”。Agent 的加工价值体现在筛选、比较和解释上。

**第四块：把调查状态和依据公开给用户。**

增加折叠的“本次依据”，显示：

> 使用了哪些会籍 → 按什么条件筛选 → 找到多少候选 → 为什么留下这些 → StatusMatcher 是否执行、查到什么。

这是可验证的操作记录，不需要展示模型思维过程，也不需要另造复杂监控平台。

StatusMatcher 在授权条件具备后，补齐按步骤、等级和时间筛选，再做真实端到端验收；未启用、失败和证据不足都明确显示，仍正常交付官方事实推荐。

**优先完成前三块，就能形成一个有说服力的演示版本。**没有必要先换 Agent 框架或推倒 Workflow；真正需要重做的是理解合约、数据投影和决策界面。

### 助手最终答复

懂，你的意思是：**用户每句话需要的信息都不一样，Agent 应该根据当前问题主动选择数据，而不是每次都走“解析会籍目标→查候选路线→推荐”这一条链。**

这会改变我们前面的设计重点。候选接口只是其中一个工具，更核心的是：**Agent 怎样判断当前需要知道什么，以及怎样从数据库拿到适量、准确的信息。**

我建议采用下面这套方案。

**一、让对话入口足够自由，让数据访问有明确边界**

用户输入不再必须带目标项目、联盟或持有会籍。

例如下面这些都是正常输入：

- “你好。”
- “Flying Blue 那个活动怎么申请？”
- “它接受匹配来的会籍吗？”
- “我现在有哪些路可以走？”
- “这两条哪个更稳？”
- “第二条太贵了，有别的吗？”
- “算了，我先等等。”

Agent 首先理解“用户现在想解决什么”，然后决定直接回答、补一个问题，还是读取数据。**只有执行某项查询时，才检查那项查询需要的参数是否齐全。**

这就不会再出现“用户只是问活动细节，却被要求先填写目标会籍”的问题。

允许所有自然语言输入，也意味着闲聊、表达不清、突然换话题都能被正常处理；涉及当前产品不具备的能力时，清楚说明即可，不应报结构化错误。

**二、不要把问题分进固定流程，而是提供几个可以组合的信息工具**

你举的情况很有代表性，但不适合写成一堆固定分支。例如：

> “这个活动贵不贵，条款允许我这种情况吗，成功案例多不多？”

同一句话就需要价格、条款和社区经验。Agent 应当能组合查询。

我建议先提供五项数据能力：

| 能力 | 解决的问题 | 默认返回什么 |
|---|---|---|
| 查找项目或活动 | 用户说的“那个活动”具体指什么 | 少量匹配项、名称、当前状态、简短描述 |
| 查看活动事实 | 多少钱、截止日期、申请条件是什么 | 与问题相关的结构化事实及证据引用 |
| 查阅来源内容 | FAQ／Terms 对某个细节究竟怎么说 | 相关章节或段落、上下文、来源与版本 |
| 查询和比较路径 | 我能到哪里、怎么走、有什么区别 | 经过筛选的路径概览、适用金额、关键限制 |
| 调查申请经验 | 哪个经验信号更好、别人遇到什么问题 | 对应申请步骤的样本统计、可比性和限制 |

这些能力可以复用底层查询，不需要各建一套数据库。

持有会籍保存、等待目标保存属于另外的**修改操作**，继续保留确认门，不能和这些读取工具混在一起。

**三、每次先拿“足够做下一步判断”的信息**

这是整个设计最重要的原则。

我建议将数据展开分成三层，但不要求每次依次走完。

**第一层：定位和概览。**

让 Agent 知道有哪些相关对象，以及它们大致是什么。

例如问匹配路径，先返回：

> 路线 R1：我的 A 会籍 → B Gold，一步；申请费 EUR 100；是否接受匹配获得的来源会籍待确认。  
> 路线 R2：我的 A 会籍 → C Gold → B Gold，两步；费用未完整确认；中间一步需要挑战。

此时不附整份 FAQ、全部价格档位和每条证据原文。

但**会影响选择的限制必须出现**，不能只显示“一步、100 欧元”，把资格未知藏起来。

**第二层：围绕当前问题补充细节。**

用户问：

> “R1 接受匹配来的会籍吗？”

Agent 就查 R1 对应的资格事实和 Terms 相关段落，不把 R2 的资料也带进来。

用户问：

> “第二步要完成什么挑战？”

就展开那一步的要求和时间限制。

**第三层：必要时查看更完整的来源。**

如果相关段落不足、存在例外或相互矛盾，继续读取该章节或关联 FAQ。

这样既能回答复杂问题，又不会一开始把所有东西都塞进去。这种“先给必要概览、再按需加载”的混合方式，也符合官方上下文工程实践；不过具体展开规则要按我们自己的业务设计。[参考：Anthropic 上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

**四、FAQ 和 Terms 应该按问题检索，不能整份固定注入**

你说“问活动细节时注入对应 FAQ／Terms”，方向是对的。我会进一步细化成：

1. 先确定活动及其当前来源版本。
2. 优先读取已有结构化事实。
3. 如果问题涉及事实字段未覆盖的细节、用户要求条款原文，或已有事实不足，就检索对应活动的 FAQ／Terms。
4. 返回相关问答、条款段落及必要的相邻上下文。
5. Agent 根据这些内容回答，并给出处。

例如：

> “匹配来的汉莎会籍能不能作为申请依据？”

不应该把整个 Terms 压成一个泛泛摘要。应找到与“来源会籍取得方式”有关的段落，保留其中的否定、例外和附加要求。

这里还要区分：

- **条款明确说不允许；**
- **当前检索范围内没找到说明；**
- **来源抓取不完整；**
- **两个来源说法有冲突。**

这四种情况不能都回答成“没有限制”。

数据库已有的当前页面版本应优先复用。是否需要重新联网刷新，是另一项可见操作，不能让用户以为每次读数据库都在实时查官网。

**五、路径浏览、路线推荐和经验比较，要用不同的数据精度**

这三种问题虽然相关，但不能使用同一个大数据包。

| 用户当前在做什么 | Agent 应该看到什么 |
|---|---|
| 看看能匹配到哪里 | 目标分组、路径、步骤数、费用状态、主要限制 |
| 挑选具体方案 | 少量有差异的候选、条件对比、资格与成本不确定性 |
| 准备研究某条路线 | 逐步申请要求、适用价格、FAQ／Terms 证据 |
| 比较实际申请经验 | 对应步骤的 StatusMatcher 观察结果 |

这里有一个重要调整：

**“一个首选＋最多两个备选”只适用于最终推荐，不应该限制用户探索。**

用户问“还有哪些酒店项目能匹配”，系统可以返回分组概览并支持继续展开。不能因为最终推荐最多三条，就永远只允许 Agent 看到三条。

同样，用户询问某个活动的申请经验时，可以先定位该活动和相应匹配方向，不必强迫他先完成一次完整的个性化推荐。如果来源等级等信息会影响案例可比性，再针对那一点追问。

用户说“哪个成功率更高”，可以作为调查经验的意图；在工具可用且授权条件满足时查询。最终表达仍应区分可比自报样本和真实审批概率。

**六、传给模型：以结构化数据为主，关键原文为辅**

我的建议很明确：

> **金额、状态、路径、计数和引用用结构化数据；细节条款用带来源的短文本。**

不需要在“全部 JSON”与“全部自然语言”之间二选一。

一个模型数据包可以理解为：

```text
当前问题：比较 R1、R2 哪条更适合不接受挑战的用户

结构化对比：
- R1：一步，EUR 100，挑战状态未知
- R2：两步，费用未知，明确需要挑战

相关来源片段：
- R1 / FAQ / 申请方式：……
- R1 / Terms / 附加要求：……

查询说明：
- R2 已违反用户不接受挑战的条件
- R1 尚不能确认无挑战
- 本次未调查 StatusMatcher
```

实际接口建议使用浅层 JSON，里面允许有这种可读的文本字段。

不把完整数据库记录、长 UUID、重复 URL、HTML 和无关简报发给模型。每条路线和证据使用短引用，程序负责映射回真实对象。

**JSON 只是承载形式。真正的优化来自选对信息、保留语义、去重和按需展开。**不同序列化格式的效果仍需要实测，不能先宣称 JSON 一定最优。[参考：Anthropic 工具设计](https://www.anthropic.com/engineering/writing-tools-for-agents)

**七、必须有一个很小的对话工作状态**

否则“它”“第二条”“还是免费优先”都接不上。

短期状态只需要记住：

- 当前讨论的活动或路线；
- 最近展示的候选及顺序；
- 用户确认的条件；
- 还没有确认的理解；
- 已读取的事实版本和证据引用；
- 当前待回答的问题。

用户说“第二条”，先从这个状态定位，不重新全库搜索。

用户换话题，就调整当前关注对象。进入闲聊时，不必把上一轮的全部路线和条款继续带入模型。

这不是保存完整聊天历史，而是保存继续完成当前讨论所需的最小状态。

**八、由程序控制数据大小，由 Agent 选择需要的信息**

我不建议完全让模型自由决定“我要多少数据”，也不建议程序把所有顺序写死。

职责可以这样分：

- **Agent 决定：**我要查价格、查条款、比较路线，还是调查经验。
- **程序决定：**允许查哪些对象、返回哪些必要字段、最多多少条、如何去重、是否已覆盖、哪些限制不能省略。

例如 Agent 请求查看活动详情，程序按问题提供价格或资格相关内容，而不是开放一个“返回全部对象”的通道。

查询被截断时必须说明还有内容未查看；有关键条件尚未展开时，不允许模型直接给出确定结论。

为了控制延迟，相互关联的信息尽量批量取得。比如“展开这两条路线的价格和资格”，一次完成，不让模型先查价格、再查资格、再查来源，来回调用很多次。

**九、用户能看见“这次回答用了什么”**

每次结果旁边可以有一个很轻的依据区域：

> 已读取：Flying Blue 当前活动事实、FAQ 相关问答、Terms 资格章节。  
> 数据更新于：……  
> 未进行：StatusMatcher 调查。

或者：

> 已按你持有的两张会籍查询；展示三个目标分组；费用未知的路线已标注。

不需要把内部技术字段展示出来，但要让用户知道回答依据、覆盖范围以及尚未确认的内容。

**我建议我们围绕这套结构继续设计：自由对话入口、少量可组合工具、分层数据展开、短期关注状态、程序控制输入预算。**

这样，候选接口不会被做成一个越来越庞大的“万能返回对象”。它只是 Agent 在讨论路径时使用的一种视图；讨论条款、经验或闲聊时，系统会选择完全不同、且与问题相称的数据。

- 申请入口；

**“申请方案”是活动里的一个申请步骤；“匹配路线”是程序把多个步骤连接起来的结果。**这两个概念明确分开。

不按来源×目标×地区×价格把所有组合机械展开成大量记录。共用条件在方案层保存，目标档位和价格作为关联项；只有申请办法或关键适用条件确实不同，才拆方案。

**三、存储方式确定为关系表与有类型的 JSON 结合**

继续使用 PostgreSQL，不引入独立图数据库或向量数据库作为前提。

具体分工是：

| 数据 | 存储方式 |
|---|---|
| 项目、等级、活动、方案身份 | 关系表、稳定 ID |
| 映射、方案关联、价格归属 | 明确的关系记录 |
| 金额、币种、目标档位、可确定的时间 | 有类型字段 |
| 复杂资格、挑战说明、例外条件 | 有固定结构的 JSON，保留原文和状态 |
| 来源正文 | 文档版本＋章节、段落、表格内容 |
| 证据 | 指向文档版本和具体内容位置 |
| 简报 | 绑定事实版本的派生产物 |
| 图谱和候选 | 查询计算，可缓存，不另存为权威事实 |

这里不是“能拆多细就拆多细”。

适合计算的内容必须结构化；无法可靠结构化的规则，保留文字、证据和未知状态。例如：

> “通过其他匹配活动取得的会籍不适用。”

可以先作为明确的资格限制保存，不必为了统一形式，立刻建设一套能表达所有条款的复杂规则语言。

但**未知、不适用、没有要求**必须明确区分，不能都用空值表示。

**四、来源资料和活动事实统一组织，但分别保存**

你说的“查询活动资料”仍然是一个能力。后台同时包含：

- 已提取、可用于查询的事实；
- 支持这些事实的 FAQ、Terms 等内容。

这样用户问价格，读取价格；问条款细节，读取相关条款；两者有冲突，能回到来源核对。

文档处理确定为：

1. 保留采集时的页面版本。
2. 提取清洗正文。
3. 按实际结构识别 FAQ 问答、条款章节、表格和脚注。
4. 为内容位置建立稳定的版本内引用。
5. 事实引用这些位置。

**不采用纯粹按固定字数切段的方式处理全部内容。**价格表与脚注、规则与例外需要保持关联。

同一篇文章可以涉及多个活动；一个活动也可以有多份资料。官方来源和第三方来源保留各自身份，不能因为进入同一个库就获得相同权威性。

**五、事实更新采用“版本发布”，三种产品读取同一版本**

Workflow 每次更新资料，不直接零散覆盖各处数据，而是：

```text
取得来源新版本
   ↓
提取草稿事实和关联关系
   ↓
校验证据、价格归属、映射方向、时间与冲突
   ↓
发布新的活动知识版本
   ↓
简报、图谱和 Agent 读取新版本
```

这能避免：

- 图中已经显示新价格，简报仍无标记地显示旧价格；
- Agent 拿着旧条款解释新活动；
- 一半数据更新成功，另一半仍属于上一版。

历史版本保留，当前版本明确。

另外分别记录：

- 最后检查时间；
- 来源内容变化时间；
- 事实版本发布时间；
- 活动规则自身的生效、截止时间。

这些时间不能相互替代。

第三方报道没有明确截止日时，也不应因为超过某个展示期限，就直接声称“活动已结束”。**活动状态与资料新鲜度需要分开表达。**

**六、渐进披露确定为四种读取视图**

这四种视图从同一套数据生成，不维护四份副本。

| 读取视图 | 提供什么 | 适合的问题 |
|---|---|---|
| 概览 | 活动身份、目标、状态、主要条件 | “这个活动是什么？” |
| 比较 | 路径、适用费用、挑战、期限、关键未知 | “我能走哪些路线？” |
| 详情 | 某个方案或步骤的完整相关事实 | “这一步具体怎么申请？” |
| 依据 | 条款段落、表格、例外与历史变化 | “哪里写了这个限制？” |

模型默认接收**浅层 JSON＋必要的短文本**。URL、全文、重复步骤和内部元数据不默认展开。

两个原则固定下来：

- 决定是否值得选的关键限制，必须在概览或比较阶段出现。
- 展开内容超过预算时，明确告诉模型还有未查看内容，不悄悄截掉。

Agent 的主要业务读取能力因此可以保持简单：

- 查询活动资料；
- 查询匹配关系与路线；
- 调查外部申请经验。

内部多表关联由程序完成，不能把数据库结构的复杂度转交给模型。

**七、简报重做成“活动更新与行动信息”**

简报不再是采集一篇文章后生成一段泛泛总结。

我建议分成两个清晰的呈现对象：

- **当前活动卡**：现在有什么机会、适合什么来源、主要费用和限制。
- **更新简报**：本次到底新增或改变了什么，对申请有什么影响。

它们共同引用当前事实和版本差异。

这样能减少同一个活动被不同文章重复介绍，也能回答：

> “我之前看过这个活动，这次有什么值得再看的？”

金额、日期和活动状态由事实直接填入；AI 负责组织重点和解释变化。生成文字不能成为另一套事实来源。

无需为了展示与用户会籍的关联，再单独生成一份内容：关联提示可以由程序计算。

**八、匹配树重做成“关系探索＋路线比较”**

后台保存直接申请关系，程序计算可达路径。前端可以保留树状布局，但不再让树的限制决定数据模型。

具体体验确定为：

- 初始显示已有会籍和直接相关机会，支持继续展开。
- 同一会籍节点可以只画一次，但保留多种到达方式的入口。
- 用户选定目标后，进入少量有差异的路线比较。
- 连线对应具体申请方案，点击能看到条件、费用和依据。
- 未知费用、待确认资格、条件路线有明确标记。
- 没有来源会籍要求的公开挑战，作为独立机会展示，不伪造一个会籍起点。

**不再以“只保留最短路径”代替推荐。**最短可以是一种查看方式，但费用更低、条件不同的路线不能因此消失。

Agent 的精选路线图与普通匹配图共用同一个路径服务，区别只是选取范围和呈现方式。

**九、用户数据与运行数据保持克制**

长期用户记忆只保存确认后的会籍。

临时工作区保存当前对象、条件、路线顺序和资料引用，到期清理，不反复保存所有原文。

用户明确建立的等待目标作为可结束的业务任务持久化，不扩展成长期画像。

采集日志、模型运行、审核和错误记录归入后台运行部分，默认不进入 Agent 上下文。

StatusMatcher 经验单独标注来源和观察时间，用于比较，不能混入官方活动规则。

**十、重构顺序也确定下来**

我建议按下面的顺序实施，而不是先做新页面：

1. **建立统一模型**：活动、申请方案、映射、价格、来源和证据关联。
2. **迁移已有资料**：能可靠关联的迁移，不能确定的保留未知，不自动猜。
3. **改造 Workflow**：产出统一知识版本，再生成简报。
4. **实现共用查询服务**：活动资料、路径计算、分层披露。
5. **重做 Agent、简报与匹配图**：全部消费同一套查询结果。
6. **对照验收后切换**：旧数据与实现先保留，验证完成后再退役。

验收不只看表结构是否漂亮，而看同一个实际问题能否贯通：

> 用户问某条路线多少钱——图、简报、Agent 必须使用同一个适用价格；点开依据，能定位到对应版本的价格表和条件；条件不明时，三个入口都不能装作已经确定。

**这套架构可以作为后续设计和实施的基准：统一保存活动知识，明确关联申请方案，按版本发布事实，按问题渐进读取，三个产品入口共用同一底座。**

## 回合 01a070fb-28f5-7e92-96b3-ae61fbc042bf

状态：completed

### 用户

接下来讨论下这个联网搜索statusmatcher的功能，这个的信息怎么读取，需要结构化存入吗还是只在工作区临时就行，还有这个读取具体是咋读取的，怎样跟整体交互产生比较强的联动性


### 助手最终答复

我的建议是：**StatusMatcher 信息需要结构化，但只作为当前工作区的临时调查结果，不进入正式活动知识库。**

“结构化”和“长期存储”是两回事。结构化是为了准确比较、引用和继续追问；长期积累案例库，目前没有必要。

**一、它在整体系统中的位置**

我们现在的活动知识库回答：

> 规则是什么、有哪些路径、适用费用和条件是什么？

StatusMatcher 回答：

> 类似申请者实际遇到了什么，这些案例能给当前选择提供多少参考？

二者通过**具体申请步骤**关联：

```text
当前讨论的活动或路线
    ↓
确定要调查的申请步骤
    ↓
读取、筛选 StatusMatcher 案例
    ↓
形成临时经验结果
    ↓
辅助比较、解释风险、继续追问
```

经验不能改写官方价格或创建新的匹配关系。如果案例说活动已关闭，它应促使 Agent 核对当前活动资料，而不是直接把数据库中的活动标成关闭。

**二、具体怎样读取**

我建议把读取分成四步。

**第一步：生成明确的调查对象。**

不能只搜“Flying Blue 成功率”。程序应尽可能确定：

- 来源项目和等级；
- 目标项目和等级；
- 对应活动、申请方案；
- 关注问题；
- 与问题有关的临时条件，例如来源会籍是否通过匹配取得。

这些信息从当前路线和工作区获取。用户说“查查第二条”，不必再复述。

如果缺少的信息会明显影响案例比较，再追问；不影响的字段可以保持未知。

**第二步：定位公司页及相关报告。**

优先使用项目与 StatusMatcher 公司页的映射，读取相关报告列表；需要搜索时，将范围限制在 StatusMatcher，搜索结果仅用于定位报告。

不能只看公司页汇总百分比，也不能拿搜索摘要直接计算观察结果。

**第三步：按需打开报告详情。**

这是现有实现最需要补上的地方。

目前代码主要读取公司列表页，从标题和摘要提取信息。我刚核对的报告详情页实际包含来源和目标等级，以及报告提交日期，说明有条件进行更细的筛选；但不能假设所有报告都填写完整。[报告页面示例](https://statusmatcher.com/report/137547)

正确的读取应当是：

> 列表发现可能相关的报告 → 打开少量相关详情 → 获取明确字段 → 判断可比性。

不需要把列表里的所有报告都展开。

**第四步：筛选、去重和统计。**

优先看近期报告，并区分：

- **可直接比较**：双方项目、等级和已知关键条件相符。
- **部分可比**：方向相关，但等级、申请方式或其他关键条件缺失。
- **不可比**：明显不是同一类申请。

这几类不能混在一个比例里。

报告提交日期和实际申请日期也要分开：最近发布的报告，可能描述很早以前的申请。

**三、临时结构化成什么样**

工作区里保存两层信息就够了。

| 层次 | 内容 |
|---|---|
| 报告记录 | 报告引用、日期、双方项目和等级、结果、可比性、相关经验要点 |
| 步骤调查结果 | 对应步骤、调查范围、样本数量、分类统计、限制、调查时间 |

单条报告可以理解成：

```text
报告引用：SM-01
对应步骤：路线 A 的第一步
来源／目标：明确项目和等级
报告提交日期：……
实际申请日期：已知或未知
页面结果标签：Match / Challenge / Deny
核对后的结果：直接匹配 / 获得挑战 / 拒绝 / 无法确认
可比性：直接可比 / 部分可比 / 不可比
与当前问题相关的要点：……
原始报告链接：……
```

**页面标签和实际描述要分别保留。**例如标签写 Match，正文却描述必须完成挑战，不能直接算成无条件匹配成功。存在矛盾就标记不确定。

金额、地区、资格等案例描述，只是“报告者称……”，不晋升为官方事实。

**四、哪些临时保留，哪些不保存**

我建议：

| 数据 | 处理方式 |
|---|---|
| 下载的完整 HTML | 默认仅在本次处理内使用 |
| 与问题相关的结构化报告信息 | 工作区临时保留 |
| 聚合统计、限制和引用 | 工作区临时保留，支持后续对话 |
| 公司页定位映射、解析器配置 | 作为程序配置维护 |
| 请求成功或失败、耗时等诊断 | 保存必要的精简运行记录 |
| 报告正文长期镜像、全站案例库 | 不建设 |

工作区临时数据可以放在 PostgreSQL 中并设置过期清理，并不一定只能放内存。这样刷新页面或短暂重启后仍可继续讨论，但不会逐渐变成长期经验库。

同一工作区、相同调查对象可以复用结果，并显示调查时间。用户明确要求刷新，或活动版本、关键条件发生变化时，再重新调查或重新判断可比性。

这里有一个实际前提：StatusMatcher 当前条款明确限制未经书面同意的内容复用，所以**临时存储也不能自动视为不受限制**。正式自动读取、结构化和展示的范围应与取得的授权一致；未启用时明确返回不可用，不阻止官方资料推荐。[StatusMatcher 条款](https://statusmatcher.com/terms)

**五、怎样与对话形成强联动**

联动的关键不是“查完附一段网页摘要”，而是**结果始终绑定当前问题和具体步骤**。

例如：

> 用户：“A、B 两条哪个更稳？”

Agent 读取两条路线的相关步骤，调查后可以回答：

> A 的近期可比报告更充分；B 的关键一步缺少相同来源等级的案例。因此目前更倾向 A，但不能据此推算真实审批概率。

用户接着问：

> “B 主要是什么原因被拒？”

直接复用工作区已有报告，提取拒绝相关的内容；已有信息不足，再定向补查，不重新从头搜索。

用户又补充：

> “我的来源会籍也是匹配来的。”

程序重新判断原有案例的可比性。之前作为强参考的样本，可能因为没有说明会籍取得方式而降为部分可比。**经验结果应随用户条件变化，而不是一旦查过就永久有效。**

另一个联动方向是回查官方资料：

> 多份案例提到来源会籍取得方式有影响。

Agent 可以接着查询对应活动的 FAQ／Terms，解释：

- 官方是否有明确规定；
- 案例反映了什么；
- 两者是否一致；
- 哪一点仍无法确认。

这才是活动知识库和外部经验真正配合起来。

**六、多步路线按步骤调查，共用步骤只查一次**

假设：

```text
路线 A：已有会籍 → X → Y
路线 B：已有会籍 → X → Z
```

“已有会籍 → X”是共用步骤，本次只调查一次，两条路线引用同一结果。

每一步分别保留经验信号。某一步证据不足，就要明确它是整条路线的不确定环节，不能用其他步骤的大量成功报告掩盖，也不能把各步观察比例相乘，声称得到整条路线成功率。

如果调查结果让原首选失去优势，可以调整推荐顺序；但必须仍满足原来的费用、挑战等硬条件。

**七、呈现上继续保持简洁**

不额外堆一组报告卡片或点击入口。

路线卡上只增加一句必要的经验状态，例如：

> 经验：近期可比案例有限，第二步待确认。

用户点击整张路线卡，在原有详情面板中看到“申请经验”部分：样本范围、结果分布、主要观察和少量来源引用。

“再查一下”“比较申请经验”仍是回答末尾的下一步对话建议，与卡片点击分开。

所以这项能力可以确定为：**围绕具体步骤按需调查，生成可追溯的临时结构化观察，随当前问题和用户条件更新，并参与路线比较与官方条款核对。**它不会成为第二套活动事实库，也不只是一次与后续对话脱节的联网搜索。
