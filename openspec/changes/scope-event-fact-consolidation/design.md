## Context

文档分类阶段已经能为一篇材料输出多个 `event_hint`，聚合阶段也会把每个提示分别关联到 `StatusEvent`，但事实整理阶段把这些关联压平为去重后的正文列表，只向 AI 提供不透明的 `event_id`。因此，同一正文关联多个活动时，事实整理缺少明确边界。另一方面，每次证据集合变化都会新建 `FactSetRecord`，即使新来源没有增加任何事实。

现有 `StatusEvent` 已保存活动上下文，`EventEvidence.locator` 已保存对应 `event_hint.summary`，原始正文、事实版本和简报版本也都已持久化。本次应复用这些结构，保持第一版轻量和解耦。

## Goals / Non-Goals

**Goals:**

- 让事实整理明确知道当前处理的唯一活动，同时仍能读取完整正文。
- 防止较弱或不完整的新来源删除已有事实。
- 仅在事实值、冲突状态或备选值发生变化时创建新事实和简报记录。
- 将以长期教学为主要目的的攻略排除在第一版会籍机会流水线之外。

**Non-Goals:**

- 不新增 `GUIDE` 标签或攻略流水线。
- 不切割、复制或改写原始正文。
- 不引入来源评分、来源白名单、向量数据库或来源专用抽取规则。
- 不在第一版自动裁决相互冲突的已知值。

## Decisions

### 使用事件上下文限定完整正文，而不是拆分文章

事实整理输入包含 `StatusEvent` 的 program、opportunity type、target status、summary，以及每份 `EventEvidence` 的 hint index 和 locator。正文保持完整；上下文只承担路由作用，最终事实仍必须引用正文中的 document ID、URL 和定位。

替代方案是按段落拆文章，但这会引入不稳定的正文分段、跨段事实丢失和来源专用规则，超出第一版边界。

### 复用现有 EventEvidence，不修改数据库结构

`EventEvidence.locator` 已等于分类阶段的 `event_hint.summary`，足以为 AI 指明当前材料与活动的关联。事实整理改为查询 `(EventEvidence, DocumentVersion)`，无需增加列或迁移数据。

### 对完整候选 FactSet 做确定性逐字段协调

AI 仍基于同一事件的全部历史材料输出完整候选 `FactSet`。系统随后按字段协调：当前未知而候选已知时接受补充；当前已知而候选未知时保留当前值；值相同时保留当前字段和已有证据；不同的已知值不允许静默覆盖，而是形成冲突并进入人工复核。

这种方式让 AI 负责语义理解，让少量确定性规则负责数据安全边界。

### 实质变化比较忽略单纯证据变化

事实签名只包含每个字段的 value、conflict 和排序后的 alternatives，不包含 evidence。新来源内容相同或更弱时，`EventEvidence` 仍会保存，但当前 `FactSetRecord` 被复用；`BriefGenerator` 随后通过现有 fact set ID 复用简报，不再次调用 AI。

### 提示词版本独立升级，输出 Schema 保持不变

分类提示词和事实整理提示词分别升级版本，避免复用旧运行。`RelevanceResult` 和 `FactSet` 输出结构没有变化，因此不提升 Schema 版本。

## Risks / Trade-offs

- [AI 仍可能忽略活动边界] → 在系统提示中声明上下文仅用于当前唯一活动，并通过同文档双活动测试检查输入隔离和结果隔离。
- [不同措辞表达同一事实可能产生新版本] → 第一版使用规范化后的结构化字段值；后续由金标评估是否需要更强的值规范化。
- [真实规则更新被暂时标为冲突] → 第一版优先不误覆盖；积累更新类金标后再设计自动取代规则。
- [新来源只提供相同事实时不会进入当前 FactSet 的来源链接] → 来源仍完整保存在事件证据中；当前简报继续沿用已验证的旧证据。

## Migration Plan

无需数据库迁移。部署后，新提示词版本使后续运行使用新逻辑；已有事实集和简报继续有效。若需回滚，只需恢复旧代码和提示词版本，已保存的文档与事件证据不受影响。

## Open Questions

无。自动处理明确更新、来源质量排序和 `GUIDE` 标签均留待后续独立变更。
