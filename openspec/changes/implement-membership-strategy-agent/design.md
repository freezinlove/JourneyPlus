## Context

JourneyPlus 当前是 Python 模块化单体：FastAPI 提供产品 API 和原生 JavaScript 页面，PostgreSQL/SQLAlchemy/Alembic 保存正式事实，`StatusHoldingService` 管理已确认会籍，`UnifiedMembershipTreeService` 从官方 StatusMatch 项目和普通文章构建来源中立的当前匹配图，`PersonalizedMatchService` 展示全部可达机会，现有 `AIProvider` 提供 Pydantic 结构化模型调用，`run_daily_cycle` 已具备数据库租约、幂等、模型预算和生命周期推进。

当前缺口不是另一个匹配引擎，而是受约束的语义决策层：用户用自然语言表达会籍、目标和取舍后，系统需要在关键歧义、正式写入、路线查询、经验调研、推荐、最小调整和持续跟进之间选择下一步。正式事实和可达性仍必须由数据库与匹配图判定。

现有数据有意保持保守边界：联盟归属已结构化，但联盟精英等级等价未结构化；挑战要求主要是证据化文本；多币种没有汇率换算。因此明确的项目、等级、联盟和显式费用可以确定性筛选，“高卡”“低成本”等相对表达由 Agent 结合候选事实取舍，无法证明免费、无挑战或跨币种高低时必须呈现为未知，不能猜测。

## Goals / Non-Goals

**Goals:**

- 交付一个实际可运行的单 Agent 完整链路，而不是固定的“解析→查询→润色”工作流。
- 保持 Agent、候选查询、持有会籍写入、外部经验调研、等待目标和 UI 之间低耦合，并复用现有图和事实读取层。
- 让模型在服务端给出的合法动作集合内，根据用户输入和工具观察选择确认、查询、调研、推荐、调整或持续跟进。
- 在代码层强制一次关键追问、三次模型调用、最多三个经验调研候选、一次最小调整、单等待目标和写入确认门。
- 提供同步回合 API 和纯呈现前端；在当前部署形态中完成数据库迁移、每日恢复、降级、审计和测试。
- 用真实自然语言、实际数据库/匹配图和 StatusMatcher 页面做一次大体正确的人工核验。

**Non-Goals:**

- 不建设通用 Agent 平台、动态工具注册、任意 DAG、多 Agent、长链规划或向量记忆。
- 不新增会籍权益、休息室、积分余额、行程规划、申请代办、支付、材料提交、申诉或异常中心。
- 不让 StatusMatcher 发现数据库外的新路线，也不把社区报告写入官方事实、生命周期或统一匹配图。
- 不发明联盟等级等价、实时汇率或“未记录挑战即无挑战”等领域事实。
- 不新增独立前端仓库、移动端、SSE、WebSocket、消息队列、独立 Worker 或新的定时器。

## Decisions

### 1. 使用一个薄型、类型化、阶段受限的 Controller

在 `journeyplus.agent` 内实现一个项目自有 Controller，复用 `AIProvider.generate_structured`。每次模型调用接收精简状态、工具观察和当前允许动作，并返回 Pydantic 校验的决定；Controller 再校验动作、参数、用户确认、授权和预算后执行普通服务。

Controller 不实现通用工具注册表。动作是封闭枚举，分派使用显式代码。一个 HTTP 回合最多三次模型调用；达到上限、输出非法或 Provider 不可用时返回可解释的失败/降级状态。

选择这一方案是因为动作少、回合短、确认与持久化规则属于本项目。PydanticAI/LangGraph 仍不能替代这些业务状态，反而会引入第二套运行抽象。固定流水线也被拒绝，因为它不能根据观察结果自主跳过追问、决定是否值得调研或在无解时选择调整分支。

### 2. 只保存一个短期交互和一个等待目标

新增两个表：

- `agent_interactions`：保存当前阶段、已结构化且必要的目标/取舍、待确认会籍、候选引用、一次调整、调用计数、简短动作审计、到期时间和最后响应。它不保存模型思维过程或无限聊天历史。
- `agent_wait_goals`：保存唯一当前等待目标的确认条件、状态、最后候选签名、待展示的首次命中结果和通知时间。服务层保证同时最多一个 ACTIVE 目标。

首次输入会创建交互；后续确认、修改或拒绝通过同一 `interaction_id` 恢复。已完成/失败交互只读，短期状态到期后不可恢复。首次命中结果直接保存在等待目标中，不再引入 Notification 表。

相比把状态全部放在浏览器或完整聊天日志中，这一设计能支持服务重启和每日恢复，又保持隐私与数据复杂度有界。

### 3. 候选路线查询只提供事实分类，不做推荐

在 `journeyplus.product.candidate_routes` 增加 `CandidateRouteService`。它复用已确认 `StatusHolding`、`UnifiedMembershipTreeService.reachable_forest` 和现有机会详情读取，遍历从任一持有会籍出发的当前路径，并输出：

- `matching_routes`：目标和全部可判定硬条件均满足；
- `nearby_routes`：恰好偏离一个硬条件，并列出该条件；
- `unknown_routes`：关键条件缺少可证明事实或需要未提供的跨币种比较。

路线包含节点路径、每一步的机会/来源引用、费用、挑战文本、条件、期限、冲突和证据链接。查询层只做目标匹配、硬条件判断、最短无环路径和稳定技术排序，不生成分数、首选或展示顺序。无映射的独立挑战机会在没有可证明来源会籍适用性时不能作为“从我的会籍可达”的正式路线。

明确项目/等级和联盟归属可以作为硬目标。“联盟高卡”等相对等级保留为 Agent 偏好：查询层先返回该联盟内可达路线，Agent 根据目标等级标签取舍并说明现有数据未证明联盟等级等价。显式 `FREE_ONLY` 只接受证据明确的零费用/免费；`NO_CHALLENGE` 遇到未记录挑战要求时进入未知而非当作满足；显式最高金额只在同币种时比较。

### 4. 自然语言理解与正式写入分开

模型先输出结构化的持有会籍候选、目标、硬条件、软偏好、是否请求实际经验和下一动作。目录解析器只允许唯一命中的项目/等级进入“待确认”；歧义会触发本次唯一的关键问题。

自然语言中新出现的会籍在用户明确确认前不写库。确认后仍由 `StatusHoldingService.upsert` 重新校验目录并写入。已有且完全相同的持有会籍无需重复确认。目标和普通取舍只保存在短期交互；只有用户确认持续跟进时才复制到等待目标。

### 5. Agent 拥有主观取舍和无方案下一步

候选查询后，模型可以根据观察选择：

- 直接给出一个首选和最多两个有实质差异的备选；
- 已授权且经验可能影响选择时，调查这些最终候选后再推荐；
- 没有 `matching_routes` 时，从 `nearby_routes` 中只提出一个最小条件调整；
- 不足以安全推荐时明确说明未知项，不把 `unknown_routes` 包装为可行。

用户确认调整后，程序只修改该一个条件并重新查询。用户拒绝调整，或调整后仍无 `matching_routes`，Agent 主动提出“按当前条件持续跟进”；用户只需确认、修改或拒绝。确认才调用等待服务，拒绝即结束，不继续自动放宽条件。

### 6. StatusMatcher 是受控只读工具

`StatusMatcherExperienceClient` 只访问 `https://statusmatcher.com/company/<slug>` 的公司页，设置固定域名、HTTPS、连接/总超时、响应大小、User-Agent 和最多分页数。目标项目 slug 先通过受控公司页查找/别名解析；不能可靠解析时返回 unavailable，不允许模型构造任意 URL。

页面解析只抽取“Reports for obtaining status with …”区域中与规范化来源项目可比的最近可见报告，分类 `MATCH/CHALLENGE/DENY/OTHER`，保留短摘要和页面链接，并汇总材料、等待、地区或拒绝模式。工具输出是社区经验信号，不称作真实审批成功率。

自动访问由 `JOURNEYPLUS_STATUSMATCHER_ENABLED` 默认关闭的服务端开关门控；只有已有正式候选、用户请求/同意实际经验且候选不超过三个时 Controller 才暴露动作。失败、HTML 变化、样本不足或未授权都返回结构化降级，不转向全网搜索。测试使用固定 HTML；最终人工验收可在本次用户授权下核对公开真实页面。

### 7. 每日检查确定性运行，命中后才恢复 Agent

在现有 `run_daily_cycle` 生命周期推进之后调用 `WaitGoalService.check_current`。检查只运行 `CandidateRouteService` 并计算候选签名：无目标或无新 `matching_routes` 时零新增模型调用；签名已通知时不重复处理；首次新命中时才用同一 Agent 应用服务生成待展示结果，必要且获授权时调研 StatusMatcher。

等待检查结果写入现有 `AutomationRun.processing_result` 的 `agent_waiting` 字段，并在 `DailyCycleSummary` 暴露简短计数。Agent 恢复失败不破坏来源采集或生命周期结果，等待目标保留以便下次安全重试；成功后记录签名并只展示一次。用户接受、取消或明确不再等待后关闭目标。

### 8. API 是前后端唯一业务边界

`create_product_app` 接受可选 `AIProvider` 和 StatusMatcher client；无 Provider 时 Agent API 返回明确不可用，既有确定性页面/API 不受影响。新增：

- `GET /agent`：Agent 页面壳；
- `POST /v1/agent/turn`：自然语言、确认、修改、拒绝、取消等待等所有回合命令；
- `GET /v1/agent/state`：当前短期交互、等待目标和待展示首次命中结果。

请求和响应均为 Pydantic 契约。前端只渲染响应中允许的操作并提交用户输入，不复制目录、候选、动作或等待规则。页面和 API 同仓是部署选择，不改变职责边界。

### 9. 生产接入保持现有部署模型

`product-api` 在配置了 AI 凭证时创建现有 Provider 并注入 Agent；未配置时服务仍可启动，Agent 页面显示不可用但其他功能正常。数据库仍由启动流程执行 Alembic 升级。`run-daily` 复用同一个 Provider、数据库租约和模型总预算；等待目标只有命中时才占用预算。

日志只记录交互 ID、Prompt/Schema/模型版本、动作、工具状态、耗时和引用 ID，不记录推理过程、完整报告正文或敏感证明材料。

## Risks / Trade-offs

- [现有数据无法证明联盟等级等价] → 把“高卡”作为 Agent 取舍而非确定性事实，结果中明确提示，后续只能通过正式数据增强改善，不在 Agent 中硬编码真相。
- [挑战字段缺失导致可用路线被归为未知] → 保守呈现 `unknown_routes` 和待核实项，优先保证不误称“无挑战”；用户仍可放宽该硬条件重新查询。
- [StatusMatcher 页面结构或访问策略变化] → 默认关闭、域名/预算受限、固定 HTML 契约测试、解析失败结构化降级；不影响正式候选和基础推荐。
- [模型输出合法 JSON 但业务动作越权] → Controller 根据阶段动态生成允许动作并二次校验；所有写入由普通服务重新验证。
- [同步回合受外部调研延迟影响] → 严格超时、候选上限和最多分页；超时立即降级，不引入异步运行平台。
- [每日命中恢复失败影响主自动化] → 等待检查隔离捕获异常并记录到 `agent_waiting`，不改变主采集结果；未成功生成结果不推进去重签名。
- [单用户单等待目标限制扩展] → 与当前本地单用户产品一致，表结构保留 UUID 与 JSON 契约，未来引入账户时可增加 owner 键，但本次不预建账户系统。

## Migration Plan

1. 增加 Agent 运行契约、候选查询和纯服务单元测试，不改变既有 API。
2. 新增 `agent_interactions` 与 `agent_wait_goals` Alembic 迁移，并验证 SQLite 测试和 PostgreSQL 升降级。
3. 接入 Controller、StatusMatcher 客户端、等待服务和 Agent 应用服务；所有外部调研保持默认关闭。
4. 接入 FastAPI、原生前端和 CLI Provider 注入，再扩展每日工作流。
5. 运行全量测试、架构约束测试、真实模型烟测（凭证可用时）和真实页面人工核验。
6. 部署时先迁移数据库，再以关闭 StatusMatcher 的模式启动；确认授权与页面契约后显式启用。

回滚时关闭 Agent/StatusMatcher 配置即可保留既有产品路径；代码回滚前执行 Alembic downgrade 删除仅由本功能使用的两张表。已有会籍表和正式事实不受影响。

## Open Questions

- 生产环境对 StatusMatcher 自动读取的长期授权与请求频率需要由部署方确认；实现以默认关闭和显式开关交付，不阻塞基础 Agent 上线。
- 当前没有用户账户，交互和等待目标按单产品实例管理；本变更不预设多用户身份模型。
