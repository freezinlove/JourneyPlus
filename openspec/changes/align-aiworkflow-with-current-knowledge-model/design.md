## Context

目标以 `doc/target-system-architecture.md` 为准。当前工作区保留用户设计的生产链，但 ORM 和写入入口尚未适配当前数据库。既有测试用于识别行为，不代表当前链路已通过新库验收。

审计发现：

| 环节 | 当前实现与问题 |
|---|---|
| 官方链 | `statusmatch/project_workflow.py` 解析 HOME/FAQ/TERMS，结合确定性映射、价格表及模型补充，合并后写 StatusEvent/FactSetRecord，再生成简报 |
| 普通文章 | `article_pipeline/` 批量筛标题、每篇正文提取、多活动物化、逐活动简报，仍写旧 ArticleAnalysis/Opportunity/Brief 表 |
| 关联文章 | `statusmatch/article_workflow.py` 读取当前官方事实和简报，单独提取亮点；其 mapping_claims 固定为空，不参与图事实 |
| 统一知识 | `knowledge/refresh.py` 依赖旧事件/文章身份再执行 KnowledgeWorkflow；不能作为最终必经桥接 |
| 简报 | `briefs/service.py` 和文章简报已有模型编辑能力；`knowledge/briefs.py` 只是较简化的确定性投影，不能替代前者 |
| 图 | 旧 `membership/unified.py`、贡献适配器及 `statusmatch/graph.py` 与新 `knowledge/routes.py` 并存；语义覆盖不能凭接口名称假定相同 |
| 存储 | ORM 缺 ActivitySourceBinding/ActivitySupplement，仍有 current_event_id、event_id、evidence_ids、section_scope 等与库不符的字段 |
| 生命周期 | 官方关闭逻辑写旧事件；普通文章的 180 天图可见期不等于申请截止时间 |

数据库实际基线为 `clean_0003` 加 `migrations/manual/optional_price_description.sql`、`relax_workflow_constraints.sql`。此前归档见 `doc/database-archives/2026-09-12-before-relaxation/`；其中 schema 是约束放松之前的结构，不可单独当作当前最终 schema。创建本 change 时正常库业务表为空，只保留来源配置和迁移记录。

## Goals / Non-Goals

**Goals:**

- 保留阶段职责、正常顺序、来源策略、模型调用安排、失败恢复、缓存及确定性解析算法；改契约、接口和存储依赖。
- 直接生产一套正式知识；模型简报及确定性完整图使用相同版本事实。
- 原文和链接留档；不恢复字段级证据、精确原文校验和已放松的数据库约束。
- 减少旧 ORM 和桥接依赖，不为每个操作新增空包装层。

**Non-Goals:**

- 不重建数据库、不导入旧事实、不清理正常库、不启动后台写入。
- 不增加新来源、扩展买分链、重写 Agent harness 或改变 Agent 工具决策方式。
- 不默认新增身份整理模型、第二次通用事实提取或简报润色调用。
- 不在本 change 创建阶段执行实施任务。真实来源重建及真实模型验收另由后续明确执行安排触发。

## Decisions

### 1. 以行为对照清单保护现有设计

实施前记录每条分支的输入输出、阶段顺序、条件分支、调用数、重试上限、缓存键和消费者，并关联现有测试。对每项改动标注“存储/契约适配”“用户明确取消的证据要求”“业务行为变化”。前两类按本 change 执行；第三类先给前后示例和原因，与用户讨论后才实施。

不用一次替换整条链的方案，因为会隐藏功能损失。纯函数可以调整参数类型而保留算法；当 ORM 与业务逻辑混在一起时，只拆出必要的输入/输出边界。不能用旧 FactSet 作为永久必经事实契约，再转换成新事实。

### 2. 统一存储落点

| 数据 | 新模型落点 | 适配原则 |
|---|---|---|
| 原始与规范正文、链接和时间 | source_items / document_versions / 按需 document_sections | 保留归档、去重和重解析；不建精确证据索引 |
| 来源与活动身份 | activity_source_bindings / activities | 用来源主体关联活动及期次，退出 legacy 表名/旧 ID 身份键 |
| 会员名称与等级 | membership_programs / tiers / aliases | 利用现有解析和命名能力，从空目录建立；不预置旧测试事实或猜等级关系 |
| 阶段输出、状态、错误、用量 | analysis_runs 及现有调度记录 | 允许必要草稿，不建立第二套正式事实；一文多活动可复用一次分析 |
| 正式事实 | activity_knowledge_versions | 关联活动、分析及来源绑定，计算内容/来源指纹 |
| 独立申请方式 | application_options / application_option_versions | 稳定身份与版本内容分离，保留申请链接 |
| 映射、价格及适用关系 | option_mappings / option_prices / option_price_mappings | 不用笛卡尔配对，不用活动最低价代替目标/方案价格 |
| 输入文档 | activity_documents | 文档级、角色级关联即可，无需逐条引文 |
| 简报、文章亮点 | activity_briefs / activity_supplements | 绑定知识版本，补充亮点不改正式费用或资格 |

新 JSON 字段格式须在契约中明确，但不新增数据库 JSON 校验或其他限制。未知链接明确缺失；申请链接不由文章 URL 自动补成。官网入口优先由官方主文档关联表达，原文链接从文档读取，避免保存多份可独立修改的同义链接。

ORM 只采用库实际存在的表和字段。失败原因写现有分析/处理记录，不重新添加 activity_briefs.error_code。迁移入口须能从空 PostgreSQL 建立当前结构，并识别已有补丁；不盲目 stamp、不重新施加旧唯一性、READY-only、补充顺序或格式版本限制。

### 3. 保留三条生产分支，替换结果契约

官方链继续先取得三页、运行确定性表格解析、模型补充和合并。解析器改为输出新映射/价格草稿或无存储语义的必要解析对象；保留原算法，不先写旧事件和 FactSet。模型已提取的信息不再交给 KnowledgeWorkflow 整体提取一遍。

普通文章保留批量标题筛选、失败放行、一次正文提取多个活动及每活动简报。多活动结果分别建立来源绑定和知识草稿，AnalysisRun 记录整篇分析。内容相同但来源不同的文章是否独立、最新成功分析取代旧结果等行为按原回归清单保留。

关联 StatusMatch 文章继续先发现项目关系，复用已有官方结果，按原策略处理官方未就绪、已关闭、抓取失败及多 host 路由。亮点写 activity_supplements，零亮点仍为成功且可复用；幂等状态写分析记录，不能因没有补充行而重复调用模型。保留其依赖官方结果的必要业务关系。

去掉 evidence_ids、EvidenceQuote、逐字引用和链接必须作为正文子串等精确校验门槛；保留模型从输入资料提取而非编造链接的要求。确定性解析原文属于提取能力，不能因取消“原文校验”而删除解析器。对费用策略、冲突处理函数逐段区分提取/合并/业务判断与引文检查，禁止整函数粗暴删除。

### 4. 调用数与缓存不因模型适配增加

| 分支 | 保留的正常调用安排 |
|---|---|
| 官方项目 | 既有项目提取/模型补充，以及原模型简报生成；按现有缓存跳过 |
| 普通文章 | 按原批次标题筛选；每篇正文提取；每个活动简报；标题筛除与已有结果复用仍有效 |
| 关联文章 | 按原文章/项目组合执行补充亮点调用 |
| 图、字段装配与落库 | 不调用模型 |

先测量同一批固定输入在原逻辑中的实际阶段计数，不能把动态批次、活动数量概括为固定总次数。移除可选 knowledge-refresh 二次提取，但当前该开关关闭，不宣称减少了当前正常调用数。正常调用上限保持；重试取消证据拒绝原因后可能减少，模型输出形状变化的实际成功率必须记录。更改契约版本使旧缓存不会被错误当作新结果，同时避免重复调用。

### 5. 模型简报保留，发布只调整必要衔接

保留中文简报生成、现有内容组织、来源链接、具体映射示例、更新摘要与重试策略。输入改为统一知识草稿/版本事实，输出写 activity_briefs；fact_refs 可以引用结构化字段，不是原文证据。历史 knowledge/briefs 的简化投影只能复用辅助能力，不替代原模型简报。

准备阶段存草稿和分析状态，模型调用在事务外进行。简报、必要图投影校验完成后，以短事务复核输入文档和 base_version、发布知识、保存产物并切换当前指针。简报失败仅重试简报，旧版本仍可读。来源已变时丢弃过期发布尝试并记录原因，不覆盖新版本。

库已允许简报重生成，但应用层仍保证历史引用有稳定语义：同一知识版本重试/修正文案不得修改正式事实，成功切换前保留可用结果；是否需要保存多份简报修订在字段契约审计中确认，不擅自扩表或重加不可变触发器。影响原阶段顺序的衔接细节先与用户讨论。

### 6. 完整图保留语义，收敛共用读取

把“从旧表取得贡献”改成从当前知识版本取得方案、映射和价格。复用目录归一化、别名处理、去重、循环/交叉引用和多跳能力；整理共同的源范围、条件、价格适用和时间判断，知识页面和 Agent 路径服务共用。只适配公共读取契约及必要调用处，不借机重构 Agent。

不能直接以现有 RouteService 的短名单替换完整图。对官方+文章混合多跳、多来源同边、条件边/冲突/不可用、最新成功版本、180 天可见期、实际期限、手工归档恢复/延期行为逐项比较。180 天是图可见政策，不能写成申请期限；其来源和有效时间在既有 JSON/处理记录中明确定义，禁止暗中丢弃或加数据库约束。完整结果受技术预算限制时明确 coverage/partial 和可继续取得的范围，不宣称完整。

### 7. 调度与旧路径退出

保留已有显式任务、资源预算、阶段状态及事务外 HTTP/模型调用结构，替换 pending 查询、旧 ID、版本指纹和关闭状态写入。暂停/失败/零结果分开，采集成功不等于知识发布成功。用户未变更的来源范围和关闭政策保持不变。

生产入口最终只有当前契约；退出 knowledge-refresh 的旧记录桥接、knowledge_migration_links 和正式消费旧查询回退。历史迁移/审计资料可保留，不运行旧消费者。处理旧 CLI 的说明及必要报错，不恢复缺失表来让旧命令“暂时能跑”。

## Risks / Trade-offs

- [业务逻辑混在 ORM/证据校验中] → 逐函数标注职责，保留原测试场景，避免整块替换。
- [旧模型没有明确价格到映射关系] → 在原提取阶段契约里补清语义；无法判定保持未知，不额外调用模型或机械配对。若原调用无法表达需讨论。
- [空目录无法直接使用 UUID 契约] → 服务端解析稳定名称与目录身份，复用已有名称算法；模糊身份记录待处理，不引入隐式身份模型调用。
- [旧图行为在新 RouteService 中缺失] → 独立图语义对照测试，不以接口成功或节点数量作为等价证明。
- [输出形状变化影响模型质量] → 固定输入比较阶段调用和结果，保留失败；模拟模型测试不能冒充真实模型验证。
- [发布顺序影响简报/补充依赖] → 把需要改变的先后关系列成可审阅差异，先讨论；保持业务依赖而非追求形式解耦。

## Migration Plan

1. 冻结行为与模型调用基线、字段落点和当前 schema 指纹，列出必须讨论的业务差异。
2. 对齐 ORM/契约及可复现的迁移链，在临时 PostgreSQL 验证，不改正常库数据或追加限制。
3. 先迁官方链与模型简报，随后普通文章、关联文章补充，再收敛图读取与调度入口；每条链独立回归。
4. 使用正常生产入口、固定来源响应和计数模型替身跑空库生产、更新、失败、重试；读取同一库核对简报和图。正常服务数据库保持空业务状态。
5. 输出差异、调用数、字段保真和剩余事项。真实模型及正常库重新入库作为后续明确安排，不通过自动调度顺带执行。

实施回退优先撤回应用变更、停止写入并保留失败记录；不回滚到旧业务 schema、不丢数据、不重写 Git 历史。只采用已确认结构时无需生产库结构回滚。已放松的六项限制不得因 ORM create_all 或迁移而重新出现。

## Open Questions

以下是实施前的有限核对项，不是授权新增流程或字段：

- 哪些原价格/映射结果尚无明确方案适用关系，需要在原阶段输出中补表达？
- 原手工可见期覆盖、关闭及期次处理信息如何无损映射到既有 JSON/记录？
- 简报修订与历史引用、官方简报和文章亮点组合的发布时点，哪些确实需要改变原有衔接？
- 当前原图与统一 RouteService 的行为差集有哪些，哪些公共函数值得复用？

无法保留原生产设计或需要增加调用时，列出具体前后行为并与用户讨论；不以本 change 已创建为由直接实施策略变化。
